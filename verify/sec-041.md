## 41. Agent Loops, Planning and Termination

*Mastering this proves you understand that a well-instrumented single-model loop with good tools beats an elaborate graph in most products — and can say when it stops being true.*

### Whiteboard me an agent loop. No framework — just the loop. And tell me where the state actually lives.

An agent loop is a `while` loop around a stateless function. That is the whole idea, and it is the sentence I want a candidate to lead with, because every confusion downstream comes from forgetting it. The model is a pure function from a token sequence to a token sequence. It has no memory, no session, no "the agent decided". What people call "the agent" is your list of messages plus your dispatcher. If your process dies, the agent does not exist anymore — unless you wrote the list somewhere durable.

```python
def run(task: str, tools: dict, max_steps: int = 20, token_budget: int = 200_000):
    messages = [{"role": "user", "content": task}]
    used = 0
    for step in range(max_steps):
        resp = client.messages.create(
            model=MODEL, max_tokens=4096, tools=[t.schema for t in tools.values()],
            system=SYSTEM, messages=messages,
        )
        used += resp.usage.input_tokens + resp.usage.output_tokens
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason != "tool_use":
            return final_text(resp), "completed"
        if used > token_budget:
            return None, "budget_exhausted"

        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            try:
                out = tools[block.name](**block.input)
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": truncate(out, 4000)})
            except Exception as e:                      # errors go BACK to the model
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": f"error: {e!r}", "is_error": True})
        messages.append({"role": "user", "content": results})
    return None, "max_steps_exhausted"
```

That is roughly 30 lines and it is a real agent. Everything a framework sells you is a wrapper around this: `messages` becomes a typed state object, `for step in range` becomes a graph traversal, `messages.append` becomes a reducer, and persistence becomes a checkpointer.

**Mechanism, precisely.** State is `messages` — an ordered, append-only log. The model re-reads the entire log every turn, which means the loop is quadratic in tokens: step *n* pays for all *n−1* prior steps. Your dispatcher owns tool execution, truncation, and the termination decision. Notice the loop has *three* exits: natural stop, budget, and step cap. A loop with one exit is a bug waiting for an on-call page.

**⚠ Trap:** returning tool errors by raising. Candidates reflexively `raise` on a failed tool call because that is correct backend hygiene. In an agent loop, an exception is a *lost turn* — the model never learns the file path was wrong and cannot self-repair. The rule I enforce in review: transport and auth failures raise (they are your bug); semantic failures ("no such customer", "invalid date format, expected ISO-8601") return as text with `is_error: true`. A well-worded error string is a free retry.

**🗣 Say this in the room:** "The agent loop is thirty lines. Everything hard is outside it — tool design, truncation, budgets, termination, and durable state. I'd rather ship a raw loop I can read in one screen with excellent instrumentation than a graph I can't reason about at 3am."

### What does the "thought" in ReAct actually buy you? Models have built-in reasoning now — would you still emit thoughts?

**📄 Paper:** Yao et al. (2022) — *ReAct: Synergizing Reasoning and Acting in Language Models*. Its contribution was interleaving free-text reasoning with actions in the same trajectory, replacing two prior designs: chain-of-thought (reasons, never acts, so it hallucinates facts it can't check) and pure action-only agents (acts, never reasons, so it flails without a plan).

The mental model: **the thought is scratch memory that the next forward pass gets to read.** A transformer has no hidden state carried between calls; the only channel from "what I worked out last step" to "what I do next step" is tokens in the context. So a thought is not the model narrating for your benefit — it is the model writing to the one register it has. Empirically it does three concrete things: it conditions the action distribution on an explicit goal restatement (which reduces off-task tool calls), it lets the model notice a contradiction between plan and observation without needing a separate critic call, and it gives *you* an auditable rationale to log.

Has native reasoning made it obsolete? Partly, and this is a genuinely live distinction. When the model exposes an extended-thinking mode, the thinking happens inside the same generation before the tool call, with the provider's own training behind it — that is strictly better than you prompting `Thought:` prefixes, and interleaved thinking (where thinking blocks persist across tool results within a turn) covers the same job. **📅 Volatile:** which providers support thinking blocks that survive across tool-result turns, and whether those blocks are billed as output tokens, changes; verify before your loop.

So my rule: **if the model has a first-class reasoning mode, use it and stop hand-rolling `Thought:`.** Keep an explicit thought field only when you need it in your trace for evaluation or user display, in which case make it a *structured* field — a short `rationale` string on the tool call — rather than free prose you have to regex out.

**⚠ Trap:** believing the thought is a faithful account of the computation. It is not. Post-hoc rationalization in chain-of-thought is well documented; a model can produce a thought that contradicts the action it then takes. Use thoughts as a debugging *hint*, never as ground truth about why the agent did something. If you build an alerting rule that fires on rationale text, you have built a lie detector out of the liar.

**💰 Math:** thoughts are not free. A 60-token thought per step over a 15-step trajectory is 900 output tokens; at $15/Mtok output that is 900 × 15/1e6 = **$0.0135 per run**, plus the compounding input cost of re-reading them: those 900 tokens get re-sent on average 7–8 more times, ≈ 6,750 input tokens × $3/Mtok = **$0.020**. So ~$0.034/run, and at 100k runs/day that is **$3,400/day** of narration. That is a real budget line, not a rounding error — which is why I strip thought text from the replayed context on long trajectories and keep it only in the log.

### Implement ReAct from scratch with text parsing, not the tool API. When would you ever still do that?

```python
import re
SYSTEM = """Answer using this exact format, one block at a time:
Thought: <your reasoning>
Action: <tool_name>[<single string argument>]
Then STOP and wait. I will reply with:
Observation: <result>
When you know the answer, emit:
Thought: <reasoning>
Final Answer: <answer>
Available tools: search[query], lookup[entity], calc[expression]"""

ACTION = re.compile(r"Action:\s*(\w+)\[(.*?)\]\s*$", re.S | re.M)

def react(task, tools, max_steps=10):
    transcript = f"Question: {task}\n"
    for step in range(max_steps):
        out = complete(SYSTEM, transcript, stop=["\nObservation:"])   # provider stop seq
        transcript += out
        if "Final Answer:" in out:
            return out.split("Final Answer:")[-1].strip(), "completed"
        m = ACTION.search(out)
        if not m:
            transcript += "\nObservation: Malformed. Emit exactly 'Action: name[arg]'.\n"
            continue
        name, arg = m.group(1), m.group(2).strip()
        obs = tools[name](arg) if name in tools else f"unknown tool {name!r}"
        transcript += f"\nObservation: {str(obs)[:2000]}\n"
    return None, "max_steps_exhausted"
```

The load-bearing detail most people miss is `stop=["\nObservation:"]`. Without it the model happily hallucinates its own observation and continues a fully imaginary trajectory — it will "search", "find" a result it invented, and answer confidently. The stop sequence is what makes the environment real. That single parameter is the difference between an agent and a very expensive fiction generator.

When would I still parse text in 2026? Three cases, and they are all real. **One: open-weight models without reliable tool-call training.** A small self-hosted model will emit tool JSON with hallucinated field names but follow a two-line text format fine — the text protocol has a shallower grammar. **Two: code-as-action agents**, where the "action" is a Python block executed in a sandbox; you are parsing a fenced code block, not JSON, and that is deliberate because one code block can express a loop over 50 records that would otherwise be 50 tool calls. **Three: when you need the format to be trivially greppable in logs across model vendors** — a normalization layer.

**⚠ Trap:** thinking text-ReAct is a downgrade because it lacks schemas. The failure profile is *different*, not worse. Native tool calling fails by producing well-formed JSON with wrong semantics (right shape, wrong customer ID). Text ReAct fails by producing malformed syntax, which your regex catches immediately and you feed back as a correctable observation. Loud syntactic failure beats silent semantic failure. What native tool calling genuinely buys is constrained decoding on argument types and parallel calls in one turn.

**🏋 Drill:** implement the above from memory in 15 minutes, no autocomplete, with two tools and a working `stop` sequence. Pass criterion: your agent answers a two-hop question ("who directed the film that won Best Picture the year X was born") in ≤4 steps and *terminates* when the tool returns nothing, rather than looping.

### Compare ReAct with Plan-and-Execute. Which is your default, and what makes you switch?

The distinction is about **when the model is allowed to change its mind.** ReAct decides one step at a time, conditioned on everything observed so far — maximally adaptive, maximally expensive, because every decision re-reads the whole trajectory. Plan-and-Execute commits to an ordered plan up front, then runs the steps with a cheap executor — maximally parallel and cheap, but it cannot react to a surprise in step 2 without an explicit replan.

You already have the analogue: ReAct is an interpreter, Plan-and-Execute is a compiler. The interpreter handles dynamic behaviour, pays per-instruction dispatch cost. The compiler produces a plan once, optimizes across steps (parallelism, dead-step elimination), and is wrong-footed by anything it could not see statically.

Mechanically the cost difference is the quadratic term. In ReAct, step *n*'s prompt contains all previous thoughts, actions and observations. For a 10-step run with ~800 tokens accumulated per step, total input tokens ≈ 800 × (1+2+…+10) = 800 × 55 = **44,000 input tokens**. Plan-and-Execute plans once (~1,500 tokens) then runs 10 executor calls each seeing only the plan plus its own step (~1,500 + 10 × 2,000 = **21,500**), and a final synthesis pass. That is a ~2× reduction on a small run and it grows: at 30 steps, ReAct's triangular sum is 800 × 465 = 372,000 tokens versus roughly 65,000. **💰** At $3/Mtok input, 372k vs 65k is $1.12 vs $0.20 per run — at 20k runs/day, **$22,400/day vs $4,000/day**, so roughly $550k/**month** of difference on one product surface.

**My default is ReAct-shaped**, and here is the honest reason: most product agents run 3–8 steps, where the quadratic term is small and adaptivity is where the quality lives. A support agent (Sierra-shaped) discovers in step 2 that the customer has two accounts; a plan written in step 0 had no way to know. Plan-and-Execute silently executes the wrong plan competently, which is worse than ReAct executing slowly.

**I switch to plan-first when three conditions hold together:** the sub-steps are largely independent (so you get real parallelism), the environment is low-surprise (a fixed corpus, a stable API, not a live web), and the step count is high enough that the quadratic term dominates. Deep-research-style fan-out is the canonical fit: plan 8 sub-questions, run all 8 in parallel, synthesize. That's a 3-round-trip wall clock instead of 8 sequential ones.

**🗣 Say this in the room:** "ReAct is an interpreter, plan-and-execute is a compiler. I default to ReAct because product agents are short and surprising, and I switch to plan-first when the steps are independent, the environment is stable, and the trajectory is long enough that re-reading the transcript dominates cost. Then I add explicit replan triggers so the compiler can bail back to the interpreter."

### Explain ReWOO. Where exactly do its token savings come from, and what does it give up?

**📄 Paper:** Xu et al. (2023) — *ReWOO: Decoupling Reasoning from Observations for Efficient Augmented Language Models*. Its contribution: generate the entire plan with **variable placeholders** for outputs you haven't seen yet, so the planner never needs the observations in its context at all. It replaced the assumption that the planner must see tool output to plan the next call.

The plan looks like this:

```
Plan: find the CEO of the company that acquired Figma's main competitor
#E1 = search["companies that acquired design tool startups 2024"]
#E2 = extract[#E1, "acquiring company name"]
#E3 = search["CEO of #E2"]
#E4 = extract[#E3, "CEO name"]
```

`#E2` is a *promise*. A dumb, deterministic worker resolves each node in dependency order, substituting realized values into later steps. Only at the end does a solver LLM see the plan plus the realized evidence and write the answer.

**Where the savings actually come from:** in ReAct, every observation enters the planner's context and is re-read on every subsequent step. In ReWOO the planner sees *zero* observations — one call, one plan. Suppose 6 steps, 2,500-token observations, 1,200-token system prompt. ReAct planner input ≈ Σ over steps of (1200 + accumulated) ≈ 1200×6 + 2500×(0+1+2+3+4+5) = 7,200 + 37,500 = **44,700 tokens**. ReWOO: one planner call at ~1,400 tokens, workers are non-LLM or tiny, solver sees 1,200 + 6×2,500 = **16,200 tokens**. Total ≈ 17,600. **💰 That is a 2.5× reduction**, and at $3/Mtok that's $0.134 → $0.053 per run; at 500k runs/month, $67,000/mo → $26,500/mo. The savings scale with observation size, which is why ReWOO shines for verbose tools (web pages, SQL result sets) and barely helps for tools that return a number.

**What it gives up is the entire point of the trade:** the plan is written blind. If `#E1` returns nothing, steps `#E2`–`#E4` execute on garbage and the solver confabulates. If the true answer requires a branch the planner couldn't anticipate ("if the customer is enterprise, check the contract table instead"), ReWOO has no branch. It is a straight-line program in a world with `if` statements.

**🔍 Failure taxonomy for blind plans**, as a decision procedure: (1) a step returns empty or errors → do you have a *replan* hook, or does the DAG keep executing? If no hook, this is your top bug. (2) A variable substitutes as literal text `#E2` because the extractor failed → assert on unresolved placeholders before dispatch; make it a hard error, never a silent string. (3) The solver produces a fluent answer citing evidence that is all empty strings → require the solver to emit `insufficient_evidence` and evaluate that it *can*. (4) The plan has a cycle or references a variable defined later → topologically sort and reject at plan-validation time, before spending a token on execution.

The design I ship in practice is a hybrid: ReWOO-style planning with a supervising loop that catches step failure and re-invokes the planner with the failure appended. You get the cheap common path and the adaptive slow path.

### What triggers a replan? Design the replanning policy — I don't want "when it seems wrong."

Replanning is exception handling for a program you didn't write. So design it exactly the way you'd design a retry/compensation policy in a Celery pipeline: enumerate the failure classes, decide per class whether it is *recoverable in place*, *recoverable by replan*, or *terminal*, and make the classification deterministic wherever you can.

My concrete trigger set, in the order I evaluate them each step:

**Deterministic triggers (no LLM call needed — these are just code):**
1. **Step hard-failed twice** after in-place retry with backoff. One failure is transient; two is a wrong plan.
2. **Unresolved dependency** — a placeholder never got a value, or a step's precondition is false (plan says "refund order #X", order lookup returned `not_found`).
3. **Budget projection breach** — you've consumed 60% of the token budget with 30% of the plan's steps completed; the plan is not going to fit. Replan under an explicit "you have N tokens left, cut scope" instruction.
4. **Repeated-identical-call detected** (same tool, same normalized args, ≥2×) — the agent is stuck; a replan is the escape.
5. **Step count exceeded the plan's own estimate by 1.5×.**

**Model-judged triggers (cost an LLM call, so gate them):**
6. **Observation contradicts a plan assumption** — a cheap classifier call: "does this observation invalidate any remaining step? yes/no + which step". I run this only after steps flagged `high_information` in the plan, not after every step, because running it every step doubles your call count for a signal that fires maybe 8% of the time.
7. **Goal drift** — the accumulated evidence answers a different question than the user asked. Rare; usually a symptom of a bad initial decomposition.

**The policy shape:** replan is *bounded* — I allow at most 2 replans per run, and each replan must strictly reduce remaining scope or the run terminates. Unbounded replanning is the single most common way a "plan-and-execute for cost savings" system becomes more expensive than the ReAct baseline it replaced. And a replan does not start from scratch: it receives the original goal, the completed steps with their realized evidence, and the specific failure — otherwise it will re-plan the work you already paid for.

**⚠ Trap:** letting the executor decide to replan. Give the *supervisor* that authority, and give the executor exactly two verbs: `succeeded(result)` and `failed(reason, retriable: bool)`. If the executor can rewrite the plan, you no longer have plan-and-execute; you have ReAct with extra latency and a misleading architecture diagram.

**🗣 Say this in the room:** "I make replanning deterministic wherever possible — two hard failures, an unresolvable dependency, a budget projection breach, or a repeated-call loop. I only spend a model call to judge 'did this observation invalidate the plan' after steps I've marked high-information. And replans are capped at two and must reduce scope, or the run terminates."

### Explain Reflexion. When is verbal self-critique real, and when is it theatre?

**📄 Paper:** Shinn et al. (2023) — *Reflexion: Language Agents with Verbal Reinforcement Learning*. The contribution: instead of updating weights from a reward signal, the agent writes a natural-language post-mortem of a failed attempt into an episodic memory buffer, and that text is prepended to the next attempt. "Verbal reinforcement" — gradient descent replaced by a note to self.

The mechanism has three parts and the third is the one people drop. An **actor** produces a trajectory. An **evaluator** produces a signal — and in the paper this is often an *external* signal: unit tests passing, an exact-match check, an environment reward. A **self-reflection** model turns (trajectory, signal) into a short lesson: "I assumed the config lived in `settings.py`; it is actually in `pyproject.toml`. Next time, list the directory first." That lesson goes in memory; the actor retries with it in context.

**When it is real:** when the evaluator is *grounded and cheap*. Coding agents are the archetype — run the test suite, get a hard pass/fail plus a stack trace, reflect on the trace, retry. That works, and it works because the reward is not the model's opinion. Any domain with a deterministic checker (SQL that either executes or errors, a JSON schema that validates or doesn't, a browser assertion that passes or doesn't, a simulator) gets genuine lift.

**When it is theatre:** when the model both generates and grades with no external signal. **📄 Paper:** Huang et al. (2023) — *Large Language Models Cannot Self-Correct Reasoning Yet* — found that intrinsic self-correction, with no external feedback, frequently *degrades* performance: the model changes correct answers to incorrect ones as often as the reverse. The intuition is that the same distribution that produced the error is being asked to detect it; if it could tell the answer was wrong, it would have produced the right one. Self-critique with no oracle mostly buys you longer, more confident-sounding output and a doubled bill.

**⚠ Trap — the "reflect and retry" loop that only adds cost.** I have reviewed several designs with a mandatory "critique your answer, then improve it" pass and no measurement of whether it helped. Ablate it. Run 200 tasks with and without; if the delta on your rubric is inside the noise band, delete the pass. The rule I enforce: **no self-critique step ships without an A/B showing lift on a held-out set.**

**💰 Math on the theatre:** a critique + revise pass roughly triples the generation cost of the final answer (original answer, critique reading the answer, revision reading both). For a 3,000-token-in / 700-token-out answer at $3/$15 per Mtok: base = 3000×3e-6 + 700×15e-6 = $0.009 + $0.0105 = **$0.0195**. Add critique (3,700 in, 300 out = $0.0156) and revision (4,000 in, 700 out = $0.0225) → **$0.0576**, a 2.95× multiple. At 300k requests/day: $5,850/day → $17,280/day, i.e. $11,430/day or **~$343k/month of extra spend** that you must be able to defend with an eval number.

**🗣 Say this in the room:** "Reflexion works when the evaluator is external and grounded — tests, a schema validator, a simulator. Self-critique with the model as its own judge and no oracle is mostly theatre; the literature shows intrinsic self-correction can make reasoning worse. So my rule is: no reflection step without a ground-truth signal feeding it, and no reflection step ships without an ablation."

### Decompose a task into a DAG and execute it. Show me the dependency handling and the parallelism.

The mental model: an agent plan is a build graph. You already know this shape — it's `make`, it's an Airflow DAG, it's a Celery chord. The only novelty is that the graph is written by a model at runtime, which means you must validate it like untrusted input before you execute a single node.

Plan format I use — steps with explicit `depends_on`, not implicit ordering, because implicit ordering hides the parallelism:

```python
import asyncio
from graphlib import TopologicalSorter   # stdlib since 3.9

async def run_dag(steps: dict[str, Step], max_parallel: int = 8):
    ts = TopologicalSorter({sid: set(s.depends_on) for sid, s in steps.items()})
    ts.prepare()                       # raises CycleError on a cyclic plan
    results, sem = {}, asyncio.Semaphore(max_parallel)

    async def run_one(sid):
        async with sem:
            args = substitute(steps[sid].args, results)   # resolve #E1 refs
            return sid, await steps[sid].fn(**args)

    while ts.is_active():
        ready = list(ts.get_ready())
        done = await asyncio.gather(*(run_one(s) for s in ready),
                                    return_exceptions=True)
        for item in done:
            if isinstance(item, BaseException):
                raise PlanStepFailed(item)   # supervisor decides: retry / replan / abort
            sid, out = item
            results[sid] = out
            ts.done(sid)
    return results
```

`graphlib.TopologicalSorter` is the right answer here and candidates rarely reach for it — it is stdlib, it raises `CycleError` in `prepare()`, and `get_ready()` gives you exactly the frontier you can run concurrently. You do not need a framework to get a correct parallel DAG executor; you need 20 lines and the standard library.

**Validation before execution — this is the graded part.** A model-authored plan is untrusted: (1) every `depends_on` must reference a defined step; (2) `prepare()` must not raise, so no cycles; (3) every placeholder in `args` must resolve to a declared upstream step (catch `#E7` when only `#E1`–`#E5` exist); (4) tool names must exist in your registry; (5) the plan's total step count must fit your budget. Reject and re-plan on violation — do not "fix it up" silently, because a silently repaired plan teaches you nothing about your planner's quality.

**Where the parallelism is worth it:** wall clock, not cost. Eight independent searches at 1.8s each are 14.4s sequential and ~2.0s in parallel — a ~7× latency win at essentially identical token spend (slightly higher in practice, since parallel branches can't share a growing prefix cache). That is the difference between a product surface that feels alive and one where users tab away. **⚠ Trap:** parallel *reads* are safe; parallel *writes* are not. Two concurrent steps that both call `create_ticket` will create two tickets, and no amount of "the plan said not to" will prevent it. My rule: side-effecting tools are marked in the registry and serialized through a single lane with idempotency keys, regardless of what the DAG says they may run concurrently.

**🔍 Failure taxonomy for DAG execution:** (a) *fan-out explosion* — a step returns 400 items and the plan says "for each, call tool X"; cap fan-out at plan-validation time and make the cap visible to the planner. (b) *partial failure* — 7 of 8 branches succeeded; decide up front whether the synthesizer runs on partial evidence (usually yes, with the gap declared) or the run fails. (c) *straggler* — one branch takes 90s and pins the whole level; per-step deadline with a `timed_out` result rather than an unbounded await. (d) *result bloat* — 8 branches × 6k tokens = 48k tokens into the synthesizer; summarize per branch before merge or you will blow the window at the last step, which is the most expensive place to fail.

### Someone tells you their agent is 95% accurate per step. It runs 20 steps. What do you tell them?

I tell them their task success rate is about 36%, and then I show the arithmetic, because this single number reframes the entire design conversation.

**📐 Numbers you must know:** if steps are independent and each succeeds with probability *p*, the trajectory succeeds with *p^n*. 0.95²⁰ = e^(20 × ln 0.95) = e^(20 × −0.05129) = e^(−1.0258) ≈ **0.358**. Memorize the family: 0.95¹⁰ ≈ 0.60, 0.95²⁰ ≈ 0.36, 0.95⁵⁰ ≈ 0.077. And the inverse, which is the one that wins arguments: to hit 90% end-to-end at 20 steps you need p = 0.90^(1/20) = e^(ln0.9/20) = e^(−0.00527) ≈ **0.9947** — 99.5% per step. Going from 95% to 99.5% per step is not a prompt tweak; that is a 10× reduction in per-step error rate.

Now the design consequence, which is the actual answer: **it is almost always cheaper to remove steps than to make steps better.** Same 95% per-step accuracy at 8 steps gives 0.95⁸ = 0.663 — you nearly doubled task success without touching the model. Halving the step count is engineering you control: merge two narrow tools into one that does the join server-side; return a richer result so the agent doesn't need a follow-up call; precompute the first two steps deterministically instead of letting the model discover them; replace a three-step "list, filter, fetch" dance with one parameterized query tool.

This is the single most transferable idea in agent engineering and it maps exactly onto something you already do: N+1 queries. An agent making 20 tool calls to assemble an answer is an N+1 query with a language model as the ORM. The fix is the same — make the tool return the joined thing.

**⚠ Trap — assuming independence.** Real errors are *correlated*, and the correlation cuts both ways. Bad news: one wrong early decision (misidentifying the customer) makes every downstream step wrong, so the true distribution is more bimodal than p^n suggests — many runs are perfect, and the failures fail totally. Good news: retries and self-repair recover a chunk of transient failures, so measured end-to-end rates often beat the naive p^n. Use p^n as the *design pressure* — it tells you where to spend — not as a prediction you'd put in a doc. If someone quotes p^n as a forecast, ask them how they measured per-step accuracy, because usually they didn't; they guessed.

**🗣 Say this in the room:** "0.95 to the twentieth is 0.36. To get 90% end to end over 20 steps you need 99.5% per step, which no prompt gets you. So I attack step count first — fold tools together, return richer results, and move deterministic prefixes out of the model's hands — and only then attack per-step accuracy."

**💰 The cost side of the same coin:** those 20 steps also cost you 20 sequential round trips. At 2.4s median per step (model latency + tool latency), that is 48s of wall clock; cutting to 8 steps is 19s. For a product where users abandon past 30s, the step-count reduction is simultaneously a quality fix, a cost fix (roughly the triangular-sum reduction: 20-step context accumulation vs 8-step is 210 vs 36 units, ~5.8× on input tokens), and a retention fix. Three wins from one change is why I lead with it.

### Explain Tree-of-Thoughts and Graph-of-Thoughts. What is the cost multiplier, and when have you actually seen it pay?

**📄 Paper:** Yao et al. (2023) — *Tree of Thoughts: Deliberate Problem Solving with Large Language Models*. Contribution: replace the single left-to-right chain of CoT with an explicit search tree — generate *k* candidate thoughts per node, score them with the model as a value function, and traverse with BFS or DFS including backtracking. It replaced the implicit assumption that one greedy chain is the only way to reason.

**📄 Paper:** Besta et al. (2024) — *Graph of Thoughts*. Contribution: generalize the tree to an arbitrary graph so thoughts can be *merged* (aggregating two partial solutions) and *refined* in loops, not just branched. That matters for tasks where combining partial results is the operation — sorting, set merging, document synthesis.

The mental model that makes both feel inevitable: **CoT is a greedy walk through solution space; ToT is beam search with an LLM as both the successor function and the heuristic.** You already know why beam search beats greedy on a search problem, and you already know why it costs more.

**The cost multiplier is the whole story.** With branching factor *b*, depth *d*, and one value call per generated node, you make roughly b^d generation calls plus b^d evaluation calls in the worst case; with beam width *w* and pruning, it's closer to w × b × d generations. Concretely: b=3, d=4, beam w=3 → about 3 × 3 × 4 = 36 generation calls plus 36 evaluations = **72 calls** versus 1 for a single CoT pass, i.e. a **~70× multiplier**, or ~15–25× with aggressive early pruning. **💰** If a single call is 2,000 in / 600 out = $0.006 + $0.009 = $0.015, then ToT at 72 calls ≈ **$1.08 per query**, plus depth×(generate+evaluate) sequential latency ≈ 4 × 2 × 2.5s = **20s** even with intra-level parallelism. That is a $1 and 20-second query. It is defensible for a legal research memo (Harvey-shaped: the alternative is a $400/hr associate) and indefensible for a chat turn.

**When it pays, in my experience:** tasks with (a) a verifiable or at least cheaply-scorable intermediate state, (b) genuine dead ends where backtracking recovers value, and (c) a user willing to wait. Constraint satisfaction, program synthesis with tests as the value function, multi-constraint scheduling. **When it does not pay:** anything where the value function is "ask the model which of these is better", because you've built a search whose heuristic is exactly as biased as the generator. That is the dominant failure — an expensive search that reliably finds the answer the greedy chain would have found.

**⚠ Trap:** proposing ToT in a product design interview as a quality lever. Nine times out of ten the interviewer is checking whether you know its cost. The senior answer is "I'd reach for best-of-n with a *deterministic* verifier before I'd reach for tree search, because n=5 with a real checker beats a 70× search with an LLM judge on both cost and reliability." Say that and you've differentiated yourself from every candidate who name-dropped ToT.

### LATS keeps coming up in papers. What is it, and would you put MCTS over agent trajectories in production?

**📄 Paper:** Zhou et al. (2024) — *Language Agent Tree Search* (LATS). Contribution: unify reasoning, acting and planning by running Monte Carlo Tree Search over *trajectories* — nodes are states of an agent interacting with an environment, expansion samples candidate actions, rollouts execute them, and the environment's feedback plus a model-based value estimate backpropagate to update node values. It generalizes ToT (which searches over thoughts) to searching over thought-action-observation sequences, and folds in Reflexion-style verbal feedback as part of the backup signal.

Mechanically it is textbook MCTS with LLM-shaped components: selection by a UCT-style rule balancing value and visit count, expansion by sampling *k* actions from the policy (the LLM), simulation by rolling the trajectory forward until terminal or depth cap, and backpropagation of the reward up the path. The novel and expensive bit is that a "rollout" is not a cheap simulator step — it is real tool calls against a real environment.

**Would I ship it? Almost never, and I can name the conditions under which I would.** MCTS needs three things: a cheap simulator, a reliable reward, and reversibility. Agent environments usually violate all three. Tool calls cost money and seconds, so rollouts are 10⁴–10⁶ times more expensive than a game simulator. Rewards are usually LLM-judged, which means you're backpropagating noise. And most interesting actions are irreversible — you cannot "explore" issuing a refund and then backtrack, because the money left.

**💰 Math on why:** a modest LATS config — 30 node expansions, each with 3 sampled actions and a depth-5 rollout — is on the order of 30 × 3 × 5 = 450 environment steps. At $0.015 model cost and 2s latency per step that's **$6.75 and 15 minutes** for one task, before tool costs. Compare best-of-4 full trajectories with a deterministic verifier: 4 × 12 steps = 48 steps, **$0.72 and ~2 minutes**. LATS must be ~10× better to justify the gap, and on most published comparisons it is single-digit percentage points better.

**Where it earns its keep:** offline. I have used tree search over trajectories as a *data generation* mechanism — search hard for successful trajectories on a training set, keep the winners, and use them to build few-shot exemplars, a distilled policy, or SFT data for a smaller model. Expensive search offline, cheap greedy policy online, is a pattern that shows up everywhere in this field and it is the answer I'd give.

**🗣 Say this in the room:** "LATS is MCTS where the simulator is your production environment. That breaks the three assumptions MCTS needs — cheap rollouts, reliable reward, reversibility. I'd use trajectory search offline to mine good trajectories and distill them, and online I'd use best-of-n with a deterministic verifier, which gets most of the benefit at a tenth of the cost."

### What does self-consistency look like at the trajectory level, and how is it different from majority voting on answers?

**📄 Paper:** Wang et al. (2022) — *Self-Consistency Improves Chain of Thought Reasoning in Language Models*. Contribution: sample *n* diverse reasoning chains at temperature > 0 and take the majority answer, replacing greedy single-chain decoding. The insight is that wrong reasoning paths disagree with each other while correct paths converge — errors are diffuse, truth is concentrated.

Lifting that to agents is not a trivial re-run, and the difference is where the interview lives. On a math problem the answer is a scalar you can bucket and count. On a trajectory, "the answer" is a sequence of actions with side effects, and three runs will produce three *differently-phrased* answers built from *differently-ordered* tool calls. So you need to define the equivalence class you're voting over, and there are three legitimate choices:

**Vote on the final answer**, after normalizing (extract a structured field — the refund amount, the chosen SKU, the boolean — and vote on that). This is the only clean one, and it requires your agent to emit a structured terminal result, which it should anyway.

**Vote on the action set.** Did all three runs decide to call `issue_refund(order=X, amount=Y)`? Agreement on the *decisive* action is a stronger signal than agreement on prose, and it's the right unit when the agent's output is an action rather than text. In practice: run n trajectories in a dry-run/sandbox mode, compare proposed side-effecting calls, and only commit the action if k-of-n agree.

**Vote via a judge over trajectories** — pick the best trajectory rather than the modal answer. This is best-of-n, not self-consistency, and it is strictly worse than a deterministic verifier when one exists.

**⚠ Trap:** running n trajectories that all actually execute side effects. Three parallel agents that each issue a refund refunded three times. If you are going to sample trajectories, either they run read-only until a commit phase, or they share an idempotency key namespace so the second and third calls are no-ops. This is the single question that separates a backend engineer from someone who read a paper — and it is exactly the instinct your Celery/Kafka background gives you.

**💰 Math:** self-consistency at n=5 is a flat 5× on cost and roughly 1× on latency if you fan out concurrently (plus a small aggregation call). For a 12-step agent at $0.18/run, n=5 is **$0.90/run**. You need to know what it buys: on my own harnesses, trajectory-level voting on the structured answer typically recovers a chunk of the *transient* failures (a flaky tool, an unlucky sample) and almost none of the *systematic* ones (a tool description that's wrong, a missing permission). So measure the failure split before you buy it. If 70% of your failures are systematic, n=5 costs 5× and fixes 30% of 30% ≈ 9% of runs. Fixing the tool description is free.

**🗣 Say this in the room:** "Self-consistency at the trajectory level means voting on a *structured* terminal result or on the decisive action set, not on prose. It's a 5× cost multiplier that only recovers stochastic failures, so I'd first measure what fraction of my failures are transient versus systematic — and I'd run the sampled trajectories read-only until a commit phase, or I'll refund the customer three times."
### Enumerate every way you stop an agent loop, and rank them by which one you'd remove last.

Termination is the hardest part of agent engineering and the part every take-home under-implements. The mental model: **an agent loop is an unbounded recursion whose base case is written in natural language by a stochastic process.** You would never ship a `while` loop whose exit condition is a model's opinion. So you don't — you wrap the model's opinion in a ring of deterministic guards, and the model's opinion is the *innermost* and least trustworthy of them.

Here is the full ring, ordered outermost (most trustworthy, removed last) to innermost:

1. **Wall-clock deadline.** A hard `asyncio.timeout` on the whole run. Protects the user's patience and your request-handling capacity. This is the last one I would ever remove, because it is the only guard that survives every other bug — including a tool that hangs, a provider that stalls mid-stream, and a bug in the other guards.
2. **Cost/token budget.** Cumulative input + output + cached tokens converted to dollars, checked after every model call. Protects the P&L. Note it must count *input* tokens, which are the ones that explode quadratically; a guard that counts only output tokens is a guard that fires after you've already spent the money.
3. **Max steps.** The simplest and the one everyone implements. Protects against the pathological loop, but note it is a poor cost proxy: 10 steps with 60k-token contexts costs more than 40 steps with 3k-token contexts.
4. **Repeated-identical-call detection.** Same tool, same normalized arguments, seen before → the agent is not making progress by definition, because the environment gave it the same answer.
5. **Oscillation / cycle detection.** A→B→A→B over states, where "state" is a hash of (tool sequence, arg fingerprints). Catches the two-step loop that the identical-call detector misses.
6. **No-progress heuristic.** Some domain-specific measure of forward motion hasn't improved in *k* steps — no new entities discovered, no new files touched, the candidate answer unchanged.
7. **Consecutive tool errors.** *m* errors in a row (I use 3) with no successful call between → the environment is broken or the agent misunderstands it; either way, more steps won't help.
8. **Model says it's done.** `stop_reason != "tool_use"`, or an explicit `finish(answer=...)` tool call. This is the *happy path* and the least reliable guard.
9. **Human interrupt / cancel.** Orthogonal to the rest, but it must exist and must actually cancel in-flight work rather than setting a flag nobody reads.

**⚠ Trap — the single-guard agent.** The take-home submission that has only `max_steps` looks complete and fails in production the first time a tool hangs (wall clock saves you), a context grows to 180k tokens (budget saves you), or the model finds a two-call loop that fits inside the step cap (oscillation detection saves you). If you implement exactly one thing beyond max-steps in a take-home, make it the wall-clock deadline; if you implement two, add the token budget.

**The other half of termination is what you do *at* the boundary,** and this is where most designs are worse than they think. A run that hits max_steps should not return `None`. It should force a final synthesis turn: strip the tools, tell the model "you are out of budget, produce your best answer from what you have and state explicitly what you could not determine," and return that with a `terminated_early` flag. A partial answer with declared gaps is worth far more to a user than a spinner that gives up, and it costs one extra call.

**🗣 Say this in the room:** "I put a ring of guards around the model's own stop decision — wall clock outermost, then dollar budget, then step cap, then loop detection, then no-progress, and the model's 'I'm done' innermost because it's the least trustworthy. And every guard exits through a forced summarization turn, so the user gets a partial answer with declared gaps instead of a timeout."

### Implement repeated-identical-call detection. What counts as "identical," and what do you do when you catch it?

The naive version is a set of `(tool_name, json.dumps(args))` and it catches maybe half of real loops, because agents rarely repeat *byte-identical* arguments — they repeat *semantically* identical ones. `search("Q3 revenue")` then `search("Q3 revenue ")` then `search("revenue for Q3")` is the same loop and a `set` of exact strings sees three distinct calls.

```python
import json, hashlib, re
from collections import Counter

def norm(v):
    if isinstance(v, str):
        return re.sub(r"\s+", " ", v.strip().lower())
    if isinstance(v, dict):
        return {k: norm(v[k]) for k in sorted(v)}
    if isinstance(v, list):
        return [norm(x) for x in v]
    return v

def fingerprint(tool: str, args: dict) -> str:
    return hashlib.sha1(
        json.dumps({"t": tool, "a": norm(args)}, sort_keys=True).encode()
    ).hexdigest()[:16]

class LoopGuard:
    def __init__(self, repeat_limit=2, cycle_window=6):
        self.seen = Counter(); self.history = []
        self.repeat_limit, self.cycle_window = repeat_limit, cycle_window

    def check(self, tool, args):
        fp = fingerprint(tool, args)
        self.seen[fp] += 1
        self.history.append(fp)
        if self.seen[fp] > self.repeat_limit:
            return "repeated_identical_call"
        h = self.history[-self.cycle_window:]
        for period in (2, 3):                       # A-B-A-B and A-B-C-A-B-C
            if len(h) >= 2 * period and h[-period:] == h[-2*period:-period]:
                return "oscillation"
        return None
```

Twenty lines, no dependencies, catches the two failure modes that burn budget. The normalization step — lowercase, collapse whitespace, sort dict keys, recurse into nested structures — is what makes it work on real traffic. If you want to go further, embed the argument string and treat cosine > 0.97 as identical, but I've found normalized-exact catches most of it and has no false positives, which matters because a false positive kills a legitimate run.

**What to do when it fires** — and this is the graded half, because "raise an error" is the wrong answer. Escalate in three stages:

**Stage 1 (first repeat):** return the *cached* result of the previous identical call, plus an injected note: `"[loop guard] You already called search with these arguments and received the result above. It has not changed. Try a different approach or a different tool."` This costs zero tool latency, zero tool cost, and gives the model the information it needs to break out. Roughly half of loops break here.

**Stage 2 (second repeat / oscillation detected):** suppress that tool for the next turn via `tool_choice` restriction or by dropping it from the tool list, and inject a stronger nudge naming the alternatives. Forcing a different action is more effective than asking for one.

**Stage 3:** terminate with `reason="loop_detected"` through the forced-summarization exit, and emit a metric. `agent_termination_reason` as a labelled counter is one of the highest-value dashboards you will build — a rising `loop_detected` rate after a prompt change is a regression signal that no accuracy eval will catch.

**⚠ Trap:** treating legitimate pagination as a loop. `list_items(cursor="abc")` → `list_items(cursor="def")` has different args so it's fine, but `read_file(path=X)` called twice because the agent genuinely forgot is *also* fine when the file changed between calls. My rule: exempt tools explicitly marked `idempotent_read` from stage-3 termination but still serve them from cache, and never exempt anything from the metric.

### Define "no progress" for an agent. I don't want a vibe — give me something I can compute.

Progress is domain-specific, and pretending otherwise is how you get a heuristic that fires on healthy runs. The general framework: **progress is monotone growth in the set of things the agent knows or has changed.** Pick a state set for your domain, hash it, and require it to grow.

Concretely, four computable definitions I have actually shipped:

**1. Novel-information ratio.** Maintain a set of content hashes over tool results. After each step, compute `new_hashes / total_hashes_this_step`. If the last *k*=3 steps each contributed < 10% novel content, the agent is re-reading things it already has. Cheap, tool-agnostic, works surprisingly well for research and retrieval agents.

**2. Domain state cardinality.** For a coding agent: the set of files opened and the set of files modified. For a support agent: the set of resolved slots in the task frame (customer identified? order identified? issue classified? remedy chosen?). For a browsing agent: the set of distinct URLs visited. Require at least one of these to increase every *k* steps. The slot-filling version is the strongest signal I know for conversational agents, because it maps directly onto the business task.

**3. Candidate-answer stability.** Ask the agent to maintain a `working_answer` field it updates each step (cheap — 50 tokens). If the working answer is unchanged for 3 consecutive steps *and* the agent keeps calling tools, it is polishing, not progressing. Terminate and ship the answer. This one converts an infinite-refinement failure into a normal completion.

**4. Distance-to-goal proxy**, where you have one. Tests passing / tests total for a coding agent. Rows matched for a data task. Constraints satisfied for a scheduling task. This is the best signal when it exists because it is external and deterministic — the same argument as with Reflexion evaluators.

```python
class ProgressMonitor:
    def __init__(self, patience=3):
        self.known: set[str] = set(); self.stale = 0; self.patience = patience
    def observe(self, artifacts: list[str]) -> bool:   # returns True if stalled
        before = len(self.known)
        self.known |= {hashlib.sha1(a.encode()).hexdigest() for a in artifacts}
        self.stale = 0 if len(self.known) > before else self.stale + 1
        return self.stale >= self.patience
```

**⚠ Trap — the patience parameter that's too impatient.** Real agents legitimately spend 2–3 steps orienting: list a directory, read a config, check permissions. None of those "make progress" on the user's goal, and a patience of 1 kills the run in its productive opening. I start at patience=3, tune it against a replay of production traces (which you have, because you logged trajectories), and I *never* let a progress heuristic terminate without also checking that at least one tool error or repeat occurred. Two weak signals agreeing beats one weak signal alone.

**💰 What it saves:** on a research agent I worked through the numbers on, roughly 8% of runs entered a no-progress tail that consumed 40% of that run's tokens for zero rubric-score improvement. Killing the tail at patience=3: 0.08 × 0.40 = **3.2% of total token spend recovered**, and the median latency of the affected runs dropped from ~4 minutes to ~2. Small on the bill, large on the p95 latency chart — and p95 is what users feel.

### Wall-clock, token, and step budgets — which one binds first in practice, and what does each actually protect?

They protect three different stakeholders and they bind in a predictable order, which is the useful part of the answer.

**Step budget protects your architecture.** It binds first on *pathological* runs — the agent that found a two-call loop. It is the crudest guard and the worst cost proxy, because token spend per step varies ~30× across a trajectory (step 1 sees 2k tokens, step 25 sees 60k). If step count is your only budget, you are pricing a triangular integral with a linear ruler.

**Token/dollar budget protects the P&L.** It binds first on *legitimately hard* runs — the agent is making real progress, but this task needed 40 tool results of 5k tokens each. This is the guard that actually correlates with money, and it is the one I check after every model call, using the `usage` object from the response rather than a client-side estimate, because a tokenizer estimate drifts and cached vs uncached input price differently.

**Wall-clock protects the user and your capacity.** It binds first on *stuck* runs — a hanging tool, a slow provider, a stalled stream. This is the only guard that fires when the agent isn't consuming resources at all, which is precisely why it must be outermost.

In my experience the distribution is roughly: on a healthy product agent, ~85% of runs terminate naturally, ~7% hit the step cap, ~5% hit the token budget, ~3% hit wall clock. If your step cap is firing on more than ~10% of runs, your cap is too low or your tools are too granular — go fix step count, don't raise the cap. If wall clock dominates, you have a tool latency problem, not an agent problem.

The implementation detail that gets missed: **budgets must be checked against a projection, not just a current value.** Checking "have I spent 200k tokens" after the call that spent them is closing the barn door. What I do is estimate the next call's input size (you know the message list length; you can count it) and refuse to start a step that cannot finish inside the remaining budget, routing instead to the forced-summarization exit. That converts "budget exceeded, run failed" into "budget nearly exhausted, here's the partial answer."

```python
def can_afford(state, next_input_est: int, max_out: int) -> bool:
    projected = state.cost_usd + (next_input_est * PRICE_IN + max_out * PRICE_OUT) / 1e6
    return projected <= state.budget_usd - RESERVE_FOR_SUMMARY_USD
```

`RESERVE_FOR_SUMMARY_USD` is the detail that separates a considered design from a naive one. You always hold back enough budget to produce the final answer.

**💰 Worked example of why the reserve matters:** budget $0.50/run. Summarization turn costs ~40k input + 800 output = 40,000 × 3/1e6 + 800 × 15/1e6 = $0.12 + $0.012 = **$0.132**. If you don't reserve it, a run that spends $0.49 on exploration has $0.01 left and cannot produce an answer — you paid $0.49 for nothing. Reserving $0.14 means the worst case is a slightly shorter exploration and a guaranteed deliverable. Across 100k runs/day at an 8% early-termination rate, that's 8,000 runs/day × $0.49 = **$3,920/day of spend converted from wasted to useful.**

### Tell the agent how much budget it has left. Does that actually change its behaviour, and how do you implement it?

Budget-aware planning works, but not the way people first implement it, and the difference is worth knowing because it's a good "have you actually tried this" question.

**What doesn't work:** putting "you have used 47,000 of 200,000 tokens" in the system prompt. Models are poor at absolute token arithmetic — they don't have a reliable sense of what 47,000 tokens buys — and a number in the system prompt is stale the moment the turn starts. You get either no behaviour change or premature capitulation.

**What works:** express the budget in *units the agent controls*, injected as a fresh system-role reminder near the end of the context, and pair it with an explicit policy. "You have approximately **4 tool calls** remaining before you must answer. Prioritize the single highest-value lookup and then produce your answer, stating what you could not verify." Steps and tool calls are the currency the model's policy is expressed in; dollars and tokens are not.

The three-band scheme I use:

```python
def budget_notice(state) -> str | None:
    frac = state.spent / state.budget
    left = state.est_steps_remaining
    if frac < 0.5:  return None                       # say nothing; noise costs tokens
    if frac < 0.8:  return (f"[budget] ~{left} tool calls remain. Prefer broad, "
                            f"high-yield calls over narrow follow-ups.")
    return (f"[budget] ~{left} tool call(s) remain. Make at most one more call, "
            f"then give your best answer and explicitly list what is unverified.")
```

Silence below 50% matters: an always-present budget line is ~30 tokens re-read every step, and worse, it primes the model toward hurrying on runs that have plenty of room. I want the pressure applied only when it's real.

**The measured effect,** in the shape you should describe rather than as a number I'd assert: what improves is not task success — it's the *distribution of terminations*. Budget-aware agents hit hard caps less often and produce declared-partial answers more often. That's the win. You are trading silent truncation for graceful degradation, and graceful degradation is a product feature.

**⚠ Trap — the agent that games its own budget.** Tell a model it's low on budget and it will sometimes claim completion without doing the work, because "produce an answer" is easier than "produce a correct answer." I've seen a support agent respond "I've processed your refund" under budget pressure without calling the refund tool. The mitigation is structural, not prompt-level: the terminal result is a *schema* with a `verified_by: [tool_call_ids]` field, and your code asserts that any claim of a side effect references a real tool call in the trajectory. Never let the model's prose be the record of what happened; the trajectory is the record.

**🗣 Say this in the room:** "I express remaining budget in tool calls, not tokens, because that's the unit the model's policy is in, and I only inject it past 50% consumption so it isn't priming every run to rush. And I validate any completion claim against the actual trajectory, because budget pressure makes models claim work they didn't do."

### How do you pick max_steps? Give me the reasoning for 8 versus 30 versus 200.

You do not pick it from intuition; you pick it from the empirical distribution of steps-to-completion on successful runs, and you set the cap in the tail. That is the whole method, and it requires you to have logged trajectories — which is why trajectory logging comes before tuning, always.

The procedure: take your successful runs, plot steps-to-completion, find p95 and p99. Set `max_steps = ceil(p99 × 1.3)`. The multiplier is headroom for legitimately hard tasks; the p99 anchor means you are not killing runs that would have succeeded. Then check the mirror statistic: **of runs that hit the cap, what fraction would have succeeded with 2× the cap?** Sample 50 of them, re-run with a doubled cap, and count. If more than ~15% would have succeeded, your cap is genuinely too low and costing you conversions. If under 5%, the cap is fine and those runs were lost anyway.

The three regimes, and what actually determines them:

**8 steps — conversational / transactional agents.** A support agent, a Notion-style "answer from my workspace" surface, a Ramp-style expense query. The task frame has 3–5 slots; a competent run fills them in 4–6 calls. p99 is around 7. Latency budget is the binding constraint: 8 steps × 2.5s = 20s worst case, already at the edge of what a chat user tolerates. If your support agent needs 20 steps, your tools are too granular — that's an N+1 problem, not a cap problem.

**30 steps — coding and multi-file agents.** A Cursor-shaped task touches 4–10 files, each needing read/edit/verify, plus test runs and a couple of recoveries from failure. p99 lands around 22–25. Wall clock here is minutes, and users accept it because the alternative is doing it themselves.

**200 steps — deep research and long-horizon autonomous runs.** The unit of work is a 10–30 minute job with its own progress UI. Here max_steps is not really the operative guard at all; the token budget and wall clock are, and max_steps exists purely as a backstop against a pathological tight loop that the token accounting somehow misses.

**⚠ Trap — one global max_steps for a multi-surface product.** If the same agent backend serves a 4-step "what's my balance" query and a 40-step "reconcile these invoices" job, a single cap is either too loose (you pay for the cheap path's pathologies) or too tight (you kill the expensive path). Budget per *task class*, classified at intake — either by a cheap router or by which endpoint was hit. And expose the class in your metrics, because "cap hit rate" aggregated across classes is a meaningless number.

**📐 Numbers you must know:** context accumulation over *n* steps is the triangular number n(n+1)/2, not *n*. Σ(1..20) = 210, Σ(1..40) = 820. So step-count changes hit input cost quadratically — memorize the ratio 820/210 ≈ 3.9 and you can price a cap change in your head.

**💰** Getting this wrong is expensive in a specific way: raising a cap from 20 to 40 does not double cost, it roughly *quadruples* the input-token cost of runs that use the extra room, because of the triangular accumulation — Σ(1..40)/Σ(1..20) = 820/210 = **3.9×**. So "let's just bump the cap" is a 4× decision on the affected slice, not a 2× one. I have watched that bump turn a $30k/month line item into $95k/month over a weekend.

### An agent ran overnight and burned $4,000 without finishing. Walk me through the postmortem.

I'd run this exactly like a runaway-consumer postmortem, because that's what it is: an unbounded consumer with an expensive per-message cost and no dead-letter path.

**First, containment** — before diagnosis. Kill switch: a global feature flag that fails every agent run closed, plus a per-tenant spend cap enforced in the gateway rather than in the agent process, because the agent process is the thing that's broken. If your spend cap lives inside the loop you're guarding, it doesn't exist. This is the same argument as putting rate limiting in the gateway rather than in the app.

**Then the trace.** With a proper trajectory log this is a five-minute query, and the shape of the answer falls out of one aggregation:

```sql
SELECT tool_name, count(*) AS calls,
       count(DISTINCT args_fingerprint) AS distinct_args,
       sum(input_tokens + output_tokens) AS tokens,
       sum(cost_usd) AS usd
FROM agent_steps WHERE run_id = :id GROUP BY 1 ORDER BY usd DESC;
```

`calls` vastly exceeding `distinct_args` is a loop. Tokens concentrated in a single step is a context blow-up (a tool returned a 400k-character payload). Cost spread evenly across 900 steps with growing input is the quadratic-accumulation failure — the agent was "working" the whole time and each step cost more than the last.

**The five causes, in the order I've actually seen them:**

1. **Missing wall-clock guard plus a retry storm.** A tool 500s, the agent retries, the retry counts as a fresh step, and step count never trips because each retry is a distinct tool call with distinct args (a timestamp in the args). Fix: normalize timestamps out of fingerprints, and cap *consecutive errors* separately from steps.
2. **Oscillation under the step cap.** Cap 200, agent looped A→B every two steps for 100 iterations. Step cap "worked" and cost $4k anyway. Fix: cycle detection, which is 20 lines.
3. **Context accumulation with no compaction.** By step 150 the context is 300k tokens and each step costs $0.90. Σ of a growing context is where the money went. Fix: budget in dollars, not steps; compact or summarize the transcript past a threshold.
4. **Fan-out without a cap.** Plan said "for each result, investigate" and the search returned 300 results. 300 sub-runs at $0.15 = $45 each level, two levels deep = catastrophe. Fix: hard fan-out cap enforced by the executor, not requested in the prompt.
5. **A retry wrapper around the whole run.** The classic backend reflex — `@retry(3)` on `run_agent()`. Now every catastrophic run costs 3×. I have seen this exact line in review more than once, and I flag it every time: **retry the tool call, never the trajectory**, unless the trajectory is provably free of side effects.

**📐 The arithmetic that makes it concrete:** $4,000 at $3/Mtok input is 1.33 billion input tokens. If the average step's context was 100k tokens, that's **13,300 steps.** No legitimate task takes 13,300 steps. The number itself tells you it was a loop before you read a single log line — and that's the kind of back-of-envelope you should do out loud in the interview.

**The permanent fixes I'd land**, in priority order: per-run hard dollar cap enforced at the gateway; per-tenant daily cap with alerting at 50/80/100%; wall-clock deadline; cycle detection; fan-out cap; a `cost_usd` field on every span so the dashboard exists next time; and an alert on `p99 cost per run` rather than total spend, because total spend hides a single run eating a day's budget.

### Critic and verifier loops — when do you use a second LLM, and when do you refuse?

The rule I enforce in review: **a deterministic verifier beats an LLM verifier every single time one exists, and you should spend engineering effort manufacturing one before you spend inference on judging.**

The reasoning is about error correlation. An LLM critic shares a distribution with the generator. When the generator is confidently wrong, the critic tends to be confidently agreeing — the errors are correlated, so the verification signal is weakest exactly where you need it most. A deterministic verifier has *uncorrelated* failure: a JSON schema validator does not care how plausible the output sounded, a SQL engine does not care that the query reads well, a test suite does not care that the code is idiomatic.

**Verifiers I reach for, ranked by strength:**

*Free and total:* schema validation (Pydantic model parses or it doesn't), type checking, `EXPLAIN`-ing generated SQL against the real catalog (catches hallucinated columns without executing anything), running the query against a read replica with a `LIMIT` and a statement timeout, compiling the code, running the tests, executing a linter, checking that every cited claim's quoted span actually appears in the source document (exact substring match — this one kills most citation hallucination for near-zero cost), checking that a computed total equals the sum of its parts.

*Cheap and partial:* regex/format checks, numeric range assertions, cross-referencing an ID against a database, checking a proposed action against a policy allowlist.

*Expensive and noisy:* an LLM judge with a rubric.

The design move that matters is **restructuring the output so that a deterministic verifier becomes possible.** If the agent answers in prose, you can only judge it with a model. If the agent answers with `{"answer": ..., "citations": [{"doc_id": ..., "quote": ...}]}`, you can verify every quote by substring match in 2ms. That is not a small improvement — it converts an unreliable $0.02 judge call into a reliable free assertion. I push for this in every design review, and it is the single highest-leverage thing most teams aren't doing.

**When I do use an LLM critic:** for genuinely subjective dimensions where no checker exists — tone, helpfulness, whether the answer addressed the question asked. And then with three disciplines: (a) the critic gets a *rubric with concrete anchors*, not "rate 1–5"; (b) the critic sees the output *without* knowing it was model-generated by the same model, and ideally is a different model family, to decorrelate; (c) the critic's agreement with human labels is itself measured on a held-out set — if your judge agrees with humans 70% of the time, your critic loop is adding 30% noise.

**⚠ Trap — the critic that always approves.** Run the null test: feed your critic 50 outputs you *know* are wrong. If it approves more than a handful, it is a rubber stamp and you are paying for a `return True`. I make this a required test in the eval suite for any judge we ship. The corollary trap is the critic that always finds something — a critic with no "this is fine" exemplar will invent nitpicks forever and drive an infinite refinement loop.

**💰** Cost comparison on a concrete case: verifying 5 citations by substring match is ~0ms of CPU and $0. Verifying them with an LLM judge is 5 × (2,000 in + 100 out) = 10,000 in + 500 out = $0.030 + $0.0075 = **$0.0375 per answer.** At 200k answers/day that's **$7,500/day, $225k/month**, to do worse than `quote in document`.

### When should the agent stop and ask the user instead of guessing? Design the elicitation policy.

The mental model: **asking is a tool call whose cost is measured in user patience rather than tokens**, and like any tool call it has an expected value. Ask when the expected cost of guessing wrong exceeds the cost of the interruption. That framing turns a vague UX question into an arithmetic one, and stating it that way is most of the answer.

The decision rule, made concrete:

**Always ask when the action is irreversible and the parameter is ambiguous.** Deleting, sending, paying, publishing, granting access. If two plausible referents exist for "cancel my subscription" and the user has two subscriptions, asking costs 20 seconds; guessing wrong costs a refund, a support ticket, and trust. This case needs no arithmetic — it's a policy.

**Never ask when the ambiguity is cheaply resolvable by a tool.** The failure I see most is an agent asking "which account do you mean?" when it has a `list_accounts` tool and the user has exactly one account. Rule: **the agent must exhaust its read tools before it is permitted to ask a clarifying question.** I enforce this by making the `ask_user` tool's description say so explicitly, and by testing it.

**Ask when the task is expensive and the specification is underdetermined.** A deep-research run that's about to spend $8 and 20 minutes should spend 15 seconds confirming scope. The expected-value math: if 30% of unclarified runs produce the wrong report and a run costs $8, the expected waste is $2.40 per run; one clarifying exchange costs ~$0.01 and ~20s of user time. Trivially worth it — which is why every serious deep-research product opens with a clarifying question.

**Batch your questions.** Three separate round trips asking one thing each is a dramatically worse experience than one message asking three things. Structure the elicitation tool to take a *list* of questions with types (choice, free text, confirm) so the UI can render a single form. This is also where MCP-style elicitation and structured UI returns matter — the question should render as a picker, not as prose the user has to answer in a sentence you then have to parse.

**Implementation shape:** `ask_user` is a real tool in the registry, and calling it *suspends* the run. This is the key architectural point and it's where your backend instincts pay off: the agent is now a durable workflow with a human-in-the-loop wait state. You persist the full state (messages, budget consumed, step index), return control, and resume from the checkpoint when the answer arrives — possibly hours later, possibly in a different process. If your agent can't survive a 4-hour gap between question and answer, you don't have elicitation, you have a blocking prompt inside a request handler.

**⚠ Trap — the over-asker.** An agent that asks about everything is worse than one that guesses, because it transfers the entire cognitive load back to the user, which is the thing they were paying you to avoid. The metric to watch is **questions per completed task**; I want it under 0.5 for transactional agents. Above 1.0, your agent is a form with extra latency. Tune by making the tool description explicit about the bar ("only ask when the answer cannot be obtained from any available tool AND a wrong guess would cause an irreversible or user-visible error") and by putting negative exemplars in the prompt.

**🗣 Say this in the room:** "Asking is a tool call priced in user patience. I gate it on three conditions — irreversible action, ambiguity not resolvable by any read tool, and a wrong guess that's expensive — and I batch questions into one structured turn. Architecturally it's a suspend/resume on a persisted checkpoint, not a blocking input, because the answer may come back four hours later in a different process."

### Deterministic scaffolding versus model-driven control. Which decisions do you take away from the model?

The principle: **give the model the decisions where its judgment is the value, and take away the decisions where its judgment is a liability.** Every decision you hand to the model costs tokens, adds latency, adds variance, and adds a failure mode. Every decision you hardcode removes flexibility. The senior skill is knowing which side of that line each decision sits on — and most teams put far too much on the model's side because it feels more "agentic."

**Take away from the model, always:**

- **Authorization.** Whether this user may call this tool with these arguments is a policy decision evaluated in code against the request's identity. Never in the prompt. A prompt that says "only call refund_order for the user's own orders" is a suggestion; a check in the tool wrapper is a control. This is the one I will fail a design on.
- **Rate limits, budgets, timeouts, retries.** All deterministic. The model should not be deciding whether to back off.
- **Idempotency.** The key is generated by your code from the semantic identity of the operation, not by the model. A model-generated idempotency key is a random string, which defeats the entire purpose.
- **Ordering constraints that are truly fixed.** If you must always authenticate before querying, do it in code before the loop starts — don't hope the model calls `login` first.
- **Data validation and coercion.** Parse and repair arguments before dispatch.
- **Fan-out limits and pagination.** Enforced by the executor.

**Leave to the model:**

- Which tool answers this question, and with what arguments.
- How to interpret an ambiguous user request.
- When enough evidence has been gathered.
- How to phrase the answer, and how to recover from an unexpected observation.

**The genuinely contested middle**, where I'd say the field has no consensus and you should say so: *routing between task types*. You can classify intent with a cheap deterministic router (fast, auditable, brittle at the edges, and every new case needs a deploy) or let one capable agent with all the tools figure it out (flexible, more expensive, harder to test). My decision rule: **if the task classes have materially different tool sets, permissions, or SLAs, route deterministically; if they differ only in phrasing, let one agent handle it all.** Different permissions is the strongest reason to split — it lets you enforce authorization at the router rather than reasoning about it per tool.

**⚠ Trap — the "prompt as policy" antipattern.** Writing constraints into the system prompt and calling that the control. Prompts are advisory under adversarial input and merely probabilistic under benign input. If a constraint appearing in your prompt would also appear in a security review, it belongs in code. I look for this specifically in take-home reviews, and it is the single most common way a technically-impressive agent submission gets marked down.

**🗣 Say this in the room:** "I take authorization, budgets, idempotency, retries, validation and fan-out caps away from the model entirely — those go in the tool wrapper, not the prompt. The model gets tool selection, interpretation, sufficiency, and phrasing. A constraint that would show up in a security review belongs in code, because a prompt is advisory."

### Your per-step accuracy is 92% and tasks average 15 steps. Product wants 90% task success. What do you actually do?

**📐 Numbers you must know:** the required-per-step-accuracy formula is p = T^(1/n), where T is target task success and n is step count. Memorize three points on it: at n=10 a 90% target needs p=0.9895; at n=15 it needs 0.9930; at n=20 it needs 0.9947. Every one of those is unreachable by prompting, which is why the formula is a *design* argument for cutting n rather than a target for tuning p.

Let me start with the arithmetic so we both know how far away we are. 0.92¹⁵ = e^(15 × ln 0.92) = e^(15 × −0.08338) = e^(−1.2507) ≈ **0.286**. Current task success ≈ 29%. The target of 90% at 15 steps needs per-step p = 0.90^(1/15) = e^(−0.10536/15) = e^(−0.007024) ≈ **0.9930**. So we need per-step error to fall from 8% to 0.7% — an **11× reduction** — or the step count to fall, or the independence assumption to break in our favour. Nobody gets 11× from prompt engineering. So the answer is a portfolio of four moves, and I'd rank them by leverage per engineering week.

**Move 1 — cut the step count (highest leverage).** If I can get 15 steps to 6 by folding tools, 0.92⁶ = 0.606. That's a 2.1× improvement in task success from pure tool design, no model change. Where the steps go is discoverable from your trajectory logs: aggregate `tool_name` sequences and look for repeated adjacent pairs. `search` → `fetch_doc` appearing 4× per run means those should be one tool that searches and returns content. `list_orders` → `get_order` means `list_orders` should return enough fields. This is the N+1 fix and it's usually worth a week.

**Move 2 — make failures recoverable rather than fatal.** p^n assumes a failed step kills the run. If a failed step returns a good error and the agent retries successfully 60% of the time, effective per-step success becomes 0.92 + 0.08 × 0.60 = **0.968**, and 0.968⁶ = 0.822. Combined with move 1 we are at 82% from two changes that touch no model. This is the highest-value under-appreciated move: *error message quality is a task-success lever.* "Invalid date" versus "Invalid date '03/04/25': expected ISO-8601 like 2025-03-04" is worth several points of end-to-end success.

**Move 3 — verify and repair the decisive steps only.** Not every step matters equally. Instrument which step's failure most often causes run failure (regress run outcome on per-step outcomes; it's a logistic regression over your trajectory table, or just a contingency table). Usually one or two steps dominate — entity resolution and the final action. Put a deterministic verifier on *those* and leave the rest alone. Verifying 2 of 6 steps costs a fraction of verifying all 15.

**Move 4 — the model and prompt.** A stronger model on the decisive steps only (tiered routing: cheap model for retrieval calls, strong model for the decision), better tool descriptions, few-shot exemplars drawn from your own successful trajectories. Real but incremental, and I put it last deliberately — because it's where everyone starts and it's not where the 3× lives.

**🗣 Say this in the room:** "0.92 to the fifteenth is 29%, and hitting 90% would need 99.3% per step, which is an 11× error reduction — not achievable by prompting. So I attack step count first, then recoverability, because 6 steps with recoverable errors gets me to roughly 82% without changing the model at all. Model upgrades are my fourth move, not my first."

**⚠ Trap:** promising the 90% at all. If the tooling can't get there, the honest senior move in the room is to say "here's what 15 steps at 92% costs you, here's what I can buy with two weeks, and here's the step count and per-step accuracy that would actually be required — let's agree on a target that the arithmetic supports, or scope the task down so it takes fewer steps." Interviewers at product companies specifically reward that pushback; it's the difference between an IC5 and an IC6 answer.
### Design the trajectory logging schema. What goes in a step record, and what will you regret leaving out?

The mental model: **a trajectory is a distributed trace where the spans happen to be model calls and tool calls.** Everything you already know about OpenTelemetry applies — one trace per run, nested spans, attributes on spans, and a sampling policy. What's new is that the *payloads* are the interesting part (unlike an HTTP trace, where the body is usually noise), and the payloads are large and often contain PII.

The record I ship, per step:

```python
@dataclass
class StepRecord:
    # identity / ordering
    run_id: str; step_index: int; parent_run_id: str | None   # sub-agents
    trace_id: str; span_id: str; parent_span_id: str | None
    ts_start: datetime; ts_end: datetime
    # what the model decided
    model: str; model_version: str            # exact snapshot id, not an alias
    prompt_hash: str; prompt_version: str     # which template built this call
    rationale: str | None                     # thought / reasoning summary
    tool_name: str | None
    tool_args: dict | None
    tool_args_fingerprint: str                # normalized hash, for loop detection
    # what happened
    tool_result_ref: str                      # pointer to blob store, NOT inline
    tool_result_bytes: int
    tool_status: Literal["ok","error","timeout","denied","cached"]
    error_class: str | None
    # economics
    input_tokens: int; output_tokens: int
    cached_input_tokens: int; reasoning_tokens: int | None
    cost_usd: Decimal
    model_latency_ms: int; tool_latency_ms: int
    # control state
    cumulative_cost_usd: Decimal; cumulative_tokens: int
    termination_reason: str | None            # set on the last step only
    # provenance
    tenant_id: str; user_id_hash: str; agent_version: str; env: str
```

**The fields people leave out and regret**, in the order the regret arrives:

**`cached_input_tokens` separately from `input_tokens`.** Without it your cost model is wrong by whatever your prefix-cache hit rate is, which on a well-designed agent is 70–90% of input. Reporting cost with cached and uncached tokens conflated overstates spend by ~3–5× and makes every optimization decision wrong.

**`tool_args_fingerprint`.** You need this at *write* time. Computing it later over a JSON column means a backfill over every historical row, and you'll want it the day you first see a loop.

**`prompt_version` and `agent_version`.** Without them you cannot answer "did the change I shipped Tuesday cause this," which is 60% of what you'll use this table for. Version the prompt template and the whole agent config, and stamp both.

**`tool_result_ref` rather than the result inline.** Tool results are the biggest payload in the system — a web page is 40k tokens, a SQL result set can be megabytes. Putting them in a Postgres column will make your table unqueryable inside a month. Write results to object storage keyed by content hash (which also gives you free dedup — the same page fetched by 400 runs stores once) and keep a pointer plus the byte count.

**`model_version` as the exact snapshot, not the alias.** "we use the fast tier" is not a debuggable fact when the alias silently rolls forward under you.

**Retention and PII.** Trajectories contain raw user input and raw tool output, which means customer data. My default: 30 days hot in Postgres for debugging, hashed/redacted derivative retained longer for analytics, raw blobs on a lifecycle rule. Field-level redaction happens at write time via a per-tool `sensitivity` declaration in the tool registry, not by a regex sweep afterwards.

**⚠ Trap — logging only the final answer.** Enormously common in take-homes, and it makes every interesting question unanswerable: which step failed, where the tokens went, whether the agent looped, whether the plan was good. The five-minute version of this schema is the difference between a submission that says "here's my agent" and one that says "here's my agent and here's how I'd know it regressed." That second one is what the rubric rewards.

**💰** Storage cost is not an excuse. 100k runs/day × 12 steps = 1.2M step rows/day. At ~600 bytes of structured fields per row that's **720 MB/day, ~22 GB/month** in Postgres — trivial. The blobs are the cost: 1.2M results × 8 KB average = **9.6 GB/day**, so ~288 GB retained over a month, which at $0.023/GB-month is about **$6.60/month**. You are spending tens of thousands of dollars a month on inference; **$7/month of blob storage** to be able to debug it is not a trade-off, it is a rounding error, and I'd push back hard on anyone framing it as one.

### I'm building the UI for a long-running agent. What events does the client actually need from the stream?

The mental model: **the client is rendering a state machine, not a text stream.** If your endpoint only streams answer tokens, every long-running agent looks identical from the outside — a spinner — and users abandon. What makes Deep Research, Cursor's agent mode and similar surfaces tolerable at 5+ minutes is that the user can see the machine thinking in terms *they* understand: what it's doing, why, and how far along.

The event set I ship, as a discriminated union over SSE:

```
run.started        {run_id, task, budget: {max_steps, max_usd, deadline_ts}}
plan.proposed      {steps: [{id, title, depends_on}]}          # if you plan
plan.updated       {reason, steps}                              # replans, visibly
step.started       {step_index, title, tool_name}
step.rationale     {step_index, text}                           # streamed, optional
tool.call          {step_index, tool_name, args_redacted}
tool.progress      {step_index, pct?, message}                  # long tools
tool.result        {step_index, status, summary, size_bytes, artifact_ref?}
artifact.created   {kind: "file"|"table"|"chart", ref, title}
token.delta        {text}                                       # final answer only
approval.required  {request_id, action, args, expires_ts}       # blocks
budget.update      {spent_usd, spent_pct, steps_used, eta_s}
run.finished       {status, termination_reason, cost_usd, duration_ms, steps}
error              {step_index?, class, message, retriable}
```

Four design decisions in there worth defending out loud:

**Stream a *summary* of tool results, not the raw payload.** A 40k-token web page down the SSE channel will lock up a browser tab and leak data the user shouldn't see. Send a one-line summary plus a byte count plus an artifact reference the client can fetch on demand.

**Redact args at the edge.** `tool.call` with `{"query": "...", "api_key": "..."}` in a client-visible stream is an incident. The redaction list lives in the tool registry alongside the schema.

**`budget.update` is a product feature, not telemetry.** An honest progress indicator — "step 6 of ~12, $0.40 of $2.00" — is the single thing that keeps users on a 4-minute run. Fake progress bars are worse than none; if you can't estimate, say "still working, 2m elapsed" and show the step count.

**Every event carries `step_index`,** so a client that reconnects can request `?since=step_index` and rebuild. Which requires the server-side event log to be durable and replayable — the same reasoning as a Kafka consumer offset. Long-running agent + browser tab = the connection *will* drop; design for resume, not for a perfect socket.

**⚠ Trap — streaming the model's raw reasoning tokens straight to the user.** Three problems: it exposes internal tool names and system-prompt structure, reasoning text sometimes contains speculative claims the model then discards (users screenshot those), and it makes the product feel chaotic. Stream a *rewritten* short status line per step ("Checking the invoice table for duplicates") — either a separate cheap model call, or better, a `title` field the agent emits as part of its structured step output for free. **📅 Volatile:** provider policies on whether raw reasoning content may be displayed or must be retained/redacted differ and change; check current terms before shipping raw thinking to users.

**🗣 Say this in the room:** "The client is rendering a state machine, so I stream typed events — plan proposed, step started, tool called, tool result summarized, budget update, approval required, finished — not just answer tokens. Every event carries a step index so a reconnecting client can resume from an offset, and tool results go as summaries plus an artifact reference, never as raw payload."

### An agent crashed at step 14 of a 20-step run that had already cost $6. How do you make that resumable?

You make the loop a durable workflow, and the thing that makes it durable is that **all state lives in one serializable object that you persist after every step, before any side effect.** Your instinct here is exactly right and transfers directly: this is checkpoint-and-restart, it is a Celery task with an idempotent body, it is a saga with compensations.

```python
@dataclass
class RunState:
    run_id: str
    task: str
    messages: list[dict]              # the whole transcript
    step_index: int
    spent_usd: Decimal
    tool_results: dict[str, str]      # tool_use_id -> result blob ref
    pending_tool_calls: list[dict]    # emitted but not yet executed
    completed_effects: dict[str, str] # idempotency_key -> effect result
    status: Literal["running","waiting_human","done","failed"]
```

The loop becomes: load state → if `pending_tool_calls` is non-empty, execute *those* first (this is crash recovery) → call model → persist → execute tools → persist → repeat. The persist points are chosen so that a crash at any instruction leaves you in a state you can reason about.

**The hard part is not the transcript — it's the side effects.** A crash between "issued the refund" and "wrote the checkpoint" means resume will re-issue the refund. Three mechanisms, and you need all three:

1. **Idempotency keys derived deterministically** from `(run_id, step_index, tool_name, args_fingerprint)` — not random, not model-generated. On resume the same key is regenerated, so the downstream service dedups. This is why the key must be a pure function of state you've persisted.
2. **An effects ledger** written in the *same transaction* as the state checkpoint where possible, or, where the effect is in a remote system, a write-ahead intent record: write `intent(key, tool, args)` → call → write `outcome(key, result)`. On resume, any intent without an outcome gets re-attempted with the same key.
3. **Reconciliation for effects that can't be made idempotent.** Some third-party APIs have no idempotency support. For those, before re-attempting, *query* — `list_refunds(order_id, since=intent_ts)` — and if the effect exists, adopt it. This is more work and I only build it for the handful of tools that need it, which is why the registry marks each tool `idempotent | keyed | requires_reconciliation`.

**What resume must NOT do:** re-run the model calls from step 0. That's $6 you already spent. The persisted `messages` list *is* the resumed context — replay from state, not from the beginning. If you find yourself replaying model calls to rebuild context, your state object is incomplete.

**⚠ Trap — persisting the state but not the model's *pending* tool calls.** The classic sequence: model emits three tool calls, you execute two, the process dies. If your checkpoint only stores completed steps, resume re-asks the model, which now emits a *different* set of calls (it's stochastic), and the two effects you already executed are orphaned — invisible to the new trajectory, already charged to the customer. Persist the assistant turn containing the tool calls *before* executing any of them. That single ordering rule is the difference between a resumable agent and a duplicate-charge incident.

**💰** The economics of resumability: at $6/run and a 1.5% crash-or-deploy-interruption rate over a 20-minute run, on 5,000 runs/day you lose 75 runs × $6 = **$450/day = $13,500/month** without resume, and roughly a tenth of that with it (you lose only the in-flight step). More importantly, you can now deploy during business hours — a run that survives a rolling restart removes the operational constraint that "we can't deploy while research jobs are running," and that constraint costs more in engineering velocity than the $13.5k.

### When do you build a workflow engine and when do you build an agent? Give me a rule I can apply.

**The rule: if you can draw the graph before the request arrives, it is a workflow. If the graph depends on what you find, it is an agent.** Everything else is elaboration on that sentence.

Elaborated into a decision procedure I actually use:

**Build a workflow (deterministic control flow, LLM as a node) when:** the steps are known in advance; the branching is on *data* rather than on judgment; you need auditability of the control path; failure handling must be per-step and explicit; latency must be predictable; and the same input should mostly produce the same execution path. Document processing pipelines, classification-then-route, extract-validate-enrich-store, most of what enterprises actually deploy. **This is the majority of production "AI features" and it is the answer interviewers under-hear.** Candidates over-reach for agents because agents sound harder.

**Build an agent (model-driven control flow) when:** the number of steps depends on the input; the tool sequence is genuinely unpredictable; the task requires reacting to intermediate results in ways you can't enumerate; and the value of adaptivity exceeds the cost of variance. Debugging, research, open-ended support, coding.

**The honest middle, which is where most good systems live:** a deterministic skeleton with agentic pockets. Fixed pipeline `intake → classify → [agent loop scoped to one sub-problem] → validate → commit`, where the agent has 5 tools and 8 steps of freedom inside a box whose entry and exit conditions are code. You get bounded variance, an auditable outer path, and the adaptivity where it pays. I would design almost every enterprise agent this way and I'd say so unprompted.

**The cost and reliability arithmetic that makes the choice for you:** a 6-node workflow makes 2 model calls (say, classify and generate) at ~$0.01 total and 3s, with a success rate that's basically the product of two model steps, ~0.97² ≈ 94%. The equivalent agent makes 8 model calls at ~$0.12 and 18s, with 0.95⁸ ≈ 66% before recovery. If the workflow *can* express the task, the agent is 12× the cost, 6× the latency and worse. The only reason to pay that is that the workflow can't express the task — so the burden of proof is on the agent.

**⚠ Trap — "we'll build it agentic so it's future-proof."** This is the most expensive sentence in applied AI. It buys flexibility you don't need at a cost you do pay, and it makes the system unevaluable because there's no fixed control path to assert on. The reverse migration is easy and the forward one is hard: start with a workflow, log the cases where the fixed path was wrong, and promote a node to an agent loop when you have evidence. I have never regretted starting deterministic; I have repeatedly regretted starting agentic.

**🗣 Say this in the room:** "If I can draw the graph before the request arrives, it's a workflow — and most enterprise AI features are workflows that got called agents. I default to a deterministic skeleton with a bounded agent loop inside one node, because that gives me an auditable control path plus adaptivity exactly where it's paid for."

### The take-home is "build a workflow engine with graph nodes and cycle protection." Walk me through your design.

This assignment shows up constantly and the graded axes are not what candidates assume. They assume it's about the graph algorithm. It's about **state, determinism, and observability** — the graph is the easy part.

**Core model.** A `Workflow` is nodes plus edges. A node is a pure-ish function `(State) -> StateDelta`. Edges are either static or conditional — a predicate over state returning the next node name. State is a single serializable object updated by *reducers* rather than by mutation, so that concurrent branches can merge deterministically (two parallel nodes both appending to `state.findings` need an append-reducer, not `=`).

```python
Node = Callable[[State], dict]          # returns a partial state update
class Engine:
    def __init__(self, nodes, edges, reducers, max_visits=25, max_steps=200):
        self.nodes, self.edges, self.reducers = nodes, edges, reducers
        self.max_visits, self.max_steps = max_visits, max_steps

    def run(self, state, start="START", checkpointer=None):
        cur, visits, steps = start, Counter(), 0
        while cur != "END":
            steps += 1
            if steps > self.max_steps:            raise StepBudgetExceeded(cur)
            visits[cur] += 1
            if visits[cur] > self.max_visits:     raise NodeVisitLimit(cur, visits[cur])
            delta = self.nodes[cur](state)
            state = self.apply(state, delta)      # reducer-based merge
            if checkpointer: checkpointer.put(state.run_id, steps, cur, state)
            cur = self.route(cur, state)
        return state
```

**Cycle protection — and here is the point candidates miss.** Cycles are not a bug to be forbidden; they are the feature that distinguishes a workflow engine from a DAG runner. "Generate → validate → if invalid, regenerate" is a cycle, and it's the whole reason you need loops. So there are *two* different requirements and you must name both:

1. **Static validation:** reject a graph with an unreachable node, a node with no outgoing edge that isn't END, an edge to an undefined node, or a conditional router that can return a name not in the graph. Do this at compile time. A cycle is *not* a static error.
2. **Runtime bounding:** per-node visit caps, a global step cap, wall-clock, and — the sophisticated version — **state-fingerprint repetition detection**: hash the subset of state the router reads; if you re-enter node N with an identical fingerprint, you are provably in an infinite loop because the same state produces the same routing decision. That's a real cycle proof, not a heuristic, and saying it will separate you from the field.

**The other graded axes:** *checkpointing* (persist after every node so a crash resumes, and so you can replay); *determinism* (a `resume_from(run_id, step)` that reproduces the run given the same node outputs — which requires caching node outputs by `(node, state_hash)`); *parallelism* (a node that fans out to a set of successors, joined by reducers, with a barrier); *interrupts* (a node can raise `Interrupt(payload)` which suspends and persists, and `resume(value)` re-enters); *typed errors per node* with a retry policy declared on the node, not scattered in the body; and *observability* (a span per node with duration, tokens, cost).

**What I'd write in the README to win the defense round:** the graph as a diagram; the state schema and each reducer with a one-line justification; the four termination guards with the reasoning for each limit's value; a worked example of a cycle that terminates and one that trips the guard; a replay/time-travel demo; and a table of what I deliberately did not build (distributed execution, durable timers, versioned graph migration) with the reason. Naming your non-goals is a seniority signal and take-home rubrics reward it explicitly.

**⚠ Trap:** implementing cycle *prevention* by rejecting cyclic graphs at compile time. It passes a naive test, and it makes the engine unable to express retry, refine, or any agent loop — the very things a workflow engine exists to run. If you do this the reviewer concludes you didn't understand the assignment.

### How do you measure whether the plan was good, separately from whether the outcome was good?

Because otherwise you cannot learn anything from a failure. If your only metric is task success, then a run that had a perfect plan and hit a flaky API scores identically to a run whose plan was nonsense and got lucky. Conflating them means every regression investigation starts from zero. This is the same reason you separate "did the query plan use the index" from "did the query return the right rows."

**Plan quality metrics, computed against a reference:**

- **Step-set F1.** Given a human- or expert-written reference plan for a task, compare the set of *step types* (not exact strings — normalize to a tool/intent vocabulary). Precision penalizes unnecessary steps, recall penalizes missing ones. This is the workhorse.
- **Ordering correctness.** Of the dependency pairs in the reference (A must precede B), what fraction does the plan respect? Kendall tau over the topological order, or just the fraction of satisfied precedence constraints, which is more interpretable.
- **Necessary-step recall.** A subset of steps marked *essential* in the reference (you cannot resolve this ticket without verifying identity). Missing one of these is a categorically worse error than adding a redundant search, and an F1 that treats them equally is hiding your worst failures.
- **Redundancy rate.** Steps whose removal wouldn't change the outcome, as judged by an ablation or by a rubric. This is your direct cost lever.
- **Plan feasibility.** Does every step reference a tool that exists, with arguments the schema accepts? Deterministic, free, and a shockingly frequent failure on smaller models.

**Outcome metrics, kept separate:** task success against a checker, answer correctness, side-effect correctness (did exactly the right mutations happen — this one is under-measured and it's the one that matters for transactional agents), cost, latency, termination reason distribution.

**The 2×2 is the actual deliverable**, and I'd draw it on the whiteboard:

- *Good plan, good outcome* — your baseline; sample a few to confirm they're not lucky.
- *Good plan, bad outcome* — **execution problem.** Flaky tools, bad error messages, argument formatting, permissions. Fix the tools, not the prompt. This quadrant should drive your reliability work.
- *Bad plan, good outcome* — **got lucky, or your task is too easy to discriminate.** If this quadrant is large, your eval set doesn't distinguish planners and you should make it harder.
- *Bad plan, bad outcome* — **planning problem.** Prompt, exemplars, decomposition strategy, model tier.

Where the mass sits tells you where to spend the next sprint, and I have seen teams spend a quarter on prompt engineering when 80% of their failures were in the "good plan, bad outcome" cell — i.e., their tools were broken and no prompt would fix it.

**⚠ Trap — using an LLM to grade the plan against the reference with a vague rubric.** Step-set F1 with a normalized vocabulary is computable and stable; "rate this plan 1–5" is noise you'll chase for a month. Where you must use a judge, give it the reference plan and ask for *set differences* (which reference steps are missing, which plan steps are extra) rather than a score — that's a task a model does reliably, and you compute the metric yourself from its output.

**🏋 Drill:** take 20 trajectories from a running agent, hand-write reference plans for them (30 min), and compute step-set F1 and necessary-step recall. Pass criterion: you can state, in one sentence with numbers, which quadrant of the 2×2 your agent's failures live in.

### How do you evaluate an agent loop end to end? What does the harness look like?

The framing I lead with: **an agent eval is an integration test suite with a stochastic system under test, so everything you know about flaky integration tests applies — and the answer to flakiness is not retries, it's n-sampling with a reported variance.**

Four layers, and a real harness has all four:

**Layer 1 — trajectory replay (unit-test speed, zero model cost).** Record real trajectories, then replay them against your *dispatcher* with the model calls stubbed from the recording. This tests your loop: termination guards, argument validation, error handling, budget accounting, resume logic. It runs in CI in seconds, catches most of the bugs you'll actually ship, and costs nothing. Almost nobody builds this and it is the highest-ROI thing in the list.

**Layer 2 — tool-level unit evals.** For each tool, a set of (natural-language intent → expected call). Measures tool-selection precision and argument F1. Cheap, catches description regressions immediately, and localizes blame to a single tool.

**Layer 3 — task-level end-to-end with a simulated environment.** This is the τ-bench-shaped design and it's the one to describe by name. **📄 Paper:** Yao et al. (2024) — *τ-bench* — evaluates agents against a *simulated user* plus a database with domain policies, and scores on the final database state rather than on conversation text. Two contributions worth quoting: scoring on **state, not transcript**, and reporting **pass^k** (the probability that all k independent attempts succeed) rather than pass@k, which exposes how unreliable agents are under repetition. That reframing — measuring consistency instead of best-of-k — is exactly the right instinct for production, and citing it signals you read past the abstract.

Build your own version: a seeded database snapshot, a scripted or model-driven user simulator, a policy document, and an assertion over final DB state plus the set of side effects. Assert on *both* what should have happened and what should not — the "did it also cancel the wrong order" check is where agents fail and transcript-based evals are blind.

**Layer 4 — production shadow and online metrics.** Termination-reason distribution, cost per resolved task, step-count distribution, tool error rates by class, human-escalation rate, and a sampled human review of ~1% of trajectories with a rubric. Cost per *resolved* task is the metric I'd put on the exec dashboard; cost per request is misleading because a cheap run that fails is not cheap.

**Statistics you must state, not skip:** run each task n≥5 times at your production temperature and report mean and the pass^n number. A 100-task suite run once has a standard error around ±5 points — which means the 3-point "improvement" from your prompt change is noise. I ask candidates for their confidence interval and it is a reliable seniority filter.

**💰** Cost of the suite: 100 tasks × 5 runs × 12 steps × ~$0.015/step = **$90 per full evaluation run.** That's cheap enough to run per-PR on a 30-task smoke subset (~$27) and nightly on the full suite. Budget it explicitly — a team that can't afford to run its eval will stop running it, and then it doesn't have one.

### Your Celery instincts about retries and idempotency — where do they transfer to agents, and where do they mislead you?

**Transfers cleanly:** idempotency keys on side-effecting operations; the distinction between retriable and non-retriable errors; exponential backoff with jitter; a dead-letter path for poison inputs; at-least-once delivery meaning your handlers must tolerate duplicates; circuit breakers around flaky dependencies; bulkheads so one bad tenant doesn't starve the pool. All of it applies unchanged to tool execution, and reaching for it fluently is a genuine advantage you have over candidates who came from ML.

**Where it actively misleads you** — four specific places, and these are worth memorizing because they're the section of the interview where a backend background becomes a liability if unexamined:

**1. Retrying the whole trajectory is not like retrying a task.** A Celery task retry re-runs a deterministic function. An agent retry re-runs a *stochastic* function that may take a different path, call different tools, and produce different side effects. `@retry(3)` on `run_agent()` triples your worst-case cost and can triple your side effects. The correct granularity is the tool call, or — if you must retry the run — from a checkpoint with the effects ledger intact.

**2. Idempotency is harder because the model generates the arguments.** In a normal system, "the same request" is byte-identical. Here, a retried trajectory might call `send_email(subject="Your refund")` the first time and `send_email(subject="Refund confirmation")` the second. Byte-level idempotency keys won't dedup those. The key must be derived from *semantic* identity — `(run_id, effect_type, business_entity_id)` — computed by your code from the task, not from the model's arguments. That's a genuinely different discipline and it's the thing I probe for.

**3. "Timeouts protect you" becomes "timeouts kill healthy work."** A 30-second timeout is generous for an HTTP call and murderous for a reasoning-heavy generation or a tool that scrapes ten pages. And a streaming response that's producing tokens slowly is *healthy*, not hung. Time out on **inter-token gap** (no token for 20s) rather than on total duration, plus a much larger absolute ceiling.

**4. Exactly-once framing.** You know exactly-once delivery doesn't exist and you build for at-least-once with idempotent handlers. Same here — but the additional wrinkle is that the *decision* to perform the effect is non-deterministic, so "the operation is idempotent" doesn't save you from "the agent decided to do it twice for two different reasons." The guard is a per-run effects ledger consulted before dispatch: `if effect_type X already executed in this run, return the prior result instead of executing`. That's a policy no message broker gives you.

**⚠ Trap — the retry that amplifies cost 4×.** Retry-on-any-exception around the model call, where the exception is a context-length error. Every retry sends the same over-long context, fails identically, and bills you for the input tokens each time (many providers charge for a request that fails validation only sometimes — but rate-limit and overload retries definitely re-send). Classify before you retry: `429` and `overloaded` retry with backoff; `context_length_exceeded` and `invalid_request` must *never* retry — they need a different action (compact the context) or a hard fail.

**🗣 Say this in the room:** "Retry the tool call, never the trajectory. Idempotency keys have to be derived from semantic identity by my code, because the model won't produce byte-identical arguments on a retry. And I time out on inter-token gap rather than wall duration, because a slow stream is healthy and a 30-second ceiling would kill it."

### Build me the per-request cost model for an agent. Show the arithmetic.

The mental model: **agent cost is dominated by the quadratic re-reading of context, not by generation.** Once you internalize that, every optimization you'd reach for reorders itself.

**📐 Numbers you must know:** the agent cost formula. Let *n* = steps, *s* = system prompt + tool schemas (constant, re-sent every call), *g* = tokens added per step (thought + tool call + tool result), *o* = output tokens per step. Then input tokens at step *i* ≈ s + (i−1)·g, so **total input = n·s + g·n(n−1)/2** and **total output = n·o**. The g·n(n−1)/2 term is the one that surprises people, and it's the one you should write on the whiteboard before quoting any number.

**Worked example — a support agent.** s = 3,000 (system prompt 1,200 + 10 tool schemas at ~180 tokens each), g = 900, o = 250, n = 8.

- Input = 8 × 3,000 + 900 × (8×7/2) = 24,000 + 900 × 28 = 24,000 + 25,200 = **49,200 tokens**
- Output = 8 × 250 = **2,000 tokens**
- At $3/Mtok in, $15/Mtok out: 49,200 × 3e-6 = $0.1476; 2,000 × 15e-6 = $0.030. **Total $0.178/run.**

Note the split: **83% of the cost is input.** Every instinct that says "shorten the answer" is optimizing 17% of the bill.

**Now apply prefix caching.** The system prompt plus tool schemas (3,000 tokens) and the accumulated prefix of the transcript are identical across steps within a run — that's exactly what a prefix cache is for. If cached input is billed at 10% of the base rate, and roughly the first (i−1) segments of each call hit cache, cached tokens ≈ 49,200 − 8×900 (the new segment each step) − small = ~42,000 cached, 7,200 uncached.

- 42,000 × 0.3e-6 = $0.0126; 7,200 × 3e-6 = $0.0216; output $0.030. **Total $0.064/run — a 2.8× reduction.**

**💰 At scale:** 300,000 runs/day. Without caching: 300,000 × $0.178 = **$53,400/day = $1.60M/month.** With caching: 300,000 × $0.064 = **$19,200/day = $576k/month.** That is a **$1.02M/month** difference from correctly ordering your prompt so the stable prefix comes first and setting cache breakpoints. **📅 Volatile:** the $3/$15 per-Mtok figures used throughout this section are illustrative placeholders, and cache write premiums, cache read discounts and TTLs differ per provider and change; verify current rates and multipliers before quoting them.

**The three levers, ranked by the model above:**
1. **Reduce n.** The n(n−1)/2 term means going 8 → 5 steps cuts the accumulation term from 28g to 10g — a 64% cut on the dominant component.
2. **Cache the prefix.** 2.8× on this workload, effectively free engineering.
3. **Reduce g** — truncate tool results. Dropping g from 900 to 500 cuts the accumulation term by 44%. This is where result truncation, summarization and pointer-to-file patterns pay.

Reducing *o* is fourth and it's what people do first.

**⚠ Trap — quoting a "cost per 1k tokens" for an agent as if it were linear.** Someone will estimate "8 steps × 4k tokens × $3/Mtok = $0.096" and be off by ~2×, because they modelled a constant context instead of a growing one. Then they'll be off by another 3× in the other direction because they ignored caching. Two errors that partly cancel is not a model; it's a coincidence. Write the triangular sum.

### Design human-in-the-loop approval for an agent that takes real actions.

Approval is a suspend/resume on a durable workflow with an authorization decision in the middle. Three things must be true and each is a place designs fail.

**One: the approval must be enforced at the tool boundary, in code.** The tool wrapper checks a policy — `requires_approval(tool, args, actor, context)` — and if true, raises a typed `ApprovalRequired` that the loop catches, persists, and surfaces. Not a prompt instruction, not a "confirm with the user first" line in the system message. If the agent can perform the action without your code granting it, you have advice, not a control.

**Two: the approver must see what will actually happen, not the model's description of it.** Render the *resolved tool call* — tool name, fully-resolved arguments, the affected entity fetched fresh from the source of truth, and the reversibility class. "Refund order #40219 — $1,240.00 to card ••4417, customer Acme Corp, non-reversible" is an approvable statement. "The agent would like to process a refund" is not, and I would reject that UI in review. The gap between them is where confused-deputy incidents live: a model that describes a benign action and requests a different one.

**Three: the approval must be bound to the exact call.** Sign or hash the resolved arguments and store them with the approval request. On resume, re-derive the hash and refuse if it changed. Otherwise you have a TOCTOU window in which a re-planned agent executes a *different* action against an approval the human gave for something else. This is exactly a CSRF-token argument and it should feel familiar.

**The policy tiers I ship:**

- **Auto** — read-only, reversible, or below a value threshold. Approve implicitly, log everything.
- **Notify-after** — reversible and low value, but visible. Execute and send a notification with a one-click undo. Undo must actually exist.
- **Approve-before** — irreversible, above threshold, or touching a protected entity class. Suspend.
- **Blocked** — never available to the agent, regardless of who asks. Some actions just aren't in the tool registry for this actor.

Thresholds come from expected-cost arithmetic, not from taste. If the agent's action accuracy on refunds is 97%, and the average refund is $200, the expected error cost is 0.03 × $200 = **$6/action**. A human review costs ~90 seconds of an agent's time, ~$1.50 fully loaded. So auto-approving below ~$50 is defensible (expected error cost 0.03 × $50 = $1.50, at parity with review cost) and above it isn't. Writing that arithmetic on the whiteboard is a much stronger answer than "we'd have a human approve big refunds."

**⚠ Trap — approval fatigue collapsing the control.** If the agent asks for approval on 40% of actions, reviewers start clicking approve without reading within two weeks, and your control is now a latency tax with a compliance narrative attached. Track **approval rate and time-to-decision**; if median decision time drops below ~5 seconds on non-trivial actions, your humans have stopped reading and you should either raise the threshold or improve the agent so fewer actions need review.

**💰** Approval also costs throughput: a queue with 200 pending approvals and 3 reviewers at 90s each is 100 minutes of drain time, so any agent action requiring approval has a p50 latency measured in tens of minutes. Design the product around that — async notification, not a spinner — or reduce the approval rate.

### Two weeks after a model upgrade, task success dropped 12 points. Diagnose it.

I would not start with the prompt, and the reason is that "the new model is worse" is almost never the finding. The finding is usually that the new model behaves differently in a way your scaffolding didn't anticipate. Here's the order, and each step is a query against the trajectory table you built.

**Step 0: confirm the regression is real.** 12 points on what n? If your eval is 100 tasks run once, the standard error is roughly √(0.5×0.5/100) ≈ 5 points, so a 12-point move is about 2.4σ — real but not overwhelming. Re-run at n=5 per task before anyone spends a week. I have seen a team chase a "regression" that was one unlucky run.

**Step 1: compare termination-reason distributions, old vs new.** This single chart usually names the bug.
- More `max_steps_exhausted` → the new model takes more steps for the same work. Often it's more thorough, or it's decomposing more finely, and your cap is now too tight for its style.
- More `loop_detected` → it repeats calls the old one didn't; usually an argument-formatting mismatch causing repeated empty results.
- More `budget_exhausted` → longer reasoning traces. Check `reasoning_tokens` if you log it.
- More natural completions but lower success → it *thinks* it's done earlier. This is a sufficiency-judgment change and it's the nastiest one, because everything looks healthy.

**Step 2: compare step-count and cost distributions.** A shift in median steps from 6 to 9 with the cap at 10 explains a large success drop mechanically, with no "quality" change at all. Fix: raise the cap (and pay the ~triangular cost increase), or fix the verbosity with prompt guidance.

**Step 3: compare tool-error rates by class.** New models change argument formatting: date formats, enum casing, whether they wrap a single item in a list, whether they emit `null` vs omitting an optional field. A jump in `validation_error` for one tool is diagnostic within seconds and the fix is in your coercion layer, not in the prompt.

**Step 4: check for suppressed or over-eager tool use.** Some models are more conservative about calling tools and answer from parametric knowledge instead — which reads as "hallucination" but is really a tool-invocation-rate regression. Compare `tool_calls_per_run` and, critically, the rate of runs with **zero** tool calls. A jump there is the smoking gun.

**Step 5: only now, look at the prompt.** Prompts overfit to a model. Few-shot exemplars written for the old model's style, a `Thought:` scaffold that fights the new model's native reasoning mode, output-format instructions that the new model's structured-output mode makes redundant and conflicting. Re-run your prompt ablations; the ones that helped before may now hurt.

**⚠ Trap — the alias that moved under you.** If you pinned a floating alias rather than an explicit model snapshot, you may not even know when the change happened. First diagnostic query: `SELECT model_version, date_trunc('day', ts), avg(success) FROM runs GROUP BY 1,2` — if `model_version` is a single alias string for the whole history, you have a logging bug in addition to a regression, and you should fix that before anything else. Pin snapshots; roll forward deliberately; keep the previous snapshot available for an A/B.

**🗣 Say this in the room:** "Before touching the prompt I diff the termination-reason distribution, the step-count distribution and the tool-error classes between the two model versions. Most 'the new model is worse' findings turn out to be 'it takes two more steps and my cap didn't move' or 'it formats dates differently and one tool now 400s.'"

### You're running plan steps in parallel. What breaks?

Everything a backend engineer already knows breaks, plus two things that are specific to agents. I'd answer in that order because the first half establishes credibility fast and the second half is what they're actually testing.

**The familiar half:** write-write conflicts when two branches mutate the same entity; duplicated work when two branches independently fetch the same expensive resource (dedup by content key and share the future — a simple `dict[key, asyncio.Task]` in-flight map removes most of it); rate-limit saturation because 8 concurrent branches × 3 tool calls hit your provider's RPM ceiling all at once, turning a latency optimization into a 429 storm (bound with a semaphore sized to your actual quota, and remember token-per-minute limits bind before request-per-minute for large contexts); stragglers pinning a join barrier; partial failure semantics; and non-deterministic completion order making runs unreproducible.

**The agent-specific half:**

**One — context merge blows the window.** Eight branches each returning 6k tokens is 48k tokens arriving at the synthesizer *simultaneously*, at the most expensive point in the run. The fix is architectural: each branch summarizes its own findings to a bounded budget (say 800 tokens) plus writes the full result to a file/blob the synthesizer can read selectively. This is the filesystem-as-shared-memory pattern and it is the difference between fan-out that scales and fan-out that hits a context limit at width 12.

**Two — blame becomes untraceable.** With sequential steps you know which step poisoned the result. With 8 parallel branches feeding a synthesizer, a wrong final answer could originate anywhere, and the synthesizer's summary has already laundered the provenance. Mitigation: every branch's output carries a `branch_id`, and the synthesizer is required to attribute each claim to a branch. Then a wrong claim maps back to a branch in one query. Without this, debugging a parallel agent is guesswork.

**⚠ Trap — parallelizing writes because the DAG says they're independent.** The planner marked `create_ticket` and `notify_team` as independent because neither depends on the other's *output*. They are still both side effects, and if the run later fails you now have two orphaned effects to compensate. My rule, enforced in the executor rather than requested in the prompt: **side-effecting tools execute in a single serialized lane, in plan order, after all reads complete.** Reads fan out; writes queue. That one rule eliminates the entire class.

**💰 What the parallelism actually buys, honestly:** it buys wall clock, not money. 8 branches at 1.8s each: 14.4s sequential → ~2.2s parallel, a **6.5× latency win at identical token cost** (in fact slightly higher cost, since parallel branches can't share a growing prefix cache the way a sequential trajectory can — expect 10–20% more input tokens). So the trade is real: pay ~15% more to be 6× faster. For an interactive surface that's obviously right; for an overnight batch job it's obviously wrong, and choosing differently in those two contexts is the judgment being tested.

### The transcript keeps growing inside a long loop. How do you manage context without losing the thread?

The mental model: **the transcript is an append-only log with a hard size ceiling and a per-byte re-read cost, so it needs a compaction policy exactly like an LSM tree does.** The question is never "do I compact" — at step 40 you have no choice — it is "what do I keep verbatim, what do I summarize, and what do I evict entirely."

**The four-tier policy I use**, from never-touch to first-evicted:

1. **Never compact:** the system prompt, the tool schemas, and the *original user task verbatim*. Losing the original instruction is the single most damaging compaction failure — the agent drifts to solving the summarized version of the task. I pin the original request at the top and re-assert it at the bottom of a compacted context.
2. **Structured state, maintained explicitly:** a running `findings` object the agent updates — resolved entities, confirmed facts, decisions made with reasons, open questions. This is small (a few hundred tokens), high-density, and survives compaction untouched. Maintaining it costs a little output per step and saves enormously.
3. **Summarize:** older tool results and older reasoning. A tool result from step 3 that produced one useful fact becomes one line: "step 3: `search_orders(customer=Acme)` → 4 orders, IDs 40219, 40220, 40221, 40388." Keep the *identifiers*, drop the prose — identifiers are what later steps actually need.
4. **Evict entirely, with a pointer:** raw payloads go to disk/blob storage and the transcript holds `artifact://run/step3/orders.json (4 records)`. Give the agent a `read_artifact` tool and it can pull back what it needs. This is the pattern that makes long-horizon agents possible at all.

**Trigger:** compact when the transcript crosses a fraction of the model's usable window — I use 60%, not 90%. Two reasons: you need headroom for the current step's tool result (which can be large and whose size you don't know in advance), and effective retrieval from context degrades well before the hard limit. **📄 Paper:** Liu et al. (2023) — *Lost in the Middle* — showed retrieval accuracy from long contexts is U-shaped, strongest at the beginning and end and materially weaker in the middle. That's a direct design instruction: put the task at the top, put the current state and the immediate instruction at the bottom, and accept that the middle is the compaction candidate.

**⚠ Trap — compacting away the failure history.** The agent tried `path/to/config.yaml`, it didn't exist; it tried `config/app.yaml`, permission denied. Summarize those away and the agent will try both again — you have manufactured an infinite loop out of a memory optimization. My rule: **negative results are the highest-value-per-token content in a trajectory and are compacted last.** Keep a running `tried_and_failed` list verbatim. It is tiny and it prevents the most expensive failure mode.

**💰** Compaction has a direct payoff you can state: a run that would have grown to 180k tokens by step 30, compacted at 60% of a 200k window down to ~40k, changes per-step input cost at the tail from 180,000 × 3e-6 = **$0.54/step** to 40,000 × 3e-6 = **$0.12/step**. Over the last 12 steps that's $6.48 → $1.44, a **$5 saving per long run**, at the cost of one summarization call (~$0.15) and some fidelity. On 2,000 long runs/day that's **$9,700/day**. The reason to do it is cost as much as capability.
### Explain LangGraph in terms of what it actually gives you over the raw loop you just wrote.

LangGraph's core abstraction is a **state machine with a typed, reducer-merged state object and a pluggable persistence layer**. You declare nodes (functions that take state and return a partial update), edges (static or conditional), and a channel-based state schema where each field declares how concurrent updates merge. You compile the graph with a checkpointer and invoke it with a thread identifier; the checkpointer persists a snapshot of state after every super-step.

```python
from typing import Annotated, TypedDict
from operator import add
from langgraph.graph import StateGraph, START, END

class S(TypedDict):
    messages: Annotated[list, add]     # reducer: concurrent branches append
    steps: int

def call_model(s: S) -> dict:  ...     # returns {"messages": [...], "steps": s["steps"]+1}
def run_tools(s: S) -> dict:   ...
def should_continue(s: S) -> str:
    return "tools" if has_tool_call(s["messages"][-1]) else END

g = StateGraph(S)
g.add_node("model", call_model); g.add_node("tools", run_tools)
g.add_edge(START, "model")
g.add_conditional_edges("model", should_continue, {"tools": "tools", END: END})
g.add_edge("tools", "model")                       # the cycle — this is the agent
app = g.compile(checkpointer=checkpointer)
app.invoke({"messages": [...], "steps": 0}, config={"configurable": {"thread_id": "t1"}})
```

**📅 Volatile:** LangGraph's API surface has moved fast — exact checkpointer class names, package split and the interrupt API have all changed across releases; verify against current docs before writing it in a take-home.

**What you genuinely get that you'd otherwise build:** durable checkpointing per super-step (so crash-resume and multi-day human-in-the-loop waits are free); the reducer model, which is the correct answer to "two parallel nodes both wrote to `findings`" and is easy to get subtly wrong by hand; interrupts as a first-class suspend/resume rather than a bespoke state machine; state history you can rewind and fork; and streaming of intermediate node outputs, which maps onto the event set your UI needs.

**What it costs you:** an abstraction between you and the message list, which is where 90% of agent debugging happens. Stack traces get deeper. The mental model of "super-steps" and channel writes is a real thing to learn. And you inherit the release cadence of a fast-moving library in a fast-moving ecosystem.

**My decision rule:** I reach for LangGraph when I need **durable, resumable, human-interruptible execution** — an agent that suspends for four hours waiting on an approval and resumes in a different pod. That is a hard thing to build well and the checkpointer is genuinely good at it. For a 6-step synchronous agent behind a FastAPI endpoint, the raw loop plus a `RunState` row in Postgres is less code, easier to debug, and has no upgrade treadmill. **The thing I would never accept as a justification is "it's the standard."**

**🗣 Say this in the room:** "LangGraph is a durable state machine with reducer-merged state and a checkpointer. I'd adopt it when I need suspend-resume across processes and human-in-the-loop waits, because that's the part that's genuinely hard to build. For a short synchronous loop it's an abstraction between me and the message list, which is exactly where I debug."

### What are LangGraph interrupts and "time travel," and what backend primitives are they?

They are the two features I'd point to as the honest reason to adopt a graph framework, because both are annoying to build correctly and both are things product requirements will eventually demand.

**Interrupts are a durable `await` on an external event.** A node signals that it needs input — either statically (compile the graph to pause before or after a named node) or dynamically (call an interrupt function inside the node with a payload for the human). Execution stops, the checkpointer persists the complete state, and the call returns. Later — seconds or days later, in a different process — you resume that thread with a supplied value, and execution continues *from inside the interrupted node*.

The backend analogue is precise: this is a durable workflow suspend, exactly what Temporal or a Step Functions wait-for-callback state gives you. The part people underestimate is the "resumes inside the node" semantics. A naive implementation re-runs the node from the top on resume, which means any side effect earlier in that node happens twice. That's the same at-least-once execution hazard you know from workflow engines, and the same answer applies: keep side effects idempotent, or isolate each side effect in its own node so the checkpoint boundary sits between them. **I'd put "one side effect per node" in the design review checklist.**

**Time travel is state history plus fork.** Because the checkpointer stores a snapshot per super-step, you can list the history of a thread, pick a checkpoint, and resume *from* it — optionally after editing the state. That's `git checkout` plus an amended commit, or a database PITR restore. Three concrete uses:

1. **Debugging.** A run went wrong at step 9. Rewind to step 8, edit the state (fix the malformed argument, replace a bad tool result), and re-run forward. You debug the actual failure without reproducing 8 steps of setup — which for an agent is genuinely painful otherwise.
2. **Counterfactual evaluation.** Fork the same checkpoint N ways with different prompts or models and compare outcomes with everything before the fork held fixed. This is a much cleaner experiment than re-running whole trajectories, because you've eliminated the variance from steps 1–8.
3. **User-facing undo.** "Go back to before it deleted that section and take a different path" is a product feature that falls out of the primitive.

**⚠ Trap — thinking time travel undoes side effects.** It does not. Rewinding state to step 8 does not un-send the email step 9 sent. The checkpointer is a database of your *agent's* state, not of the world. If you expose rewind to users, you need compensating actions for every side effect between the fork point and the current head, and you need to know which effects are compensable. This is saga design, and it's the question I'd ask a candidate who name-drops time travel — because most people repeating the feature name have not thought about it for ten seconds.

### Walk me through the OpenAI Agents SDK. What's the shape of it and where would you use it?

The shape: **a small, deliberately un-clever library around agents-as-objects with handoffs, guardrails, sessions and built-in tracing.** You define an agent with instructions, a model, and a list of tools (Python functions decorated so their signature and docstring become the JSON schema). You run it with a runner that owns the loop. Agents can *hand off* to other agents — a handoff is exposed to the model as a tool, so delegation is just tool calling with the target agent's context taking over. Guardrails are validation functions that run on input and/or output and can trip a tripwire that halts the run. Sessions provide conversation history persistence so you don't manage the message list yourself. Tracing is on by default and emits spans for runs, model calls, tool calls and handoffs.

**📅 Volatile:** exact decorator and class names, and whether the framework is provider-agnostic in your target version, change; verify before writing it in a take-home.

**What I like about it, honestly:** the abstraction count is low. You can read the whole surface in an afternoon, and dropping to a raw API call is not a fight. Handoffs-as-tools is the right primitive — it makes delegation appear in the trace as a normal tool call, so your observability doesn't need a special case. And tracing being on by default is a real product decision: the number one thing missing from hand-rolled agents is instrumentation, and a framework that gives it to you unasked is doing you a service.

**What I'd watch:** guardrails that run as *model* calls add latency to every request and can become the p95 story — an input guardrail that costs 400ms on a 1.8s request is 22% of your latency budget, so run cheap deterministic guardrails first and only escalate to a model-based one on suspicion. And the handoff model makes it easy to build a five-agent topology when one agent with five tools would be better and cheaper — the framework makes the expensive design as easy to type as the cheap one, which is always a hazard.

**Where I'd use it:** a multi-surface product where routing between specialists with genuinely different tool sets and permissions is the architecture — triage → billing specialist → refunds specialist, each with a distinct tool allowlist. The handoff primitive plus per-agent tool scoping does real work there. For a single-purpose agent, it's a thin wrapper over the loop and I'd weigh it against just writing the loop.

### What do you inherit from the Claude Agent SDK, and what do you still own?

The framing I'd lead with, because it's the honest one and it's the sentence hiring managers want to hear: **the agent loop is not your code anymore, and that's mostly good.** What a harness like this gives you is the loop plus the operational machinery around it — context-window management and compaction as the transcript grows, tool execution with retry, transcript persistence and session resumption, a permission system that gates tool use, subagents that run with their own separate context and return a summary, hooks that fire at defined lifecycle points so you can inject policy deterministically, and MCP client support so external servers become available tools.

**📅 Volatile:** the exact surface — function vs client-class entry points, hook event names, permission modes, subagent configuration — evolves; check current docs.

**What's genuinely valuable and hard to rebuild:**

- **Compaction that works.** Deciding what to summarize and what to keep verbatim at 80% window utilization, without losing the original task or the failure history, is a real engineering problem that a harness has already solved and tuned across many workloads.
- **Subagents as context isolation.** The correct justification for a subagent is a *separate context window* or *separate permissions*, not "sophistication." A subagent reads 40 files and returns 600 tokens of findings; the lead's context never sees the 200k tokens of raw file content. That's the pattern, and having it built in stops people from inventing worse versions.
- **Hooks as deterministic policy.** A hook that fires before every tool call is exactly the place to put authorization, redaction, audit logging and rate limiting — in code, on the enforcement path, not in the prompt. This is the mechanism that lets you follow the "take authorization away from the model" rule inside someone else's loop.

**What you still own, entirely, and what your interview should be about:** tool design (still the number one determinant of quality); the system prompt and the task decomposition; domain state and its consistency; your evals; budgets and cost attribution; observability beyond what the harness emits; the product's termination and escalation policy; and everything about your data model. A harness gives you a loop. It does not give you a good agent, and the gap between those two is where you get hired.

**⚠ Trap — assuming the harness's defaults are your policy.** Default permission behaviour, default compaction thresholds, default retry counts and default max turns are chosen for a general workload, not for one where a tool moves money. Read them, override them explicitly, and write down why in the repo. A harness default silently becoming your production risk posture is a real incident pattern.

**🗣 Say this in the room:** "I treat the harness as inherited infrastructure — it owns the loop, compaction, retries and transcript persistence. I still own tool design, policy, budgets, evals and observability. And I override every default that touches money or permissions explicitly, because a general-purpose default is not a risk decision for my product."

### Position CrewAI, AutoGen/AG2 and Semantic Kernel for me. When is each the right call?

These three occupy genuinely different niches and the mistake is treating them as three brands of the same thing.

**CrewAI** models a team: agents with a role, a goal and a backstory, tasks assigned to them, and a process that is sequential or hierarchical (a manager agent delegating). It also has a more deterministic flow-style construct for wiring event-driven pipelines around crews. Its strength is **speed to a demo** — the role/goal/task vocabulary maps onto how a non-engineer describes the problem, so you get something running in an hour and stakeholders understand the diagram. Its weakness is that the same vocabulary encourages a multi-agent design where a single agent would do, and the persona prompting ("You are a seasoned financial analyst with 20 years of experience") is largely decorative — I have not seen backstory text produce reliable quality gains, and it costs tokens on every call. Use it for prototyping and for internal tools where the team-of-agents metaphor is genuinely the user's mental model.

**AutoGen / AG2** comes from a conversation-programming lineage: agents are conversational participants, and orchestration is expressed as multi-agent chat with configurable speaker selection, plus first-class code-execution agents. Its strength is **research-shaped exploration** — debate, critic-generator pairs, group chats with a selector, and the code-writing-and-executing pattern. Note the ecosystem split: the project forked into a community-governed AG2 alongside Microsoft's continued work, and the API went through a substantial re-architecture; **📅 Volatile — check which lineage and which major version you'd actually be adopting before committing.** Use it when the pattern you want really is a conversation between agents and you want the group-chat machinery for free.

**Semantic Kernel** is Microsoft's enterprise SDK, .NET-first with Python and Java support, built around a kernel with plugins (functions the model can invoke), connectors, memory abstractions, filters for cross-cutting policy, and dependency-injection-shaped composition. Its strength is that it fits an existing enterprise .NET/Azure application the way none of the others do — telemetry, identity, DI, and governance all plug into what the org already runs. If the interview is at a Microsoft-shop enterprise, knowing that Semantic Kernel exists and *why* it looks the way it does (it is designed to be adopted by an application, not to be the application) is the answer they want.

**⚠ Trap — grading these on features.** They are not really competing on capability; they're competing on which mental model your team already has. The senior framing: "CrewAI optimizes for stakeholder legibility, AutoGen for multi-agent research patterns, Semantic Kernel for enterprise .NET integration. None of them changes what a model can do, and none of them removes the work — tool design, evals, budgets."

**🗣 Say this in the room:** "I'd pick on team fit and blast radius, not features. All three wrap the same loop. What differs is the vocabulary they impose and how hard it is to drop to a raw API call when the abstraction is wrong — and I weight that last property heavily, because at some point it always is."

### Same question for LlamaIndex Workflows, Pydantic AI and Smolagents.

These three are the ones I'd actually reach for most often in a Python backend shop, and each embodies a distinct thesis.

**LlamaIndex Workflows** takes the position that agent orchestration is **event-driven**, not graph-declared. You write step handlers that consume an event type and emit another; the runtime routes by type. There is no separate graph object to keep in sync with your code — the wiring is the type signatures. Loops are steps that emit an event they also consume; branches are steps that emit one of several event types; parallelism is emitting multiple events and having a step that collects N of them before proceeding. If you've written a Kafka consumer topology this will feel immediately right, and the absence of a declared-graph-versus-actual-code drift is a genuine advantage over node-and-edge frameworks. It also sits next to a mature retrieval library, so a RAG-heavy agent has less integration work.

**Pydantic AI** takes the position that the interesting problem is **typed IO and dependency injection**, which is precisely the thesis a FastAPI-shaped engineer already believes. Agents are generic over a dependency type and an output type; tools are functions with Pydantic-validated arguments; the output is a validated model, and validation failure is fed back to the model for repair automatically. It's provider-agnostic, testable with the patterns you already use, and it has the smallest conceptual delta from a normal Python service of anything in this list. **This is my default recommendation for a Python backend team building a production agent**, because the abstractions it adds are ones you'd have built anyway, and it does not try to own your control flow.

**Smolagents** takes the position that the action space should be **code, not JSON**. The headline agent writes Python that calls your tools as functions and runs it in a sandbox, rather than emitting one tool call per step. The argument is compelling: a task that would be 20 tool calls ("for each of these 20 tickets, fetch the customer and check their tier") becomes one code block with a loop, which collapses 20 round trips into one — a huge win on both latency and the quadratic context term. The cost is that you are now executing model-written code, so the sandbox is a security boundary that must be real (no network by default, no filesystem outside a scratch dir, resource limits, and a whitelist of importable modules). It's small enough to read end to end, which I value.

**💰 The code-as-action arithmetic, since it's the interesting claim:** 20 items processed as individual tool calls, against a growing context (≈3,000-token base, ≈900 tokens added per step) at 1.6s each ≈ 20 model calls, roughly Σ input ≈ 20×3,000 + 900×190 = 60,000 + 171,000 = 231,000 tokens ≈ $0.69 and 32s. As one code block: one generation (~1,500 out), one execution (0.4s), one result (~1,200 tokens in) ≈ **~$0.04 and ~4s.** That's a **17× cost reduction and 8× latency reduction** on a fan-out-shaped task, which is why this pattern keeps winning and why I expect more of the ecosystem to move toward it.

**⚠ Trap:** proposing code execution without naming the sandbox requirements. If a candidate says "the agent writes code and we run it" and doesn't immediately say "in a container with no network, a read-only mount, a CPU/memory cap and a timeout," that's a security-review fail regardless of how good the rest of the design was.

### What is DSPy actually, and where does it fit in an agent loop?

DSPy is not an agent framework competing with the others; it is a **programming model plus an optimizer for prompts**, and misclassifying it is a common interview stumble.

The mental model: **stop writing prompt strings, write a typed function signature and let a compiler search for the prompt.** You declare a *signature* — input fields, output fields, a short task description — and compose *modules* (predict, chain-of-thought, a ReAct-style module) into a program. Then an *optimizer* takes a small training set and a metric and searches over few-shot exemplar selection and instruction wording to maximize the metric, producing a compiled program with concrete prompts baked in. The exemplars can be *bootstrapped* — the optimizer runs your program on training inputs, keeps the traces where the metric passed, and uses those as demonstrations.

Why this matters for agents specifically: every prompt in your agent — the planner, the sufficiency judge, the summarizer, the router — is a hand-tuned string that someone wrote once and nobody has re-tuned since the last model upgrade. DSPy turns those into artifacts you can *recompile* against a new model with your existing eval set. That reframing is the strongest argument for it: **prompts overfit to a model, and a compiler makes model migration a re-run instead of a rewrite.** If you have ever had to re-tune fifteen prompts after a model change, the value is obvious.

**Where it fits and where it doesn't.** It fits the *individual model calls* inside your loop — replacing hand-written prompts for well-defined sub-tasks that have a measurable metric. It does not fit your control flow, your budgets, your termination policy or your tool execution; you still own all of that. The right composition is: your loop and your scaffolding, with DSPy-compiled modules where a prompt would otherwise be.

**The prerequisite people skip:** you need a metric and a training set. If you cannot write `metric(example, prediction) -> float`, there is nothing to optimize and DSPy gives you a slightly awkward way to write prompts. So it's downstream of building an eval, which is where you should be anyway. **📅 Volatile:** the optimizer lineup and their names have changed across versions; describe the mechanism (bootstrapped demonstrations plus instruction search against a metric) rather than reciting an optimizer name you're unsure of.

**⚠ Trap — expecting optimizer magic on a broken program.** If the module's signature is wrong, or the metric doesn't measure what you care about, the optimizer will faithfully maximize the wrong thing and hand you a program that scores well and behaves badly. Same failure as any optimization loop with a bad objective — it's Goodhart, and the fix is the same: hold out a test set the optimizer never sees, and look at the actual outputs.

### Framework churn is real. How do you architect an agent so swapping the framework is cheap?

I name framework churn as a *risk to be mitigated*, not a competition to be won, and I say that explicitly in interviews because it's the truthful read: this ecosystem has re-architected itself repeatedly and will again. Betting your codebase's structure on a library that may be substantially different in eighteen months is a real engineering risk, and treating it as one is a seniority signal.

The mitigation is boring and it is exactly the hexagonal/ports-and-adapters discipline you already apply to a database driver. Four boundaries:

**1. Tools are plain functions with Pydantic models, in your own package, with zero framework imports.** A tool is `def refund_order(args: RefundArgs, ctx: Context) -> RefundResult`. Schema generation, registration and dispatch are adapters. When you swap frameworks, your tools do not change — and tools are where the actual value is. If a candidate's tools import framework decorators, their tool layer is captive.

**2. Domain state is yours, in your database, not in the framework's state object.** The framework may hold the transcript. It must not hold "which order we're refunding." Your `RunState` row is the source of truth; the framework's state is a cache of the conversation. This also means a framework migration doesn't need a data migration.

**3. Prompts are versioned artifacts** — files or DB rows with an ID, not string literals inside node functions. Then the prompt suite migrates with a copy, and you can A/B prompt versions independently of code deploys.

**4. Evals run against an interface, not an implementation.** `run_task(task: str, ctx) -> Trajectory`, where `Trajectory` is your dataclass. Both the raw loop and the framework implementation satisfy it. Now "should we adopt X" is an experiment you run in an afternoon — implement the adapter, run the eval suite, compare success rate, cost and p95 — instead of a quarter-long religious argument. **This is the single most useful thing on the list**, because it converts a taste debate into a measurement.

**What I explicitly do NOT abstract:** I do not build a framework-agnostic wrapper over agent frameworks. That's a second abstraction layer over abstractions that are already leaky, and it fails at exactly the moment you need to use the one feature that motivated the choice. Pick one, isolate it behind the four boundaries above, and accept that swapping means rewriting the orchestration layer — which should be a few hundred lines, not the system.

**🗣 Say this in the room:** "I treat framework choice as reversible and design for the reversal: tools are plain functions with no framework imports, domain state lives in my database, prompts are versioned artifacts, and evals run against my own `run_task` interface. Then adopting or dropping a framework is an afternoon's adapter plus an eval run, not a rewrite — and I've made a taste argument into a measurement."

### Would you use a framework at all? Give me your actual answer, not a diplomatic one.

For most product agents: **no framework for the loop, yes for the parts that are genuinely hard.** Here's the reasoning, and I'd give it in this order.

The loop is thirty lines. It is not the hard part, and wrapping it costs you the thing you need most, which is the ability to read the exact message list you're sending. Every agent debugging session I have ever run ended with printing the messages array. An abstraction that makes that harder is a tax paid in the worst hour of the quarter.

What *is* hard, and where I'd take help: durable suspend/resume across processes (LangGraph checkpointers, Temporal, or a workflow engine you already run); context compaction that doesn't lose the task or the failure history (a harness); tracing and evaluation infrastructure (an observability vendor or an OTel-based setup, and I would take this every time — instrumentation is the most commonly missing piece and the most valuable); sandboxed code execution; and typed IO with automatic validation-repair, which Pydantic AI gives you for almost no conceptual cost.

**The decision rule I'd state:** adopt a framework when it owns a problem you would otherwise have to solve *correctly*, not when it owns a problem you would otherwise have to *type*. Checkpointing across a pod restart is the former. Calling `messages.append` is the latter.

**The counter-position, stated fairly**, because this is genuinely contested and pretending otherwise is a worse answer: on a large team, a framework is a shared vocabulary and a floor on quality. Fifteen engineers each hand-rolling a loop produces fifteen different termination policies, and the one that forgot the wall-clock guard is the one that pages you. If you're standardizing across many teams, the framework's real product is *consistency*, and that's a legitimate reason to accept abstraction cost. I'd say exactly that, then say which side I'd choose for the specific team in the question — because the interviewer is testing whether you have a position, and refusing to pick one reads as not having thought about it.

**⚠ Trap — the anti-framework answer that's just ignorance.** "I'd write it from scratch" is only credible if you can immediately name what LangGraph's checkpointer does, what a reducer solves, and what an interrupt is. Reject the abstraction *from knowledge*, not from unfamiliarity. Interviewers can tell the difference in one follow-up question, and the failure mode is severe: you go from "opinionated senior" to "hasn't used the tools."

**🗣 Say this in the room:** "I don't use a framework for the loop — it's thirty lines and I want to read my own message list when I'm debugging. I do use one for durable suspend-resume, compaction, tracing and sandboxing, because those are things I'd have to get *right* rather than things I'd have to type. On a fifteen-engineer team I'd flip toward the framework, because its real product is consistency of termination policy."

### 🏋 Build a working agent loop against a real API in 45 minutes, with retry and termination. What's the rubric?

**🏋 Drill.** Timer at 45 minutes, no autocomplete, no copy-paste from a previous project. Task: an agent with three tools against a real API of your choice — a search tool, a fetch-detail tool, and one side-effecting tool (create a record). Answer a question that requires at least two dependent lookups and one write.

**Pass criteria, and this is the rubric I'd grade a take-home on:**

1. **The loop terminates on all four paths** — natural stop, max steps, token/dollar budget, wall clock — and each sets a distinct `termination_reason` you can read in the output. Missing wall clock is the most common miss.
2. **Errors return to the model as text with `is_error`, not as exceptions**, and the error text is specific enough to enable self-repair. Grade your own error strings: does `"Invalid date"` appear anywhere? Rewrite it.
3. **The side-effecting tool has a deterministic idempotency key** derived from run state, and calling the loop twice with the same run ID does not create two records. Test it by killing the process mid-run and restarting.
4. **Arguments are validated with a Pydantic model before dispatch**, and a validation failure returns the validation error to the model rather than raising.
5. **Tool results are truncated to a budget** with a marker showing truncation happened, and the truncation limit is a constant you can point to.
6. **Every step is logged** with step index, tool, args fingerprint, status, input/output tokens, cost and latency. Printing to stdout as JSON lines counts; you can grep it.
7. **Retry is on the tool call with backoff and jitter, and it is not on the trajectory.** Retryable errors are classified explicitly; a validation error is not retried.
8. **A loop guard exists** — repeated identical call detection, at minimum.

**Failure modes to watch for in yourself under time pressure:** you will skip the wall-clock deadline (it feels redundant next to max steps — it isn't); you will inline the tool result without truncation and be surprised when one result is 90k characters; you will forget that the assistant turn containing tool calls must be appended *before* you execute them, and your resume path will orphan effects; and you will write a `while True` with one `break` because it's faster, then be unable to say why the run ended.

**If you finish early**, the extension that shows seniority: add the forced-summarization exit. When any guard trips, strip the tools and make one final call asking for the best available answer with explicit gaps. Then your loop never returns `None`, which is the difference between a demo and a product.

**💰 Budget the drill itself:** at ~12 steps and ~$0.015/step, each test run costs about **$0.18**, so twenty iterations while debugging is $3.60. Set a hard `MAX_RUN_USD = 0.50` in the code from minute one — partly because it's the right engineering, partly because you will write an infinite loop at least once during this drill and it is much better to learn that lesson at $0.50 than at $400.

### 🏋 Now the harder one: a DAG executor with cycle detection and parallel execution, timed.

**🏋 Drill.** Timer at 40 minutes. Implement a plan executor that takes a model-authored plan (steps with `id`, `tool`, `args` possibly containing `#Ex` references, and `depends_on`), validates it, and executes it with bounded parallelism, per-step timeouts, and a supervisor that decides retry-versus-replan-versus-abort on failure.

**Pass criteria:**

1. **Validation rejects a bad plan before any execution.** Undefined dependency, cycle, unresolvable placeholder, unknown tool name, plan longer than the step budget. Five distinct error types, each with a test.
2. **Cycle detection is real.** Use `graphlib.TopologicalSorter` and let `prepare()` raise, or write Kahn's algorithm and show the remaining-nodes-nonempty check. Either is fine; hand-waving is not.
3. **Parallelism is bounded and correct.** Steps at the same topological level run concurrently under a semaphore; the level barrier is correct; a failure in one branch doesn't silently lose the others' results.
4. **Placeholder substitution is strict.** An unresolved `#E7` after substitution is a hard error, never a literal string passed to a tool.
5. **Side-effecting steps are serialized** regardless of what the DAG permits, and this is enforced by the executor from a registry flag — not by trusting the plan.
6. **Per-step timeout produces a `timed_out` result** that flows into the supervisor's decision, rather than cancelling the world.
7. **Fan-out is capped**, with the cap enforced at validation time and reported back to the planner on violation.
8. **Partial results survive failure.** If step 6 of 8 fails, steps 1–5's results are still available to the supervisor and to a replan.

**Pass criterion for the whole drill:** you can run it on a plan with a diamond dependency (A → {B, C} → D), watch B and C execute concurrently in the log timestamps, kill C's tool with an exception, and see the supervisor make a decision with A's and B's results in hand. If you can demo that in one terminal, you'd pass this round at most companies.

**⚠ Trap you will hit:** `asyncio.gather` with the default `return_exceptions=False` cancels sibling tasks on the first exception, and you will lose the results of branches that had already completed. Either pass `return_exceptions=True` and inspect, or wrap each step to return a result object rather than raise. Getting this wrong is the single most common bug in hand-rolled parallel executors and it's invisible until a branch fails in production.

**Stretch, if you finish:** make it resumable. Persist completed step results keyed by `(plan_hash, step_id)`; on restart, skip steps with a cached result. Then kill the process mid-run and restart it, and watch it complete without re-running the expensive steps. That's ten more lines and it's the feature that turns a homework exercise into something you'd actually ship.

### Close me out: when does "one well-instrumented loop with good tools" stop being the right answer?

I'll state the thesis first because I believe it and I'd defend it: **for the large majority of product agents, a single model in a well-instrumented loop with excellent tools beats an elaborate multi-agent graph, and the elaborate design usually loses on cost, latency, debuggability and evaluability simultaneously.** The reason is structural, not fashionable — every additional agent boundary is a lossy serialization of context, an extra model call, an extra failure mode, and a place where blame becomes ambiguous. Complexity in this domain has a measurable price and it is rarely paid back.

Here are the five conditions under which I'd abandon the single loop, and I want each one to be a *forcing* condition, not a preference:

**1. Separate permissions.** A sub-agent that can read HR records must not share a context with one that can post to Slack, because prompt injection in the second becomes exfiltration from the first. Different trust domains are the single strongest reason to split, and it's an argument you can make to a security reviewer. This one alone justifies the architecture.

**2. Context that cannot coexist.** The lead needs to read 40 documents totalling 500k tokens and then answer in 2k. That does not fit, and no compaction policy makes it fit well. Fan out readers that each return a bounded summary; the lead never sees a raw page. Note this is a *context* argument, not a *parallelism* argument — you'd split even if it were slower.

**3. Latency requiring genuine concurrency on independent work.** Eight independent searches at 1.8s each: 14.4s serial versus ~2.2s parallel. If the product's tolerance is 5s, you have no choice. Below that threshold, don't pay for it.

**4. Materially different tool sets or SLAs per task class,** such that a single agent's tool catalog would exceed the size where selection degrades. Past a few dozen tools, selection accuracy falls measurably; splitting by domain restores it. Note the fixes to try first: namespacing, retrieval-based tool selection, and folding narrow tools into flexible ones.

**5. Independent iteration by separate teams.** Organizational, but real. Two teams shipping to one prompt is a merge conflict with a quality regression attached.

**What is NOT on that list, and I'd push back if proposed:** "the task is complex" (complexity argues for better tools, not more agents); "a persona per role will improve quality" (I've seen no reliable evidence, and backstory prompting costs tokens on every call); "multi-agent is more scalable" (it is 5–15× the tokens for read-heavy fan-out); and "the paper did it that way" (the paper wasn't paying your inference bill or your on-call rotation).

**💰 The number that ends the argument:** a supervisor with four workers on a research-shaped task runs roughly 1 planning call + 4 × 6 worker steps + 1 synthesis = 26 model calls with a lot of duplicated context, versus a single loop's 10 steps. At ~$0.02/call that's $0.52 versus $0.20 — **2.6× on a small task, and the multiple grows toward 10–15× as worker context grows**, because each worker re-reads its own accumulating transcript. The multi-agent design must be more than 2.6× better on the metric you actually care about. Sometimes it is — parallel research genuinely covers more ground. Usually it isn't.

**🗣 Say this in the room:** "I'd start with one loop, excellent tools, and real instrumentation, and I'd split only for separate permissions, context that can't coexist, hard concurrency requirements, tool-catalog size, or team boundaries. Everything else — complexity, personas, elegance — I'd treat as a reason to improve the tools instead. And I'd say out loud when a multi-agent design should be collapsed back into one, because that recommendation is usually the higher-value one and nobody wants to make it."
