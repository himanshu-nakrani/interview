## 44. Multi-Agent Topologies and Harness Engineering

*Mastering this proves you know the real justification for sub-agents is separate context or separate permissions — not sophistication.*

### A team shows up at design review with a five-agent architecture. What is the first question you ask them?

"Which of these agents needs a context window the others must not see, or a credential the others must not hold?" That is the whole question, and if the answer is "neither, we just thought it was cleaner," I send the design back as a single agent with five tools.

The mental model I want you to hold is that a sub-agent is not a module. It is a **process boundary with a lossy serialization layer bolted onto it**. You already know what that costs, because you have argued against premature microservices: you give up shared memory, you gain a network hop, you gain independent failure, and now every piece of state that used to be a variable has to be marshalled into a schema someone maintains. Sub-agents are exactly that, except the serialization format is English, the marshalling is done by a stochastic process, and there is no type checker. The only things that justify paying that price are the two that a single agent physically cannot provide:

**Separate context.** The lead's window is a scarce, shared, quadratically-priced resource. If a subtask must read 400k tokens of source material to produce a 500-token conclusion, that reading must happen somewhere the lead cannot see, or the lead's window is destroyed for every subsequent turn. This is the honest case, and it is the majority of real multi-agent systems in production. It is a *garbage-collection* argument, not an intelligence argument.

**Separate permissions.** The agent that can `DELETE FROM` must not be the agent that reads untrusted web pages. If one loop holds both capabilities, a prompt injection on page three is a production incident. Splitting the loop turns a policy problem into a topology problem, which is the only place you can actually enforce it.

Everything else people cite — "specialization improves quality," "each agent has a focused prompt," "it mirrors how a human team works" — is either achievable with better tool descriptions inside one loop, or is an anthropomorphic story about org charts that does not survive contact with a token bill.

**⚠ Trap:** believing role prompts create capability. Telling one instance "you are a meticulous security reviewer" and another "you are a performance expert" does not produce two different models. It produces one model sampled twice with different priming, and their errors are strongly correlated because they share weights and training data. Specialization by prompt buys you attention allocation, not independent judgment. Anyone who claims their five personas "check each other" is claiming independence they cannot demonstrate.

**🗣 Say this in the room:** "I treat sub-agents the way I treat microservices — the justification has to be an isolation boundary I actually need, either context isolation or a permission boundary. Anything I can do with one loop and better tools, I do with one loop, because every handoff is a lossy English serialization I now have to test."

### Enumerate the multi-agent topologies for me, and give me the decision rule for picking each one.

There are five shapes worth naming, and the useful way to order them is by how much control you hand from your code to the model. That axis predicts both the failure modes and the debugging cost.

**1. Single agent with tools.** One loop, one message list, N tools. Control flow is the model choosing tool calls; your code owns dispatch. *Rule: this is the default, and you must be able to state the specific reason you left it.* It wins on debuggability (one linear transcript), cost (no context duplication), and coherence (no handoff loss). It loses when one subtask's raw output would blow the window, or when two subtasks need different credentials.

**2. Supervisor / orchestrator-worker.** A lead agent decomposes, spawns workers, receives their compressed results, synthesizes. Workers do not talk to each other and do not talk to the user. *Rule: use when the work is read-heavy, parallelizable, and each unit produces a small conclusion from a large input.* This is the research-agent shape, and it is the topology that pays for itself most reliably because the compression ratio is real: 200k tokens in, 800 tokens out, per worker.

**3. Hierarchical (supervisor of supervisors).** Three or more levels. *Rule: I have essentially never seen a third level pay for itself, and I would push back hard.* Each level adds a full serialize/deserialize of intent, so the instruction that reaches a leaf has been paraphrased twice. Use it only when the fan-out is genuinely too wide for one lead's context to hold even the worker *manifest* — e.g. 300 workers where the list of task specs alone is 60k tokens.

**4. Network / swarm / handoff.** Any agent can transfer control to any other; there is no coordinator. *Rule: use when the routing decision is genuinely local and the topology is small (3–5 agents) — the classic case is customer support triage where the billing agent knows, mid-conversation, that this is really a fraud question.* Beyond ~5 nodes it becomes untestable: the reachable state space is the transitive closure of the handoff graph, and you have no way to enumerate the paths.

**5. Debate / ensemble.** Multiple agents produce candidate answers, then critique or vote. *Rule: use only where you can show measured error decorrelation, which in practice means different models or different evidence, not different personas.* 📄 **Paper:** Du et al. (2023), "Improving Factuality and Reasoning in Language Models through Multiagent Debate" — showed that having several model instances propose and then revise across rounds improves factuality on reasoning benchmarks. It replaced single-pass self-consistency for some tasks, at roughly N×R the cost for N agents and R rounds. That multiplier is why it lives in offline eval and high-stakes verification, not in a chat latency budget.

**⚠ Trap:** treating this as a ladder of sophistication where you graduate upward. It is a ladder of *cost and opacity*. The correct movement in a mature system is usually downward — teams start at 4 and collapse to 2, or start at 2 and collapse to 1 once they realize the sub-agents were compensating for bad tool design.

**🗣 Say this in the room:** "Single agent, orchestrator-worker, hierarchical, network, debate — in increasing order of how much control I hand to the model. I default to single-agent, I reach for orchestrator-worker when the subtasks are read-heavy and compress well, and I'm suspicious of anything deeper because each level is another lossy paraphrase of the original instruction."

### Make the case for the single agent with tools. Why is it still the default in 2026, when every conference talk is about agent swarms?

Because a single loop is the only topology where the model has complete information, and complete information is the scarcest resource in agentic systems.

Think about what happens inside one loop. Step 7 can see the exact bytes that step 3's tool returned. If step 3's SQL query returned an empty result because of a timezone boundary, step 7 sees the empty result *and* the query, and can notice. The moment you split that across agents, step 7 sees "the query returned no rows" — a sentence written by a different sampling event, which has already discarded the query text, the timezone, and the fact that the worker guessed at the date format. The information that would have let the system self-correct was destroyed at the handoff, and no amount of prompt engineering downstream can reconstruct it.

The second reason is that debugging is linear. One transcript, one ordering, one place to look. In an orchestrator-worker run you have a tree, the leaves are concurrent, timestamps interleave, and the causal chain from "wrong final answer" back to "worker 4 misread a table" crosses two summarization steps. I have spent hours on multi-agent postmortems that would have been a ten-minute transcript read in a single loop.

The third is cost, and this is where people are least honest. A single agent pays for its context once per turn. An orchestrator-worker run pays for the lead's context *plus* each worker's full system prompt, tool schemas, and task briefing — and workers re-read their own growing transcripts too. 📐 **Numbers you must know:** Anthropic's published engineering write-up of their multi-agent research system reported that agents use roughly **4× the tokens of a chat interaction, and multi-agent systems roughly 15×**. Derivation of why that shape is plausible: a chat turn is one prompt plus one completion. An agent turn re-reads its whole transcript every step, so a 10-step loop pays roughly the triangular sum — with a 6k-token base and 2k added per step, total input across steps is 6k·10 + 2k·(0+1+…+9) = 60k + 90k = 150k versus ~8k for a single chat exchange, and once you add tool schemas and results you land in the 4× ballpark relative to a *multi-turn* chat. Multi-agent then multiplies that by fan-out plus the lead's own loop. **📅 Volatile:** verify that 15× figure against the current published source before you quote it in a loop; the number is architecture-dependent, and quoting it as a law rather than as one team's measurement is how you get caught.

**⚠ Trap:** reaching for sub-agents to fix a context problem that is actually a tool-design problem. If your tool returns 40k tokens of JSON and you "solve" it by putting the tool behind a sub-agent that summarizes, you have paid a full model round-trip to do what a `fields=` parameter and a server-side filter would have done for free. Fix the tool first. The rule I enforce in review: you may not propose a sub-agent for a context problem until you have shown me the tool's output schema and explained why it cannot be narrowed.

### Draw me the orchestrator-worker topology. Where does the state live, and what crosses the boundary?

Picture it as a fan-out job in a worker pool where the queue payload is a paragraph of English and the return value is a paragraph of English — and neither is validated by anything but your own schema discipline.

The lead agent runs a normal loop. One of its "tools" is `spawn_worker(task_spec) -> worker_report`. When the model calls it, your dispatcher does not call an API — it starts an entirely fresh agent loop with its own message list, its own system prompt, its own tool subset, and its own budget. That loop runs to completion (or to its own step/token/wall-clock cap), produces a final report, and your dispatcher returns *only that report* as the tool result in the lead's transcript.

State lives in three distinct places, and conflating them is the single most common design error:

- **Lead transcript** — the plan, the task specs it issued, and the compressed reports. This is the only thing that grows across the whole run, so it is the thing you must budget.
- **Worker transcripts** — ephemeral, discarded after the report is produced. They may be enormous; that is the point. A worker that reads 300k tokens and returns 600 is doing its job.
- **Shared durable store** — the filesystem, an object store, a table. This is where anything a worker produced that is *bigger than its report* must go, so a later reader can fetch it without going through the lead's window.

```python
async def orchestrate(task: str) -> str:
    lead = AgentLoop(system=LEAD_PROMPT, tools=[SPAWN, READ_ARTIFACT, FINISH])
    lead.append_user(task)
    while not lead.done:
        step = await lead.step()
        specs = [c for c in step.tool_calls if c.name == "spawn_worker"]
        if specs:
            reports = await asyncio.gather(*[
                run_worker(WorkerSpec(**c.input), run_id=lead.run_id, parent=lead.span_id)
                for c in specs
            ], return_exceptions=True)
            lead.append_tool_results(zip(specs, [render(r) for r in reports]))
    return lead.final_text
```

Note `return_exceptions=True`. A worker failure must arrive at the lead as *text describing the failure*, not as an exception that kills the gather. The lead is the only component that can decide whether losing worker 3 invalidates the run — and it can only decide that if it is told.

**⚠ Trap:** letting a worker's raw tool output flow back into the lead's context "just in case." The instant you do this — and it usually arrives as an innocuous `include_raw=True` flag added during debugging — you have paid the full cost of a sub-agent while receiving none of the context-isolation benefit. This is the number one silent regression in orchestrator-worker systems: the topology looks right on the diagram, the token bill says single-agent-plus-overhead. Assert on it. I put a hard cap in the dispatcher: a worker report over N tokens is truncated and the worker is told to write the rest to a file.

### When does a third level of hierarchy ever pay for itself?

Almost never, and I would make you defend it hard.

The cost of a level is not compute — it is **intent decay**. The user says "find every place we handle refunds inconsistently across our three payment providers, and tell me which one is the outlier." The lead paraphrases that into a sub-task. The mid-level supervisor paraphrases *that* into a leaf task. By the leaf, "which one is the outlier" has usually become "summarize refund handling in Stripe," and the comparative framing — the actual question — has evaporated. You then get three competent summaries and no answer.

The one structural case where I have seen a third level justified is when the *manifest itself* does not fit. Suppose you are running a migration audit over 900 repositories. Each leaf worker handles one repo. The lead cannot hold 900 task specs; even at 80 tokens each that is 72k tokens of pure bookkeeping before any results arrive, and the lead needs its window for synthesis. So you introduce mid-level supervisors that each own 30 repos, hold their own manifest, and return a 300-token rollup. Now the lead holds 30 rollups instead of 900 reports. That is a real capacity argument with arithmetic behind it: 30 × 300 = 9k tokens versus 900 × 400 = 360k tokens, which does not fit in any window you would want to pay for.

The mitigation that makes hierarchy survivable is to **pass the original instruction verbatim down every level, unmodified, alongside the derived subtask.** Every task spec at every depth carries a field like `root_objective` that is copied byte-for-byte from the user's words. The leaf sees both "your job: audit refunds in repo X" and "the overall question this serves: which provider is the outlier in refund handling." That single field recovers most of what hierarchy costs, and it costs you 40 tokens per spawn.

**🗣 Say this in the room:** "I'd push back on three levels unless the middle tier exists because the task manifest itself doesn't fit in the lead's window. And whatever the depth, I propagate the user's original instruction verbatim to every leaf, because otherwise the comparative framing in the request dies at the first paraphrase."

### Explain the network or swarm topology, where any agent can hand off to any other. Where would you actually deploy that?

The mental model is a state machine where the transitions are chosen by a language model at runtime. That is either exactly what you want or a nightmare, depending entirely on how many states there are.

The one place it genuinely fits is **conversational routing with mid-conversation reclassification** — the shape Sierra-style customer-experience agents and support products actually run. The user starts in billing. Four turns in, the billing agent realizes this is a disputed charge, which is a fraud workflow with different tools, a different escalation policy, and different compliance logging. A supervisor could do this, but a supervisor would have to be in the loop on every single turn to notice, and that is an extra model call per turn on a latency-sensitive path. Letting the billing agent itself call `transfer_to_fraud(context_summary)` is cheaper and the routing knowledge lives where the signal is.

What crosses the handoff is the critical design decision, and there are two schools. **Full transcript transfer**: the new agent inherits the entire message history and only the system prompt and tool set change. This preserves everything and is what I default to for support, because the user must never repeat themselves. **Summary transfer**: the departing agent writes a structured handoff and the new agent starts fresh. Cheaper, and necessary once the conversation is long, but it is where users start saying "I already told you my order number."

The hard limits I put on swarm topologies:

- **Bound the graph.** Explicit allowed-transition table, not "any agent may call any agent." Billing → fraud, yes. Fraud → billing, no (once it is fraud, it stays fraud or escalates to human).
- **Cap the hops.** A `handoff_depth` counter in the shared state, incremented on every transfer, hard-failing to a human at 4. Without it you get the ping-pong loop: billing hands to fraud, fraud decides it is actually billing, hands back, and you burn $2 of tokens and 40 seconds while the user watches a spinner.
- **One writer.** Only the currently-active agent may take actions. This sounds obvious until someone implements handoff as "spawn the new agent and let the old one finish its turn."

**⚠ Trap:** the "specialist agent per department" org-chart design. Teams model twelve agents because the company has twelve teams. Conway's law applied to prompts. Twelve nodes means up to 132 directed transitions, and you cannot write evals for 132 paths. If your agents differ only in their system prompt and share a tool set, they are not twelve agents — they are one agent and a routing prompt, and you should build it that way.

### Multi-agent debate keeps showing up in papers. Is it real, and would you put it in a product?

It is real and it is measurable, and I would put it in an offline verification path, not on a user-facing latency budget.

The mechanism: N model instances independently answer, then each sees the others' answers and revises, for R rounds, and you take the converged or majority answer. 📄 **Paper:** Du et al. (2023) — multiagent debate improved factuality and arithmetic/reasoning accuracy over single-pass generation, essentially by giving the model a chance to condition on disagreement it did not generate itself. What it replaced, conceptually, was pure self-consistency (sample K times, majority-vote) — debate adds a *conditioning* step where each agent sees the alternatives rather than just having them tallied.

The reason it works is decorrelation of errors, and that is exactly the reason it usually does not work in the sloppy version people ship. If your three "debaters" are the same model at the same temperature with three different personas, their errors are highly correlated — they share weights. You get three confident agreements on the same hallucination, and now you have paid 3×R the cost to increase your *confidence* in a wrong answer, which is worse than the original problem. Decorrelation has to come from something structural: **different model families**, **different retrieved evidence**, or **different tool access**. Two models from different labs disagreeing about a fact is signal. One model wearing two hats is not.

💰 **Math:** take a 4k-token question with 1k-token answers, three debaters, two rounds, at $3/Mtok input and $15/Mtok output. Round 1: 3 × (4k in + 1k out) = 12k in, 3k out. Round 2 each agent sees the question plus three answers: 3 × (7k in + 1k out) = 21k in, 3k out. Totals 33k in, 6k out → 33 × $0.003 + 6 × $0.015 = $0.099 + $0.090 = **$0.189 per question**, versus $0.027 for a single pass. That is 7× cost and roughly 2× wall-clock (two sequential rounds). At 50k questions/day that is $9,450/day versus $1,350 — you need the accuracy delta to be worth $8,100 a day, which for a support bot it is not and for a pre-merge security review on a payments codebase it plausibly is.

Where I actually use it: as an **LLM-judge ensemble in eval**, where latency is free and disagreement between judges is itself the useful signal — it flags the examples a human should look at.

### You told me multi-agent research costs about 15× a chat. Break that number down for me — where does it actually go?

📐 **Numbers you must know:** the ~4× (agent vs chat) and ~15× (multi-agent vs chat) figures come from Anthropic's engineering write-up of their multi-agent research system. **📅 Volatile:** verify the source and figure before quoting; it is one team's measurement of one architecture, not a constant of nature. What matters in an interview is that you can reconstruct where the multiplier comes from, because that is what tells you which lever to pull.

Take a concrete run: lead plus 5 workers, each worker doing 8 tool-calling steps.

**Per worker.** System prompt + tool schemas: 3k tokens, re-sent every step → 3k × 8 = 24k. Task briefing: 1k, re-sent every step → 8k. Accumulated tool results: search results and page extracts averaging 4k per step, and the transcript grows, so input across steps is roughly 4k × (0+1+2+…+7) = 4k × 28 = 112k. Worker output: 8 × 400 = 3.2k. Worker total ≈ **144k input, 3.2k output**.

**Five workers.** 720k input, 16k output.

**Lead.** System + tools 3k re-sent over ~8 steps = 24k, plus the 5 worker reports (800 tokens each) accumulating across its later steps, call it 20k, plus synthesis output 2k. Lead ≈ **50k input, 4k output**.

**Run total: ~770k input, ~20k output.** At $3/Mtok in and $15/Mtok out: 0.770 × $3 = $2.31 plus 0.020 × $15 = $0.30 → **$2.61 per research run**.

The same question asked as a single chat turn with one search call: maybe 12k input, 1.5k output = $0.036 + $0.023 = **$0.059**. Ratio: 2.61 / 0.059 ≈ **44×** — worse than 15×, and that is the honest shape when you fan out to five deep readers. The 15× figure corresponds to a lighter fan-out.

Now the levers, in the order I pull them:

1. **Prompt caching on the worker system prompt + tool schemas.** That 3k × 8 = 24k per worker is identical bytes every step. At a 90% cache discount that 720k input drops by roughly the 120k of repeated preamble across five workers → saves 0.120 × $3 × 0.9 = **$0.32/run**, ~12%.
2. **Cap worker steps and result size.** The triangular 112k term is the dominant cost and it is quadratic in steps. Cutting a worker from 8 steps to 5 takes 4k × (0+…+4) = 40k instead of 112k — a 64% cut on the biggest line item.
3. **Truncate tool results aggressively before they enter the worker transcript.** Halving 4k to 2k halves that whole term.

**🗣 Say this in the room:** "The multiplier isn't the fan-out, it's the fan-out times the quadratic transcript growth inside each worker. So the first thing I cap is per-worker steps and per-result token size, not the number of workers — cutting a worker from eight steps to five saves more than dropping two workers."

### Why are parallel reads safe and parallel writes not? Give me the rule you'd enforce.

The rule is one line: **fan out on reads, serialize on writes, and if two workers must write, they write to disjoint paths that a single reconciler merges.**

The reason reads are safe is that they are commutative and idempotent in a way you already trust. Two workers grepping the same repo, two workers hitting the same search API, two workers reading two different Postgres tables — the outcome does not depend on the order, and re-running one changes nothing. The only cost of a duplicated read is money.

Writes break in four distinct ways, and I want you to be able to name them separately because the mitigations differ:

**Conflict.** Two workers edit the same file. Last-write-wins silently discards one worker's entire contribution — and unlike a database, nothing raises. The lead receives two reports both saying "done," and the artifact contains one of the two changes. There is no error anywhere in the trace.

**Ordering.** Worker A creates the migration, worker B writes the code that depends on it. In a fan-out there is no happens-before. You will get a run where B finishes first, sees no migration, and *invents a plausible one inline* — because that is what a helpful model does when the world does not match its brief. Now you have two migrations.

**Duplicated work.** Three workers all decide the auth module is the interesting part and all rewrite it. You paid 3× and got one usable result plus two conflicts. This is not a bug in any single worker; each was locally correct.

**Untraceable blame.** After a concurrent write, the artifact is a merge of contributions from N stochastic processes. When it is wrong, "which worker wrote this line" is not answerable from the artifact — only from the trace, and only if you instrumented it. In a single agent, causality is the transcript order. In a concurrent write, causality is gone.

The enforcement mechanisms I actually put in code, in order of preference:

- **Disjoint namespaces by construction.** Worker *i* may only write `runs/{run_id}/workers/{i}/**`. Enforce it in the tool implementation, not the prompt — a path prefix check in `write_file` that raises. Prompts are advisory; the dispatcher is not.
- **A single writer agent.** Workers return proposed patches as data; one final agent (or, better, deterministic code) applies them in a defined order. This is the pattern that makes overnight code-modification runs survivable.
- **Optimistic concurrency where a shared artifact is unavoidable.** Read-with-version, write-if-version-matches, and on conflict hand the *conflict itself* back to the model as a tool error so it can re-read and re-reason. You know this pattern; the novelty is only that the retry costs $0.04 and 3 seconds.

**⚠ Trap:** believing git is your concurrency control. Two sub-agents running `git commit` in the same working tree do not conflict at the git level — they interleave into one index and produce commits containing each other's partial work. Git protects you across *branches and worktrees*, which means giving each writer worker its own `git worktree` and merging deliberately. That is a real design, and it costs disk, not correctness.

### Two sub-agents modified the same file in an overnight refactor run. Walk me through what actually went wrong and how you'd have prevented it.

Let me make it concrete, because the failure is more interesting than "they raced."

The run: 40 workers, each assigned one service directory, tasked with migrating from a deprecated logging helper to structured logging. Worker 12 owns `services/billing/`. Worker 27 owns `services/shared/` — and `shared/logging.py` is imported by billing. Worker 27 changes the helper's signature from `log(msg, **kw)` to `log(event, fields)`. Worker 12, reading the *old* signature at the start of its run, rewrites 60 call sites against `log(msg, **kw)`.

Both report success. Both are individually correct. The build breaks, and here is the part that costs you a night: because worker 12's report says "migrated 60 call sites in billing, tests pass," and it *did* pass tests — against the pre-27 state it had checked out at spawn time — the lead has no signal at all. It synthesizes "all 40 services migrated successfully," commits, and the morning CI run is red with 60 errors that no single agent's transcript explains.

**🔍 Failure taxonomy — the diagnosis procedure for concurrent-write damage:**

1. **Is the artifact's final state a superset of all reported changes?** Diff the artifact against each worker's claimed change list. If a claimed change is absent, you had a lost write (conflict). If all are present but the whole is broken, you had an ordering or interface-contract failure, which is this case.
2. **Do any two workers' file sets intersect?** If yes, the topology was wrong regardless of outcome — you got lucky on the runs that passed.
3. **Did any worker's read of a shared file predate another worker's write to it?** This requires per-tool-call timestamps in the trace. If you cannot answer this question from your logs, that is the actual finding of the postmortem.
4. **Did a worker "helpfully" reconcile?** Grep worker transcripts for the model inventing a missing dependency. Models do not fail loudly on an inconsistent world; they patch it locally and continue.

**The prevention, in order of how much I trust it.** First, **dependency-aware partitioning**: compute the import graph before the run and put mutually-dependent modules in the same worker's scope. This is deterministic code you write once, and it eliminates the class rather than mitigating it. Second, **interface freeze**: shared contracts are changed in a serial phase 0 by exactly one agent, everything else runs in phase 1 against a frozen interface, and phase 1 workers are given the *new* signature in their brief. Third, **per-worker git worktrees plus a merge phase** where conflicts surface as real merge conflicts rather than silent overwrites. Fourth — and this is the cheap one everyone skips — **run the full test suite once, after the merge, as a single deterministic step**, and treat any worker's self-reported "tests pass" as unverified until then.

💰 **Math on why this matters:** that run was 40 workers × ~$0.90 = $36 in tokens plus ~50 minutes of wall clock. The re-run after fixing partitioning is another $36. Cheap. What was not cheap was the engineer-morning spent bisecting a 40-way concurrent change, and the fact that for two weeks afterward nobody trusted the tool. The cost of a multi-agent failure is rarely the tokens; it is the credibility.

### Three of your parallel workers independently investigated the same lead. How do you stop that without serializing the run?

You cannot prevent it with prompting, because each worker's decision is locally rational and they cannot see each other. You prevent it with **partitioning discipline at spawn time** and **claim-based coordination through shared state** — and you accept a residual duplication rate rather than chasing zero.

**Partition at spawn.** The lead's task specs must be *disjoint by construction*, and the way you get that is to make the lead emit an explicit partition and validate it in code before spawning. Not "investigate the payments issues" ×3, but "worker 1: Stripe webhook handling only; worker 2: Adyen only; worker 3: the shared retry layer only — do not investigate the others, another worker owns them." That last clause matters more than it looks; without an explicit exclusion, a worker that finds a cross-cutting clue follows it, correctly and expensively.

I validate the partition mechanically where I can. If the units are files, assert the file sets are disjoint. If they are search queries, assert Jaccard similarity below a threshold. If the lead emits overlapping specs, the dispatcher rejects the spawn batch and returns "your task specs overlap on X; re-partition" as a tool error. Letting the model fix its own malformed plan is far cheaper than letting three workers discover the overlap at $0.90 each.

**Claim through shared state.** For the cases where you cannot partition up front — exploratory research where the interesting leads are discovered, not enumerated — give workers a `claim(topic) -> bool` tool backed by Redis `SET NX`. A worker claims before doing expensive work; if the claim fails it is told who holds it and moves on. This is a plain distributed lock and you have built a hundred of them; the only new thing is that the "topic" is a fuzzy string, so you need normalization (lowercase, strip, maybe an embedding-similarity check against existing claims above 0.9) or the claims never collide.

**Deduplicate at the merge, not the fork.** Some duplication is fine and cheaper to absorb than to prevent. If two workers independently reach the same conclusion, that is *corroboration*, and I would rather my synthesis step notice "two independent investigations converged" than have suppressed one of them. What I will not tolerate is duplication that is invisible — so the lead's synthesis prompt must be told which workers were told to look where, so it can distinguish "two workers agreed" from "one worker said it twice."

**⚠ Trap:** trying to fix duplication with a shared scratchpad that all workers read *and* write during the run. It reads as elegant on a whiteboard — "they coordinate through shared memory!" — and in practice you have built a system where every worker's context is polluted by every other worker's intermediate noise, which is precisely the thing sub-agents existed to prevent. If workers need to read each other's findings, you wanted a sequential pipeline, not a fan-out. Say that out loud in the design review.

**🗣 Say this in the room:** "I make the lead emit an explicit disjoint partition and I validate disjointness in the dispatcher before any worker spawns. For exploratory work where you can't partition up front, workers take a Redis `SET NX` claim on a normalized topic before doing expensive work. And I let some duplication through on purpose — convergence between two independently-briefed workers is evidence, as long as the synthesizer knows they were independent."

### A sub-agent is about to start. What must you tell it, and what happens if you leave each piece out?

This is the question I ask to find out whether someone has actually run a multi-agent system, because the list is learned by failure and every item on it corresponds to a specific bad night.

A worker starts with an empty context. It has none of the conversation, none of the lead's reasoning, none of the user's tone, none of the ten things the user clarified in turn three. Everything it knows, you wrote. The brief has to carry:

**The root objective, verbatim.** The user's own words, unparaphrased. Without it you get locally-correct work that answers the wrong framing. This is the single highest-value field and it costs ~50 tokens.

**The specific subtask, with scope boundaries stated as exclusions.** "Investigate X. Do not investigate Y or Z; other workers own those." Omit the exclusions and you get the duplication problem.

**The output contract.** Exact shape, exact length budget, exact required fields. "Return at most 600 tokens as: FINDINGS (bullets, each with a citation), CONFIDENCE (high/med/low), GAPS (what you could not determine)." Omit this and workers return 4k-token essays, and your lead's context dies from the thing you built workers to prevent.

**The budget.** Max steps, max tokens, max wall-clock, stated *in the prompt* as well as enforced in the dispatcher. Telling the model its budget measurably changes its behaviour — it front-loads the high-value searches instead of getting cut off mid-exploration. Enforce it in code too; the prompt is a hint, the dispatcher is the law.

**Resolved context the worker cannot re-derive.** Today's date, the tenant/customer identity, the schema version, the branch name, the fact that "the migration" refers to the one merged on Tuesday. Omit these and the worker guesses, plausibly, and you will not notice.

**What has already been established.** Not the whole transcript — the *conclusions*. "We have already confirmed the issue is not in the CDN layer." Omit it and workers re-investigate settled ground.

**The tool subset and its constraints.** Workers should get the minimum tools for their task, both for permission reasons and because a smaller catalog measurably improves selection accuracy.

```python
class WorkerSpec(BaseModel):
    root_objective: str          # user's words, verbatim, never paraphrased
    subtask: str
    out_of_scope: list[str]      # what other workers own
    established_facts: list[str] # conclusions, not transcript
    resolved_context: dict[str, str]  # date, tenant, branch, schema_version
    output_contract: str
    budget: Budget               # max_steps, max_tokens, deadline_s
    tools: list[str]
```

The reason I make this a Pydantic model rather than a prompt template is that it turns "did the lead brief the worker properly" into a validation error at spawn time instead of a quality regression discovered in eval three weeks later. `root_objective` is required and I assert it is a substring of the actual user message — that assertion has caught real bugs where a lead started paraphrasing under context pressure.

**⚠ Trap:** the assumption that the lead will naturally include what the worker needs because the lead "knows" it. The lead is a language model writing a paragraph; it optimizes for a plausible-looking task description, not for informational completeness under an unknown recipient's ignorance. Structure the spec and validate it, or you are relying on a stochastic process to do requirements engineering.
### What is measurably lost at a handoff? Don't tell me "information" — quantify it.

Three things are lost, and each one has a measurement you can actually run.

**Compression loss.** A worker consumes 150k tokens and returns 600. That is a 250:1 compression ratio, and by construction the report cannot contain the evidence for its claims — only pointers to it. The measurement: take a set of questions whose answers require a detail from the worker's raw material, run the full orchestrator, and score answer accuracy; then run the same questions with the worker's raw material dumped directly into a long-context single agent. The gap is your compression loss. In my experience the gap is small for "what did you find" questions and large for "why do you believe that" and "what did you *not* find" questions. Negative findings are the first casualty of summarization — a worker that searched five sources and found nothing writes "no evidence found," which is indistinguishable in the lead's context from "did not look."

**Intent drift.** The subtask the worker executes is a paraphrase of the lead's paraphrase of the user. The measurement I actually use: an LLM judge scores `subtask` against `root_objective` on "would completing this subtask serve this objective?" across a sample of spawns, and I alert when the pass rate drops. It sounds soft; it is the fastest detector I have found for a lead agent that has started degrading under context pressure, because intent drift shows up in the spawns before it shows up in the final answers.

**Uncertainty flattening.** This is the expensive one. A worker internally weighed three interpretations, picked one, and wrote a declarative sentence. The lead now treats a coin-flip as a fact and builds on it. The measurement: force `confidence` and `alternatives_considered` fields in the report schema and check how often they are populated non-trivially. If every worker returns `confidence: high`, the field is decoration and your system is laundering guesses into assertions.

💰 **Math on the round-trip you pay for this loss:** the handoff is not free even ignoring quality. Serializing a spec (400 tokens) and deserializing a report (600 tokens) costs nothing directly, but the *worker* pays to re-read its brief every step: 400 tokens × 8 steps = 3.2k tokens of pure re-briefing per worker, and 5 workers is 16k tokens = $0.048 per run at $3/Mtok. Trivial. The real cost is that when the lead needs a detail the report dropped, it must re-spawn — a second $0.52 worker run and another 45 seconds of wall clock, for information the system already had and threw away.

**⚠ Trap:** believing you can fix compression loss by making the report longer. Going from 600 to 3,000 tokens per report multiplies the lead's context growth by 5× and buys you the *middle* of the distribution — the details the worker thought were second-most important, which are usually not the ones you needed. The fix is not a bigger pipe, it is **addressability**: the report stays 600 tokens and contains stable references (file paths, span IDs, URLs with anchors) that the lead can dereference on demand with a cheap read tool.

### Design the handoff schema. What does the lead send down, and what comes back up?

Two schemas, and the discipline is that both are typed, versioned, and validated in code — not in prose. The moment a handoff is "the lead writes a paragraph," you have an untyped RPC boundary and you will spend your quarters debugging it.

**Down: the task spec.** I covered the fields; the design principles are what matter. `root_objective` is copied byte-for-byte and I assert it against the actual user turn. Scope is expressed as inclusion *and* exclusion, because a model given only an inclusion will follow interesting threads outward. The output contract is stated as a template the worker fills in, not as a description of a template, because models comply with forms far more reliably than with instructions about forms. And the budget is stated numerically so the worker can plan against it.

**Up: the report.**

```python
class Finding(BaseModel):
    claim: str
    evidence_ref: str          # file path + line range, or URL + anchor, or artifact id
    confidence: Literal["high", "medium", "low"]

class WorkerReport(BaseModel):
    spec_id: str
    status: Literal["completed", "partial", "failed", "budget_exhausted"]
    findings: list[Finding]                 # capped, e.g. max_items=10
    negative_findings: list[str] = []       # "searched X, Y; found nothing about Z"
    open_questions: list[str] = []
    artifacts: list[str] = []               # paths written, not contents
    usage: Usage                            # input/output tokens, tool calls, wall_clock_s
```

Four of these fields exist because of specific production failures. `negative_findings` exists because a lead cannot distinguish "nothing there" from "didn't look," and without it your synthesis quietly asserts absence. `evidence_ref` exists because citations detach: a claim without a dereferenceable pointer becomes unverifiable the instant it enters the lead's context, and the lead will happily restate it in the final answer with a citation it invented. `status` distinguishes `partial` from `completed`, because a budget-exhausted worker returns real findings that must be labelled as incomplete or the lead treats a truncated search as an exhaustive one. `usage` exists because cost attribution is impossible to retrofit.

Rendering matters too. Do not hand the lead raw JSON; hand it a compact human-readable block, because models parse prose-with-structure more reliably than deeply nested JSON, and the JSON keys cost tokens on every subsequent turn. I keep the validated object for the trace and render a flattened text form into the transcript.

**⚠ Trap:** letting the worker return free text "because the model writes better prose that way." It does — and then the lead's synthesis inherits the worker's rhetorical confidence rather than its evidence. Structured returns are not about parsing convenience; they are about forcing the worker to separate claim from evidence from confidence, which is a *reasoning* intervention, not a serialization one.

### The user asked one specific question, and after two levels of summarization the final answer answers a different question. Debug it.

This is the telephone game, and it is the most common quality failure in orchestrator-worker systems. The debugging procedure is mechanical.

**Step 1 — read the leaf task specs, not the final answer.** Pull every `spawn_worker` input from the trace and read the `subtask` fields against the user's original message. In nine cases out of ten the drift is fully visible here: the user asked "which of our three providers handles refunds inconsistently," and the specs say "summarize refund handling in Stripe / in Adyen / in Braintree." Nobody was ever asked to compare. The synthesis step then had three summaries and no comparative evidence, so it produced a comparison it inferred from summaries, which is exactly as reliable as it sounds.

**Step 2 — check whether `root_objective` was propagated verbatim.** If the field is absent from your spec schema, that is the bug and the fix is one field. If it is present but the workers ignored it, the fix is in the worker's system prompt: the objective must be positioned as a constraint on the *output*, not as background. "Your findings will be used to answer: {root_objective}. Report anything relevant to that question even if outside your assigned scope, flagged as `cross_scope`."

**Step 3 — check whether the decomposition was answerable.** Some questions do not decompose. "Which is the outlier" is inherently comparative; partitioning by provider destroys the comparison. The right decomposition for a comparative question is either (a) one worker per *dimension* rather than per subject — "compare retry behaviour across all three providers" — or (b) fan out to gather, then do the comparison in a single agent that reads all three artifacts. This is a design bug, not a prompt bug, and no amount of prompt tuning fixes it.

**Step 4 — check the synthesis prompt's inputs.** Does the synthesizer see the original user message, or only the reports? I have reviewed systems where the final synthesis prompt contained the plan and the reports but *not the user's question*, on the theory that the plan encoded it. It did not.

**🗣 Say this in the room:** "The first place I look isn't the answer, it's the task specs the lead emitted — drift is almost always visible there, and it's usually because the original question was comparative and the decomposition was by subject, which destroys the comparison. Fixing that is a decomposition-shape change, not a prompt tweak."

**⚠ Trap:** patching this with a "verification agent" that checks whether the answer addresses the question. It will catch some cases and it costs a full extra round-trip, but it cannot recover evidence that was never gathered. Verification at the end cannot fix decomposition at the start. Add the check if you like, but fix the partition.

### Explain the filesystem-as-shared-memory pattern. Why is writing a file better than returning the data?

The one-line intuition: **the filesystem gives you addressability without occupancy.** A file path is a 40-token pointer to an unbounded amount of content, and the lead pays for the pointer, not the content, until the moment it actually needs the content. Your context window has no such indirection — everything in it is resident, and everything resident is re-read and re-paid on every subsequent turn.

You already have the right intuition for this from a different domain: you would never pass a 2GB blob through a Kafka message, you would pass an S3 key. Same reasoning, different scarce resource. Except the constraint here is sharper, because context is not merely expensive, it is *quality-degrading* — a lead with 180k tokens of accumulated worker output reasons measurably worse than a lead with 20k tokens of pointers, independent of cost.

The concrete pattern in an orchestrator-worker run:

- Every run gets a directory: `runs/{run_id}/`.
- Each worker writes its full output to `runs/{run_id}/workers/{i}/report.md` plus any artifacts (extracted tables, downloaded pages, generated code) alongside it.
- The worker's *return value* to the lead is the structured 600-token report plus the paths.
- The lead has a `read_artifact(path, offset, limit)` tool and pulls content only when synthesis actually needs it.
- The synthesis step may read 3 of 5 artifacts fully and never touch the others.

Second-order benefits that are easy to miss. **Durability**: if the process dies, the artifacts survive; a resumed run re-reads instead of re-computing. **Auditability**: a human can open `runs/{run_id}/` and read exactly what each worker produced, which is worth more in an incident than any tracing UI. **Cross-run reuse**: an artifact from last night's run is still a file. **Deterministic post-processing**: you can run a script over 200 worker reports, which you cannot do over 200 context windows.

**⚠ Trap:** giving the lead a `list_files` tool and letting it browse. It will list the directory, read everything, and you are back to full occupancy with extra steps. The lead should receive paths from reports it already has; browsing is for humans and for recovery, and I gate it behind an explicit "resuming a crashed run" mode.

**Second trap:** the filesystem is shared mutable state, which means everything from the concurrent-writes discussion applies to it. Per-worker subdirectories, enforced by a path-prefix check inside the `write_file` tool implementation. Not in the prompt. In the tool.

💰 **Math:** five workers each producing a 25k-token artifact. Streamed into the lead's context: 125k tokens resident, re-read on every one of the lead's remaining ~6 turns = 750k input tokens = **$2.25** at $3/Mtok, plus measurable quality degradation. Written to disk with 600-token reports: 3k resident, re-read 6 times = 18k = $0.054, plus perhaps two on-demand reads of 25k each that are then resident for the final 2 turns = 100k = $0.30. Total **$0.35**, an 84% reduction, and the lead's working context stayed under 30k.

### Isn't the filesystem just a slower pipe with extra steps? Defend it against "the sub-agent should just return the data."

I would defend it on three grounds, and I would concede one point.

**First, occupancy versus transfer.** Returning the data means the data is *in the lead's context forever*, not just at the moment of transfer. This is the crux and it is what people miss when they call it a slow pipe. A pipe delivers and the bytes are consumed. A context window delivers and the bytes stay, and are re-uploaded to the model on every subsequent turn for the rest of the run. The filesystem converts a permanent cost into a one-time optional cost.

**Second, selective and partial reads.** `read_artifact(path, offset=0, limit=2000)` lets the lead sample a 200k-token document. Returning the data offers no such granularity — it is all or nothing, decided by the worker, before anyone knows what the lead will need.

**Third, the artifact outlives the context.** Compaction will eventually eat the lead's transcript. Everything the lead "knows" from returned data is deleted at the compaction boundary, and post-compaction the lead confidently proceeds on a summary of a summary. Everything the lead knows as a *path* survives compaction, because a path is 40 tokens and survives any summarizer, and the content is re-derivable. This is the argument I find most convincing and the one candidates almost never make: **the filesystem is the only memory in an agentic system that is immune to context compaction.**

**The concession:** it costs latency and it costs a tool round-trip. If the worker's output is genuinely small — a number, a boolean, a one-line classification — writing it to a file is silly ceremony. My threshold in review is roughly **2k tokens**: below that, return it; above that, write it and return a pointer plus a summary. And for a low-latency user-facing path where the lead needs the content anyway, the extra read step costs a full model round-trip (400–900ms of TTFT plus generation) and I would just return it.

**🗣 Say this in the room:** "A returned value occupies the lead's context permanently and dies at the next compaction. A file path occupies forty tokens, survives compaction, and can be read partially and on demand. Below about two thousand tokens I just return the value; above it, the pointer wins on cost, on quality, and on the fact that it's still there after the transcript gets summarized."

### Walk me through the initializer-agent pattern. Why does a run start by running a script and making a commit?

The mental model: **you are building a known-good checkpoint that every downstream agent can be diffed against, before any stochastic process touches the workspace.** Without it, when the run goes wrong you cannot tell which changes came from the agents and which were already there, and you cannot roll back cleanly.

The initializer runs before any task-doing agent and does four things, all deterministic where possible:

**1. `init.sh` — establish and verify the environment.** Install dependencies, start required services, run the test suite once, record what passed. This is deterministic code, not an agent, wherever you can manage it. The output is a recorded baseline: "342 tests pass, 3 skipped, 0 fail; build succeeds in 47s." Every later claim of "tests pass" is now meaningful because you have the *before*. Without a baseline, a worker reporting "all tests pass" is unfalsifiable — maybe those three failures were already there.

Where an agent is genuinely useful here is the messy part of environment setup: the repo has no README, the build breaks on a missing system package, the Python version is wrong. That is exactly the kind of unstructured recovery a model is good at and a script is bad at. So the honest pattern is `init.sh` for the known steps, with an initializer *agent* invoked when `init.sh` exits non-zero, whose only job is to make it exit zero and then append what it did to the script.

**2. The initial git commit.** `git add -A && git commit -m "checkpoint: pre-run baseline {run_id}"` on a dedicated branch. Now every agent's work is a diff against a named commit. You can `git diff baseline..HEAD` to see the total change, `git log` to see per-agent commits if you make each worker commit, and `git reset --hard baseline` to abandon a bad run in one command. This is the cheapest insurance in the entire pattern and it takes 200 milliseconds.

**3. The progress log file.** Create `runs/{run_id}/PROGRESS.md` with the plan, the task list, and a status per task. Append-only from then on. This is the resumability substrate.

**4. The context pack.** Generate the things every downstream agent will need and would otherwise each derive independently: a repo map, the dependency graph, the list of test commands, the schema dump. Doing it once and writing it to `runs/{run_id}/context/` means 40 workers read a file instead of 40 workers each running `find` and `grep` for six steps. 💰 At 6 exploratory steps × ~3k tokens of tool output per worker × 40 workers = 720k tokens = **$2.16** saved for one deterministic script that runs in 4 seconds.

**⚠ Trap:** letting the initializer be an agent that does all four steps "intelligently." Every deterministic step you hand to a model is a step that can fail nondeterministically at 3am, and the initializer failing is the worst possible failure because everything downstream inherits a broken baseline. My rule: the initializer is a script; an agent is the *fallback* when the script fails, and its output is a patch to the script so the failure is fixed permanently rather than re-diagnosed nightly.

### Design the progress file. What has to be in it for a crashed run to resume correctly?

The mental model is a write-ahead log, and the property you need is the one you already enforce on WALs: **the file must be sufficient to reconstruct intent and completion state without any process memory.** If resuming requires knowing something that only lived in the dead process's context window, the design is wrong.

What goes in, in order of how badly you miss it:

- **`run_id`, `created_at`, `baseline_commit`.** Identity and the rollback point.
- **The original user request, verbatim.** A resumed run starts a fresh lead with an empty context. The only way it knows what it is doing is this field.
- **The plan** — the ordered or partially-ordered task list, with stable IDs. Regenerating the plan on resume is wrong: a second lead will produce a *different* plan, and now your completed tasks do not correspond to any entry in the new plan.
- **Per-task status**: `pending | in_progress | done | failed | skipped`, plus `attempts`, `worker_id`, `artifact_paths`, `started_at`, `finished_at`, and a one-line `result_summary`.
- **Established facts / decisions.** The conclusions the run has reached so far. This is what replaces the dead lead's context.
- **Cumulative usage**: tokens and dollars spent so far, so the resumed run inherits the remaining budget rather than a fresh one. This is the field people forget, and it is how a crashed-and-resumed run costs 2.5× its cap.

Format: I use a JSON or JSONL sidecar as the source of truth (`progress.json`) and render a Markdown view for humans. Do not make Markdown the parseable source of truth — you will end up regex-parsing checkboxes written by a model, and it will one day write `[X]` instead of `[x]`.

Writing discipline matters more than schema. **Update at task boundaries, atomically, before and after.** Mark `in_progress` with a timestamp *before* spawning, mark `done` *after* the artifact is durably written. Write via temp-file-plus-`os.replace` so a crash mid-write cannot corrupt it — you know this pattern; the only novelty is that the writer is an agent loop that may be killed by an OOM at any instruction.

The `in_progress`-with-a-timestamp state is what makes resume correct. On restart you scan for tasks stuck in `in_progress`: those are the ones that were running when the process died. Whether you re-run them depends on whether the task is idempotent — a research read, yes, re-run it; a "post the summary to Slack" action, no, that needs a durable idempotency key checked against the side-effect store. This is exactly the at-least-once semantics you already reason about in Celery, and the same conclusion applies: the queue can only give you at-least-once, so the *action* must carry the deduplication.

**⚠ Trap:** letting the agent be the sole writer of the progress file via a `write_file` tool. It will forget under context pressure, it will rewrite the whole file and drop entries, and it will reformat it. The dispatcher writes progress at task boundaries as ordinary Python; the agent may *append notes*, never own the state machine. State machines are code.

### Your 120-task overnight run crashed at task 47. Walk me through what happens next.

Concretely, step by step, because "we resume from the progress file" is not an answer.

**On restart, the supervisor process — not an agent — reads `progress.json` and classifies.** Tasks 1–46 are `done` with artifact paths; verify each path exists and is non-empty, because a `done` marker written before an incomplete flush is a real failure mode. Any `done` task whose artifact is missing gets demoted to `pending`. Task 47 is `in_progress` — this is the crash point. Tasks 48–120 are `pending`.

**Decide about task 47 on idempotency grounds.** If it is a read/analysis task, re-run it; the cost is one worker. If it took an external action, check the side-effect store for its idempotency key before re-running. If you have no such store, this is the moment you learn you needed one, and the honest answer in the room is: "I would mark it `needs_human` and not guess."

**Reconstitute the lead.** New process, empty context. It is briefed with: the original request verbatim, the plan, the established-facts list, the completed-task summaries (one line each — 46 lines × 20 tokens = ~900 tokens, which is why the schema caps `result_summary`), and the remaining budget. It is explicitly told it is resuming, because otherwise it re-plans. I make that a literal instruction: "You are resuming run X at task 47 of 120. The plan is fixed. Do not re-plan; execute remaining tasks."

**Inherit the budget, don't reset it.** If the cap was $80 and `progress.json` says $31.20 spent, the resumed run gets $48.80. Skipping this is how a crash loop turns a $80 cap into a $400 bill: crash at $31, resume with a fresh $80, crash again at $30, resume again.

**Bound the resume attempts.** `resume_count` in the progress file, hard stop at 3, then page a human. A run that crashes three times is not going to succeed on the fourth; something structural is wrong and continuing just spends money.

**🔍 Failure taxonomy — why overnight runs die, and what each demands:**

| Symptom | Likely cause | Fix |
|---|---|---|
| Died at the same task index every time | Deterministic failure on a specific input (a 40MB file, a binary, a permissions error) | Poison-input isolation: quarantine that task, continue the rest |
| Died at wildly varying points, memory climbing | Unbounded transcript growth in the lead | Cap lead context; move accumulated state to the progress file |
| Died shortly after a burst of parallelism | Provider rate limit → unhandled 429, or local OOM from N concurrent workers | Bounded concurrency semaphore + retry with jitter on 429 |
| Ran to "completion" but artifacts are empty | Workers hit budget exhaustion and reported `completed` | Distinguish `completed` from `budget_exhausted` in the report status and propagate it |
| Never died, never finished | Lead in a re-plan loop, or a worker in a tool-retry loop | Wall-clock deadline on the whole run, enforced by the supervisor, not the agent |

**🗣 Say this in the room:** "Resume is a supervisor-process concern, not an agent concern. The supervisor reads the progress file, verifies artifacts actually exist for anything marked done, demotes liars, decides about the in-flight task on idempotency grounds, and re-briefs a fresh lead with the fixed plan and the *remaining* budget. The two things people get wrong are re-planning on resume and resetting the budget."

### Design the scheduler for an overnight run that spawns two hundred sub-agents.

The mental model to lead with: **this is a job queue with a worker pool, and the fact that the workers are language models changes exactly three things** — the per-job cost is variable and unbounded, the failure mode is "plausible garbage" rather than an exception, and the upstream dependency has a token-rate limit rather than a connection limit. Everything else is the Celery/Kafka design you have built many times, and I would say so out loud rather than pretending it is novel.

**The architecture.** A durable task table (Postgres is correct here; you need transactional status transitions and you are not doing 100k/sec). A supervisor process that claims tasks with `SELECT ... FOR UPDATE SKIP LOCKED`, a bounded concurrency semaphore, and an asyncio task per running worker. Artifacts to the filesystem or object store. Trace spans to your observability backend. If you already run Celery, use it — the novelty budget should go into the agent logic, not into rewriting a queue.

**Concurrency is bounded by the provider, not by your CPU.** This is the one sizing decision people get wrong. Your limit is tokens-per-minute, not requests. If your tier gives 2M input TPM and a worker consumes ~150k input tokens over its lifetime of ~90 seconds, that is 100k tokens/minute per worker, so **20 concurrent workers saturates you**. Running 60 gets you 429s, retries, and an effective throughput *lower* than 20 because retried requests re-send their full context. Compute the number, do not guess it, and expose it as config because it changes when your tier changes.

**Scheduling policy.** Ready tasks by dependency, then priority, then FIFO. Dependencies matter here specifically because of the shared-write problem — phase 0 (interface changes) must complete before phase 1 (call-site updates). I encode phases as a simple integer and the scheduler will not start phase *n+1* until phase *n* has zero non-terminal tasks.

**Failure isolation.** Every worker runs behind a timeout, a step cap, and a token cap, all enforced by the supervisor. A worker failure updates one row and never propagates: `return_exceptions=True` at the gather, exception recorded as task state. Retry with exponential backoff and jitter, capped at 2 attempts for model-quality failures (a third attempt of a stochastic process that failed twice is usually money on fire) and more for transport errors, which are a different class and should be retried inside the client.

**Circuit breakers, plural.** Global: if the failure rate over the last 20 completed tasks exceeds 40%, halt the run and page. Something changed — a model deprecation, an expired credential, a schema drift — and burning through the remaining 150 tasks will produce 150 failures at full price. Per-task: 2 strikes and quarantine. Per-cost: covered next.

**Observability.** One trace per run, one span per task, per-span token and cost attribution, and a live-updating progress file. At 200 tasks the thing you need at 3am is a single query answering "how many done, how many failed, how much spent, what is the current failure mode" — build that view before you build anything clever.

**⚠ Trap:** using `asyncio.gather` over 200 coroutines and calling that a scheduler. No backpressure, no partial-failure semantics, no persistence, and one unhandled exception takes the batch. It works at 5 and dies at 200, which means it will pass your test and fail your first real run.

### Where exactly do you enforce cost caps on a fan-out run? Give me the levels.

Four levels, and you need all four because each catches a failure the others cannot.

**1. Per-model-call.** `max_tokens` on every request. This is the only cap that is enforced by the provider and cannot be bypassed by a bug in your loop. Set it to what the output contract actually needs — if reports are capped at 600 tokens, `max_tokens=800`, not 8192. This single line prevents the runaway-generation failure where a model enters a repetition loop and emits 100k tokens of the same paragraph. 💰 That failure at $15/Mtok output is $1.50 for one call; across 200 workers it is $300, and I have seen exactly this bill.

**2. Per-worker.** A `Budget(max_steps, max_tokens, deadline_s)` checked in the worker's loop before every model call, with accumulated usage from `response.usage`. On exhaustion the worker does not raise — it is prompted to produce its best report *now* and returns with `status="budget_exhausted"`. This matters: a killed worker returns nothing and you paid for everything; a gracefully-terminated worker returns partial findings and you paid the same. The difference is whether the money bought anything.

**3. Per-run.** The supervisor accumulates spend across all workers and the lead, checked before each spawn. On breach it stops spawning, lets in-flight workers finish, and forces synthesis from whatever exists. Note the ordering: you check *before* spawning, not after, and you must reserve headroom for the synthesis call — if the run cap is $80 and you spend $80 on workers, you cannot afford the synthesis and the entire run produces nothing. I reserve 10%.

**4. Per-tenant / global.** A rolling window counter in Redis, keyed by tenant and by day, checked at run admission. This is the one that saves you from a customer or a cron misconfiguration launching forty concurrent runs. Same token-bucket you have built for API rate limiting, denominated in dollars instead of requests.

```python
class BudgetGuard:
    def __init__(self, cap_usd: float, reserve: float = 0.10):
        self.cap, self.reserve, self.spent = cap_usd, reserve, 0.0
    def charge(self, usage: Usage) -> None:
        self.spent += usage.input_tokens * IN_RATE + usage.output_tokens * OUT_RATE
    def may_spawn(self, est_usd: float) -> bool:
        return self.spent + est_usd <= self.cap * (1 - self.reserve)
    def must_finalize(self) -> bool:
        return self.spent >= self.cap * (1 - self.reserve)
```

**⚠ Trap:** enforcing the cap only in the prompt. "You have a budget of $5, spend it wisely" is a hint that improves planning and provides zero protection. Models cannot count their own tokens, they cannot see the price sheet, and under pressure they will spend anyway. I tell the model its budget *and* enforce it in the dispatcher, and if I had to pick one I would pick the dispatcher every time.

**Second trap:** a cap with no kill switch. You need a way to halt a running batch from outside the process — a flag in Redis or a row in the task table that the supervisor checks between tasks. At 3am the person paged is not going to find the right PID.

### One sub-agent in a batch of two hundred gets stuck in a tool-retry loop. What contains it, and how do you detect it early?

Three containment layers, and then the detection, which is the more interesting half.

**Containment.** A wall-clock deadline per worker enforced with `asyncio.wait_for` — this is the backstop that catches everything including the failures you did not anticipate, and it is the one I would keep if I could only have one. A step cap that terminates the loop regardless of what the model wants. A token cap. All three enforced by the supervisor, because a loop that has gone pathological is not going to voluntarily obey its own budget check if the pathology is in the loop.

**Detection is the part people skip.** A worker stuck in a retry loop does not look failed — it looks busy. It is making successful API calls, paying full price, producing tool calls, and returning results. Nothing errors. Your dashboard is green and your bill is not. The signals that actually catch it:

**Repeated identical tool calls.** Hash `(tool_name, canonical_json(args))` and keep a per-worker counter. Three identical calls is near-certainly a loop; two is sometimes legitimate (a retry after a transient error). On the third, do not just terminate — inject a tool result that says "you have called this tool with these exact arguments three times and received the same result; it will not change. Choose a different approach or report what you have." Roughly 40% of the time in my experience the model breaks out and completes usefully, which is a much better outcome than a kill.

**Cost velocity.** Tokens per second per worker, compared against the batch median. A worker at 3× the median rate is either doing something legitimately expensive or is looping; either way it deserves a look. This is a cheap anomaly detector and it catches loops that are not literally identical — the model varying one argument each time, which the hash check misses.

**Progress-free steps.** Define progress concretely: a new artifact written, a new distinct tool called, a new URL fetched, a finding appended. N consecutive steps with none of those is a stall. This catches the subtler pathology where the model is exploring but not converging.

💰 **Math on why detection beats containment alone:** a worker with a 15-minute deadline stuck in a loop at 8k input + 500 output tokens per step, one step every 5 seconds, runs 180 steps: 1.44M input + 90k output = 1.44 × $3 + 0.09 × $15 = $4.32 + $1.35 = **$5.67 burned by one worker** that produced nothing. Deadline alone caps it there. Loop detection at step 3 caps it at **$0.10**. Across a 200-worker batch where 5% go pathological, that is 10 × $5.67 = $56.70 versus 10 × $0.10 = $1.00 per night, or roughly **$1,700/month** for one detector that is thirty lines of code.

**⚠ Trap:** retrying the whole worker on failure without changing anything. A worker that failed because the task is ambiguous will fail identically three times at full price. Retry is for transport errors. For quality failures, the retry must carry the failure back in as context ("your previous attempt failed with: X") or it is just a more expensive way to get the same answer.
### You've said "the agent loop is not your code." Unpack that. What do you inherit from a harness and what do you still own?

**🗣 Say this in the room:** "When I adopt a harness I'm inheriting the loop — context management, compaction, tool dispatch and retry, transcript persistence, streaming. What I still own is everything that determines whether the product is good: tool design, policy and permissions, evals, budgets, observability, and domain state. Teams get this backwards, spend three months on framework selection, and ship an agent with four badly-described tools and no eval harness."

The mental model that makes it stick: a harness is a web framework. FastAPI gives you routing, validation plumbing, dependency injection, and an ASGI lifecycle. It does not give you a good API, and nobody has ever shipped a bad product because they picked Starlette over Django. Agent harnesses are the same layer, and the same reasoning applies — including the part where a bad framework choice costs you weeks and a bad domain model costs you the company.

**What you inherit, precisely:**

- **The loop itself** — call model, parse tool calls, dispatch, append results, repeat, terminate. Roughly 30 lines you could write from memory, and the reason harness choice matters less than people think.
- **Context-window management and compaction** — deciding what to drop or summarize when the transcript approaches the limit.
- **Tool dispatch, schema generation, and error-to-tool-result conversion** — turning your Python signatures into JSON Schema and your exceptions into `is_error` results.
- **Transport concerns** — retries on 429/500, streaming assembly, partial-message handling, provider abstraction.
- **Transcript persistence and resumption**, if the harness offers it (many do not, or offer only in-memory).
- **Sub-agent spawning primitives**, if it has them.

**What you still own, and what no harness will ever do for you:**

- **Tool design.** Names, descriptions, argument schemas, output shape and size. This is the single largest determinant of agent quality and it is 100% yours.
- **Policy.** What requires approval, what is irreversible, what credentials each agent holds, what the blast radius is.
- **Evals.** Task sets, graders, regression gates. No harness ships your rubric.
- **Budgets and caps.** Some harnesses give you hooks; none give you the policy.
- **Observability semantics.** A harness may emit spans; what those spans mean, what attributes carry cost, and what your on-call dashboard shows is yours.
- **Domain state.** The database, the idempotency records, the tenant isolation. The harness has no opinion and should not.

**⚠ Trap:** the framework-shopping trap, where a team burns a quarter evaluating five harnesses. The loop is 30 lines. If your agent is bad, it is bad because your tools return 40k tokens of unfiltered JSON with descriptions like "queries the database," and no harness fixes that. My rule in review: you may not open a framework-selection discussion until you can show me your tool schemas and one eval run.

### Your harness does context compaction for you. What does that buy you, and where does it burn you?

What it buys is real: when the transcript approaches the context limit, something must happen, and "crash with a 400" is the alternative. A harness that summarizes the older portion of the transcript, or drops middle tool results, or evicts by a recency-plus-importance heuristic, is doing work you would otherwise have to write and tune. For a long-running agent it is the difference between a 20-step ceiling and an unbounded run.

Where it burns you is that **compaction is a lossy, silent, model-dependent transformation of your agent's memory, triggered by a threshold you may not control, at a moment you cannot predict.** Three specific consequences:

**Silent capability loss.** After compaction the agent no longer remembers a constraint the user stated in turn 2 — "never touch the production database," "the customer is in the EU so no US data residency." The agent does not know it forgot. It proceeds confidently. This is the failure that produces the worst incidents, because the pre-compaction and post-compaction agents are the same object with different beliefs. The mitigation is that **anything that must survive must not live in the transcript**: constraints go in the system prompt (which harnesses do not compact), and state goes in a file or a structured store the agent re-reads.

**Prefix cache invalidation.** Prompt caching keys on an exact token prefix. Compaction rewrites the middle of the transcript, which changes every token after the rewrite point, which invalidates the entire cache. 💰 The step right after compaction pays full price for its whole input. On a 120k-token context at $3/Mtok that is $0.36 uncached versus roughly $0.036 at a 90% cached-read discount — a **10× spike on one step**, and if your compaction threshold interacts badly with your loop you can hit it repeatedly. If your dashboard shows periodic cost spikes with no traffic change, look at compaction events first.

**Non-reproducibility.** Compaction is usually itself an LLM call. Two identical runs compact differently, so post-compaction behaviour diverges. Your eval on a long task now has a variance source you did not model, and a regression you observe may be compaction luck.

**⚠ Trap:** assuming compaction is idempotent or bounded. Compact a summary and you get a summary of a summary; run long enough and the agent's entire history is a paragraph of vague generalities that reads fine and contains nothing actionable. I cap this by keeping an **uncompacted spine** — the original user request, the plan, and the established-facts list — that is re-injected verbatim after every compaction and never itself summarized. It costs a few hundred tokens per turn and it is the difference between a 200-step run that stays on task and one that drifts into confident nonsense at step 90.

**🗣 Say this in the room:** "I treat harness compaction as a garbage collector I don't control — it will run, it will run at a moment I didn't choose, and it will free something I needed. So the invariants live outside the heap: constraints in the system prompt, state in files, and a small verbatim spine re-injected after every compaction."

### The harness retries failed tool calls for you. What's the trap in that?

The trap is that "retry" means two completely different things depending on which side of the model the failure is on, and harnesses routinely conflate them.

**Transport retries** — connection reset, 429, 502, timeout on the HTTP call to the provider — are exactly the retries you already know. Idempotent, exponential backoff with jitter, retry-after honoured, invisible to the model. These belong in the client and I want them there.

**Tool-execution failures** — your `search_orders` tool raised because the customer ID was malformed — must **not** be silently retried. They must be returned to the model as a tool result with `is_error: true` and the error text, because the error *is the information the model needs to correct itself*. A harness that catches the exception and re-invokes your tool with the identical arguments will get the identical exception, three times, at zero benefit and non-zero latency. The model never learns the ID was malformed and produces a final answer built on a gap it does not know exists.

The third and worst case: **retrying a non-idempotent tool.** The tool timed out at 30 seconds. The harness retries. The underlying operation — a payment, an email, a `POST /refunds` — had actually succeeded; only the response was lost. You have now issued two refunds. This is a bug you have shipped and fixed before in ordinary backends, and the only new thing is that the caller deciding to retry is a framework you did not write, operating on a tool whose idempotency properties it cannot know.

The discipline I enforce:

- Tool implementations declare their own retry policy; the harness does not retry tools generically. If your harness cannot be configured that way, that is a serious mark against it.
- Every mutating tool takes an **idempotency key derived deterministically from the run and the call** — `f"{run_id}:{tool_call_id}"` — and the *tool* deduplicates server-side. The `tool_call_id` is stable for a given model output, so a retry of the same call reuses the key.
- Every tool declares `read_only: bool` and only read-only tools are eligible for automatic retry.
- Timeouts on mutating tools resolve by **querying for the effect**, not by re-issuing. "Did a refund with key X exist?" is a safe question; "issue the refund again" is not.

**⚠ Trap:** believing the model's retry behaviour is safer than the harness's because "the model can see it already tried." It cannot reliably. A model that sees a timeout will often re-issue the call — that is the locally-sensible move, and it is the same double-refund with an extra $0.02 of tokens attached. The deduplication has to be server-side, keyed, and outside the model's control. This is the single place where backend instinct transfers perfectly and candidates still get it wrong, because they reason about the model's judgment instead of about at-least-once delivery.

### What does a harness give you for transcript persistence, and what do you still have to build?

What harnesses typically give you is a **checkpointer**: an interface that serializes the agent's state after each step to some backend — memory, SQLite, Postgres, Redis — and can restore it. That is genuinely useful, and it gives you three things for free: crash resumption within a step boundary, the ability to pause for human input and resume hours later, and "time travel," which is just restoring an earlier checkpoint and re-running from there with a different input.

What you still own is everything that makes persisted transcripts operationally useful:

**Retention and PII.** A transcript contains everything the user typed and everything your tools returned — customer records, tokens, internal documents. It is a durable store of production data with none of the classification your primary database has. You need a retention policy, encryption at rest, tenant-scoped access, and a redaction pass before anything lands in your observability backend. No harness does this for you and every compliance review will ask.

**Schema evolution.** Checkpointers usually serialize the harness's own state objects. Upgrade the harness and yesterday's checkpoints may not deserialize. If you are resuming week-old runs, you own a migration story for a schema you did not design — which is an argument for persisting *your own* run state (the progress file, the artifacts, the established facts) as the source of truth and treating the harness checkpoint as a cache.

**Query patterns.** "Show me every run where the agent called `issue_refund` above $500" is an analytics query over transcripts. A checkpointer stores blobs keyed by thread ID; it does not index tool calls. You need a separate event stream — one row per model call and per tool call, with structured columns — feeding whatever you already use for analytics. This is the part teams retrofit and regret.

**Cross-run linkage.** A user's third conversation about the same incident is a different thread ID. Connecting them is memory architecture, not persistence, and it is yours.

**⚠ Trap:** treating the checkpointer as your durable store of record for a multi-agent run. Worker transcripts are enormous and mostly worthless after the fact; leads are small and valuable. Checkpointing everything symmetrically means your Postgres grows by hundreds of megabytes per overnight batch for data nobody will ever read. 💰 200 workers × 150k tokens × ~4 bytes/token ≈ 120 MB *per run*; nightly, that is 3.6 GB/month of transcript blobs. I keep lead transcripts and worker *reports* durably, and worker transcripts for 48 hours in cheap object storage with a lifecycle rule — long enough to debug last night, short enough not to become a data-retention problem.

### I'm choosing a harness. Give me the axes I should actually score on.

Six axes. I score them explicitly in a table because "it felt nicer" is not a defensible engineering decision, and because the right answer is genuinely different for a chat product and an overnight batch runner.

**1. State persistence.** Does it checkpoint, to what backends, at what granularity, and can I resume mid-run after a process death? In-memory only is disqualifying for anything long-running and completely fine for a request-scoped chat turn. Ask specifically: can I resume a run that was killed *between* a tool call being issued and its result arriving?

**2. Streaming.** Can I stream tokens, tool-call starts, tool results, and — critically for multi-agent — **sub-agent lifecycle events** out to a client? Many harnesses stream the top-level agent's tokens and give you nothing from workers, which means your UI shows a 90-second silence during the most interesting part of the run. For a user-facing product this is close to a veto.

**3. Typed IO.** Are tool arguments and structured outputs validated against a schema I control, ideally Pydantic? Does it give me typed state between nodes, or is everything a dict? Untyped state is the thing that rots fastest in a multi-agent system, because the contract between agents is exactly where the bugs live.

**4. Human-in-the-loop.** Can I suspend mid-run, durably, awaiting an external approval that may arrive in four hours from a different process — and resume with the approval as input? This is a hard requirement for anything that takes real actions, and it is where in-memory harnesses fall over completely. The test question: does approval survive a deploy?

**5. Observability hooks.** Does it emit OpenTelemetry spans, or at minimum callbacks on every model call and tool call carrying token usage? Can I attach my own attributes (tenant, run ID, agent version) to every span? If token usage is not exposed per call, cost attribution is impossible and you should walk away.

**6. Ease of dropping to raw API calls.** Can I bypass the abstraction for one call — hand-build the message list, set a provider-specific parameter, use a feature that shipped last week — without leaving the framework? This is the axis I weight highest, because model providers ship faster than frameworks. Extended thinking, cache breakpoints, a new tool-choice mode, a new structured-output mode: these arrive months before framework support. A harness that makes the escape hatch painful will eventually block a product decision, and the day it does is the day you find out you cannot afford to migrate.

**⚠ Trap:** scoring on "how nice is the hello-world." Every harness has a beautiful five-line quickstart. What matters is what the code looks like at week twelve, when you have per-tenant tool sets, an approval gate, three agent versions in flight, and a customer asking why their run cost $14. Score the week-twelve shape, and the fastest way to see it is to read the framework's own test suite and its GitHub issues, not its README.

### Pick a harness for three cases: a customer-facing chat agent, an overnight refactor bot, and an internal research assistant. Justify each.

I will give you the reasoning rather than a brand ranking, because framework churn in this space is fast enough that a name I give you today may be the wrong answer by your loop. **📅 Volatile:** verify the current feature matrices before quoting any specific framework's capabilities; what follows is the decision procedure, which is durable.

**Customer-facing chat agent (Sierra-like, Notion-assistant-like).** The binding constraints are latency, streaming fidelity, and per-tenant isolation. I want: token streaming to the client with sub-second TTFT, tool-call events surfaced so the UI can show "searching your workspace…", request-scoped state (the conversation lives in *my* database keyed by user, not in the framework's checkpointer), and dead-simple escape to raw API calls because I will be tuning prompt caching and structured outputs constantly. Topology: **single agent with tools**, possibly a small bounded handoff graph for routing. What I do *not* want is a heavy graph abstraction — the control flow is "one turn, some tool calls, one answer," and a state-machine framework buys nothing while costing me streaming complexity. I would seriously consider the provider's own thin SDK plus my own 40-line loop here, and I have shipped that.

**Overnight refactor bot.** The binding constraints are durability, cost caps, and failure isolation across many parallel workers. I want: durable checkpointing to Postgres, resumption after process death, per-worker budget enforcement, and structured artifacts on disk. Streaming is irrelevant — nobody is watching. Typed IO matters a lot because 40 workers returning free-form text is unmanageable. Honestly, the *scheduler* here is a job queue, and I would build the outer layer on the queue infrastructure I already run (Celery, or a Postgres task table) and use an agent library only for the inner loop of a single worker. The mistake I would push back on is picking a graph framework and then discovering it has no backpressure, no rate-limit-aware concurrency control, and no story for a 40-task partial failure — all of which Celery has had for a decade.

I want: real sub-agent primitives, filesystem tooling, good compaction I can override, and per-agent token accounting out of the box. This is the case where a purpose-built agent SDK earns its keep, because sub-agent spawning with isolated context is genuinely fiddly to write well and it is the core of the product.

**🗣 Say this in the room:** "I'd answer this by binding constraint rather than by brand. Chat is latency and streaming, so I want a thin loop and an easy path to raw API calls. Overnight batch is durability and isolation, so the outer layer is a job queue I already operate and the agent library only runs the inner loop. Research is context isolation and cost accounting, which is the one case where sub-agent primitives are worth adopting wholesale."

### When do you drop to raw API calls, and how do you keep that option cheap?

I drop out whenever the abstraction is between me and a provider feature that materially changes cost, latency, or quality — and in practice that is more often than framework advocates admit. Concretely: setting explicit cache breakpoints to control what gets prefix-cached; using extended-thinking parameters; hand-building the message list to place a large static document before the volatile part so the cache prefix is maximal; using a provider's batch tier for offline work at roughly half price; using a structured-output mode the framework has not wrapped yet.

The way you keep it cheap is architectural, and it is the same discipline you already apply to ORMs: **the framework is allowed to be a convenience layer over an interface you own, never the interface itself.**

```python
class ModelClient(Protocol):
    async def complete(self, *, system: list[Block], messages: list[Msg],
                       tools: list[ToolSchema], max_tokens: int,
                       extra: dict) -> Completion: ...
```

Everything in my agent code calls `ModelClient`. One implementation wraps the framework; another hits the provider SDK directly. `extra` is the escape hatch — a passthrough dict for provider-specific parameters — and the fact that it is explicitly in the interface is what stops people from reaching around it. `Completion` carries normalized `usage` so cost accounting never depends on the framework's accounting.

The two other things that keep the option open: **do not let framework types leak into your domain.** If your database rows store the framework's serialized message objects, you have married it. Store your own message model and adapt at the edge. And **keep one non-trivial path implemented against raw API calls** — the highest-volume path is a good choice, since that is where cache tuning pays. It stays exercised, it stays correct, and it is proof to yourself that the migration is possible. The moment nobody has run the raw path in six months, you are locked in regardless of what the architecture diagram says.

💰 **Why this pays concretely:** cache-breakpoint control alone. A 12k-token system prompt plus tool schemas, at $3/Mtok, costs $0.036 per call uncached. With cache reads at roughly a 90% discount that is $0.0036, a saving of $0.0324 per call. At 200k calls/day that is $6,480/day — **around $194k/month** — for a feature that is one parameter in the raw API and may be entirely unreachable through a framework that owns your message construction. **📅 Volatile:** cache discount rates and pricing change; re-derive with current numbers before quoting.

**⚠ Trap:** the inverse mistake, which is refusing all abstraction and writing everything raw. Then you own retry, streaming assembly, tool-schema generation, and provider differences forever, and none of that is where your product is. The position is not "no frameworks," it is "frameworks behind an interface I control."

### Two agents are exchanging data. Show me how you'd type that boundary, and why it matters more than typing a normal function call.

It matters more because the sender is a stochastic process and the receiver is a stochastic process, so neither end will fail loudly on a malformed message — they will both interpret it plausibly and keep going. Every other typed boundary you have ever built has a runtime that raises. This one has a runtime that *improvises*.

The pattern is: define Pydantic models for the spec and the report, have the worker produce its report through a structured-output mode or a dedicated "emit_report" tool whose schema is the model, validate at the boundary, and on validation failure feed the error back to the worker for one repair attempt before failing the task.

```python
class WorkerReport(BaseModel):
    model_config = ConfigDict(extra="forbid")
    status: Literal["completed", "partial", "failed", "budget_exhausted"]
    findings: list[Finding] = Field(max_length=10)
    negative_findings: list[str] = Field(default_factory=list, max_length=10)
    artifacts: list[str] = Field(default_factory=list)

    @field_validator("findings")
    @classmethod
    def evidence_must_be_dereferenceable(cls, v: list[Finding]) -> list[Finding]:
        for f in v:
            if not (f.evidence_ref.startswith(("runs/", "http")) or ":" in f.evidence_ref):
                raise ValueError(f"evidence_ref {f.evidence_ref!r} is not a resolvable pointer")
        return v
```

That validator is the interesting line. It is not type-checking; it is **semantic checking of a model's output at an agent boundary**, and it catches the specific failure where the worker writes `evidence_ref: "the config file"` instead of a path. Without it, that string flows into the lead's context, the lead cites "the config file," and the user gets an uncheckable claim. With it, the worker gets one repair round and usually produces the real path, because it *has* the path — it just did not think the field was load-bearing.

Three more rules I enforce at agent boundaries:

**Cap collection lengths in the schema.** `max_length=10` on findings is a context-budget control expressed as a type. Without it a worker returns 40 findings and your lead's context grows 4× more than you modelled.

**`extra="forbid"`.** A worker inventing extra fields is a signal that the contract drifted, and you want that loud, not silently ignored.

**Version the schema.** Every report carries `schema_version`. When you change the report shape, in-flight runs from the old version must still deserialize, or a deploy kills every running batch.

**⚠ Trap:** validating and then, on failure, falling back to "just pass the raw text through." I have seen this exact `except ValidationError: return raw` in production code, added to stop pager noise. It converts a loud failure into a permanent silent one — the boundary is now untyped for exactly the cases where typing mattered. Fail the task, or repair once and then fail. Never degrade to raw.

### Where does the human-approval interrupt live in a tree of agents? The worker wants to do something irreversible.

The answer that ends the argument: **irreversible actions do not live in workers.** If a worker can take an action requiring approval, you have put a permission boundary in the wrong place, and the fix is topological, not procedural.

The reasoning. A worker is ephemeral, concurrent with N others, and has no user session. For a worker to request approval, the request must propagate up through the lead — which is mid-`gather`, cannot respond to one child without blocking the rest, and would have to hold the entire fan-out open for however long a human takes. Meanwhile the worker's process is parked holding a transcript, and if the human takes four hours you are checkpointing a suspended worker across a deploy. It is buildable and I have seen it built; it is a large amount of machinery to support a design mistake.

**The design I actually use: workers propose, a single writer executes.** Workers are read-only by construction — their tool set contains no mutating tools, enforced in the dispatcher, not the prompt. A worker that concludes an action is needed returns a **proposed action** in its structured report: the tool name, the arguments, the justification, the reversibility class. The lead collects proposals. After the fan-out completes, there is a single serialized execution phase where proposals are presented to the human as a batch, approved or rejected individually, and executed by one agent (or by plain code) with the approvals attached.

This is better on four counts, and I would enumerate them out loud. **The human sees the batch**, so they can spot "these three actions together are wrong" — which is invisible when approving one at a time. **The suspension point is one place**, so durable HITL is one state machine and not N. **The blast radius is bounded** by construction, since no worker holds a mutating credential. And **the audit record is clean**: one approval event, one executor, one ordered list of effects.

The mechanics of the suspension itself: persist the run state, emit an approval request with a durable ID to whatever your approval surface is (a Slack message, a queue, a UI card), and *end the process*. Do not hold a coroutine open for four hours. When approval arrives, a fresh process loads the state and continues. This is the durable-execution shape and it must survive a deploy — the test I insist on before launch is "approve something, deploy during the wait, confirm it still executes correctly."

**⚠ Trap:** approval fatigue converting a safety control into a rubber stamp. If a run generates 40 approval requests, the human approves all 40 without reading by the second week and you have a compliance artifact rather than a control. Batch them, sort by blast radius, auto-approve the reversible ones under a threshold with an audit record, and reserve genuine interrupts for the small set that can actually hurt. A control nobody reads is worse than no control, because it launders the decision.

### Design the event protocol for streaming a tree of agents to a UI. The user is watching a six-minute run.

The design constraint is honesty under uncertainty: the user must always be able to answer "is it working, what is it doing, how much longer" and you cannot answer the third accurately, so you must answer the first two extremely well.

Flat event stream, every event carrying `run_id`, `span_id`, `parent_span_id`, and a monotonic sequence number. The tree is reconstructed client-side from parent pointers, which means events can arrive out of order from concurrent workers without the client caring.

```
run.started        {objective, estimated_phases}
plan.emitted       {tasks: [{id, title}]}         # the plan IS the progress bar
agent.started      {span_id, parent, role, title} # "Reading the billing docs"
agent.token        {span_id, delta}               # lead only, by default
tool.started       {span_id, tool, summary}       # "searching: refund policy"
tool.finished      {span_id, ok, summary, ms}
finding.emitted    {span_id, text, evidence_ref}  # incremental value, the key event
agent.finished     {span_id, status, tokens, cost_usd}
run.usage          {tokens, cost_usd, elapsed_s}  # every few seconds
run.finished       {status, answer_ref}
```

Four design decisions worth defending.

**Stream the plan first, and treat it as the progress indicator.** The single biggest UX improvement in a long-running agent is emitting the task list within the first few seconds. Now the user sees eight items and watches them tick over. That converts an opaque wait into a legible one, and it is why "clarify → plan → execute" is the dominant shape for these products — the plan is a *product* surface, not just an internal artifact.

**Stream findings, not worker tokens.** Do not pipe five workers' token streams to the client. It is unreadable, it is a lot of bandwidth, and it exposes intermediate reasoning that is often wrong and later corrected — users remember the wrong intermediate. Stream a one-line title when a worker starts, and the *findings* as they are produced. Findings are the incremental value; tokens are noise.

**Emit cost continuously.** Users and internal operators both need it, and it is trivial once your spans carry usage. It also does something subtle: a visible dollar counter makes users tolerant of a long run, because they can see it working.

**ETAs must be honest.** Never a percentage derived from elapsed time. Either derive from plan completion — "3 of 8 subtasks complete" — or say "typically 4–8 minutes" from your own p50/p90 telemetry. A fabricated progress bar that sits at 90% for three minutes destroys trust faster than no progress bar.

**⚠ Trap:** rendering the tree as nested collapsible panels that auto-expand as workers start. It looks impressive in a demo and it is unusable with five concurrent workers, because the layout reflows constantly and the user cannot read anything. Render a flat, append-only activity feed with the tree available on demand. The tree is for debugging; the feed is for humans.

### Is there a real difference between "sub-agent as a tool" and "sub-agent as a node in a graph"? Or is that just framework marketing?

There is a real difference and it is about **who decides**, which is the axis that governs every multi-agent design decision.

**Sub-agent as a tool.** The lead's model sees `spawn_researcher(task)` in its tool catalog and *decides at runtime* whether to call it, how many times, and what to pass. Control flow is model-determined. This is flexible — the lead can spawn 2 workers or 9 depending on what the task turns out to need — and it is opaque, because you cannot enumerate the paths ahead of time, and your cost distribution has a long tail you did not choose.

**Sub-agent as a graph node.** Your code decides. The edge from `plan` to `research` is in the graph; the model fills in the content of each node but does not choose the topology. This is testable — you can enumerate every path and write an eval per path — and it is rigid, because a task needing an extra research pass does not get one unless you built a loop edge with a condition.

The distinction has three practical consequences. **Cost predictability**: a graph has a bounded worst case you can compute; a tool-spawn has whatever the model decides, which is why you need hard spawn caps in the dispatcher (`max_spawns_per_run`, and I set it low — 8 is generous). **Testability**: you can write "does the router send billing questions to the billing node" as a unit test on a graph; on tool-spawn it is a statistical property you measure over a sample. **Debuggability**: a graph gives you a fixed vocabulary of node names, so your dashboards can group by node and you get stable metrics; tool-spawn gives you free-text task descriptions and no natural grouping.

My actual rule: **the topology is my code; the content is the model's.** I use graph structure for anything I can enumerate — the phases of a research run, the stages of a support conversation — and tool-style spawning only for genuine fan-out where the *count* is data-dependent and the workers are homogeneous. "Spawn one worker per file that matches this pattern" is a fine tool-spawn; "decide whether to consult the legal agent" is a graph edge with a condition, because I want to test it.

**🗣 Say this in the room:** "It's the same question as static versus dynamic dispatch, and I answer it the same way: I want the topology in my code because that's what I can test and cost-bound, and the model choosing content within it. The only thing I let the model decide about topology is fan-out width over homogeneous workers, and even that gets a hard cap in the dispatcher."

### Your harness shipped a minor version bump and your agent's behaviour changed. How did that happen, and how do you stop it?

It happened because a harness upgrade can silently change the *prompt*, and the prompt is your product.

The specific mechanisms, roughly in order of how often I have seen them bite:

**The framework's own system-prompt scaffolding changed.** Many harnesses prepend or append text — tool-use instructions, formatting guidance, a reminder about how to call functions. A version bump rewords it. Your carefully-tuned prompt is now preceded by different words, and behaviour shifts. You will not see this in your diff because it is not in your repo.

**Tool-schema serialization changed.** The framework generates JSON Schema from your Python signatures. A change in how it renders `Optional`, or whether it includes docstring text as `description`, or the ordering of properties, changes the bytes the model sees. Ordering changes alone invalidate prefix caches; description changes alter tool-selection behaviour.

**Default parameters changed.** `temperature`, `max_tokens`, the default model alias. A framework bumping its default model from one snapshot to the next is the most consequential change possible and it can arrive in a patch release.

**Compaction or truncation policy changed.** Different summarization prompt, different threshold, different eviction order. Long runs now behave differently at exactly the moment they were fragile.

The defences, and I would insist on all four:

1. **Pin exact versions, including transitives.** Lockfile, no ranges. You already do this; the point is that agent frameworks change semantics in patch releases far more than your usual dependencies.
2. **Snapshot-test the wire payload.** This is the high-value one and almost nobody does it. A test that constructs a canonical agent state and asserts on the *exact JSON sent to the provider* — system blocks, tool schemas, message list — with the request intercepted at the transport layer. Any framework change that touches the prompt now fails CI with a readable diff. It is maybe 60 lines and it has caught every one of the failures above for me.
3. **Pin the model explicitly**, never an alias like `-latest`. Aliases move under you and a model change is not a framework problem but it will present as one.
4. **Run the eval suite on dependency bumps**, gated in CI, with a regression threshold. Renovate opening a PR that bumps your agent framework should trigger the eval job, not just the unit tests.

**⚠ Trap:** assuming your unit tests cover this. They mock the model. Every one of the failure modes above lives in the bytes you send to the model, which is precisely what mocking hides. If your entire test suite passes with a mocked client, you have zero coverage of the thing most likely to break.

💰 **What it costs to skip:** a silent quality regression takes days to notice — it shows up as a drift in resolution rate or a rise in escalations, not as an alert. On a support agent handling 30k conversations/day at a 70% automated-resolution rate, a 5-point drop is 1,500 extra human-handled tickets per day; at $4 fully-loaded per ticket that is **$6,000/day** accruing while you bisect. The snapshot test costs an afternoon.
### Do the arithmetic on error compounding in a multi-agent system. Why is it worse than in a single agent?

The mental model: a multi-agent run is a **series-parallel reliability network**, and you compute it exactly the way you would compute the availability of a service graph — except the per-component reliability is a per-step model accuracy in the low nineties, which is a number no infrastructure engineer would ever accept in a dependency.

**Series compounding inside one worker.** A worker doing 8 steps at 95% per-step correctness completes correctly with probability 0.95^8 = 0.663. At 90% it is 0.90^8 = 0.430. That is already brutal, and it is the single-agent baseline.

**Parallel compounding across workers.** If the lead needs *all* 5 workers to be correct — which is the case for a synthesis that depends on every finding — you get 0.663^5 = **0.128**. Twelve percent. Five competent workers each two-thirds reliable produce a run that is right one time in eight.

**Plus the handoff layer.** Each spawn is a lossy paraphrase and each report is a lossy compression. Assign a generous 97% fidelity to each and you have 10 handoff events (5 down, 5 up): 0.97^10 = 0.737. Multiply: 0.128 × 0.737 = **0.094**.

**Plus the synthesis step**, say 90%: **0.085**.

So a system built from components that are individually 90–97% reliable delivers a fully-correct answer about 8.5% of the time. That number is why "our agents are 95% accurate" is a meaningless claim, and saying this out loud in an interview is worth a lot, because it reframes the whole conversation from "how do I make each agent better" to "how do I change the topology so errors do not multiply."

**What actually fixes it — and none of it is a better prompt:**

**Reduce the exponent.** Fewer steps, fewer workers, fewer levels. Cutting workers from 5 to 3 and steps from 8 to 5 gives 0.95^5 = 0.774 per worker, 0.774^3 = 0.464 — a 3.6× improvement from *deleting things*. This is the strongest lever and it is the one that argues for collapsing topologies.

**Make failures independent and detectable rather than silent.** A worker that returns `status: failed` does not multiply into the product; it is a known hole the lead can route around or re-spawn. The multiplicative disaster comes from *silent* wrongness. So every mechanism that converts silent failure into loud failure — schema validation, evidence-ref checks, negative-findings fields, baseline test runs — is worth more than any accuracy improvement.

**Change AND to OR where the task allows.** If the answer only needs 3 of 5 workers to be right, the reliability is the tail of a binomial, not a product: with p = 0.663, P(at least 3 of 5) = 0.79. This is what redundant or overlapping partitions buy you, and it is the honest justification for tolerating some duplicated work.

**Verify at the end against ground truth, not against the model.** A test suite, a compiler, a schema check, a numeric reconciliation. A deterministic verifier turns an 8.5% success rate into an 8.5% *first-pass* rate with retries, and retries against a real signal converge.

**🗣 Say this in the room:** "Per-step accuracy compounds multiplicatively across steps and across workers, so five workers at eight steps and 95% per step lands around 13% before handoff loss. The lever that actually moves that is reducing the exponent — fewer agents, fewer steps — and converting silent failures into loud ones, not improving the prompt."

### The final answer was wrong. Walk me through how you find which agent broke it.

Blame attribution in a tree is a real discipline and the honest starting point is that **you cannot do it at all unless you instrumented for it before the run.** So the first half of my answer is the instrumentation, and the second is the procedure.

**What must be in the trace.** One span per agent invocation, parented correctly. Every span carries: `run_id`, `agent_role`, `agent_version`, the full input (spec) and output (report), token usage, and cost. Every tool call is a child span with arguments and a truncated result plus a pointer to the full result in object storage. Every claim in a report carries an `evidence_ref`. Without evidence refs the procedure below stops at step 3 and you are guessing.

**The procedure, top-down:**

1. **Isolate the wrong claim.** Not "the answer is wrong" — the specific sentence. "It says our Adyen retry window is 72 hours; it is 24."
2. **Follow the citation.** The final answer should carry an `evidence_ref` inherited from a worker finding. Resolve it. Three outcomes: the reference resolves and the source genuinely says 72 hours (upstream data problem, not an agent problem — and this is more common than people expect); the reference resolves and says 24 (**the synthesis step corrupted it** — bug is in the lead); the reference does not resolve or does not exist (**a citation detached**, which is its own bug class and usually means the claim was invented at a summarization boundary).
3. **If it resolves correctly at the worker level, diff worker report against worker transcript.** Did the worker's raw tool output contain 24 and the report say 72? That is the worker's compression step. Did the tool output itself say 72? That is the tool or the source.
4. **If the claim appears nowhere below the lead, it was fabricated at synthesis.** Look for thin evidence: the lead had 5 reports of which 3 said "no information found," and it produced a confident answer anyway. This is the classic hallucinated-synthesis-from-thin-evidence failure and the fix is a synthesis-time rule: assertions require at least one resolvable evidence ref, and the lead must be permitted — explicitly, in its prompt — to answer "the research did not establish this."
5. **If the worker never looked in the right place, the bug is the task spec.** Read the spec. Nine times out of ten the scope excluded the relevant area, or the root objective was paraphrased away.

**The one automated check that pays for itself:** a post-run job that resolves every `evidence_ref` in the final answer and asserts (a) it exists, and (b) the cited span actually supports the claim, using a cheap model as the checker. Run it on 100% of production answers if you can afford it — at ~2k tokens per check on a $0.25/Mtok small model that is $0.0005 per answer, or $50/month at 100k answers/month — and surface a "citation integrity" metric. It catches step-2 and step-4 failures before a customer does.

**⚠ Trap:** blaming the last agent that touched the output. The synthesizer is the most visible and the least often at fault; the usual culprit is a spec written three levels up that excluded the relevant scope. Always read the specs before you read the reports.

### Design the observability schema for a multi-agent run. I want to be able to answer "why did this cost $14."

The mental model: **a run is a distributed trace, and you already know how to build one.** Root span per run, child span per agent invocation, grandchild spans per model call and per tool call, correct parenting through async boundaries. The delta from an HTTP trace is exactly one thing: the interesting numeric attributes are tokens and dollars rather than milliseconds, and they must aggregate up the tree.

**Span attributes I require on every agent span:**

```
run.id, run.tenant_id, run.user_request_id     # attribution keys
agent.role            # "lead" | "researcher" | "verifier" — LOW cardinality, on purpose
agent.version         # the version hash; see agent versioning
agent.depth           # 0 for lead, 1 for workers
gen_ai.usage.input_tokens, gen_ai.usage.output_tokens
gen_ai.usage.cache_read_tokens, gen_ai.usage.cache_write_tokens
gen_ai.request.model
cost.usd.self         # this span only
cost.usd.subtree      # self + all descendants, computed on span close
status, stop_reason   # completed | budget_exhausted | error | max_steps
```

`cost.usd.subtree` is the field that answers your question directly. Computed as each span closes by summing children, it means a single query — "show me spans where `agent.depth = 0` and `cost.usd.subtree > 10`, ordered desc" — gives you the expensive runs, and then drilling into the tree shows you the branch that ate the money. Without subtree rollup you can only see per-call costs and you have to reconstruct the tree by hand in an incident.

`agent.role` being low-cardinality is deliberate and I would call it out. Do not put the task description in a span name; you will get a million unique operation names and your tracing backend will either drop them or bill you for the cardinality. The task description is an *attribute* (or, better, an event body); the name is the role.

**Two derived views I build on top:**

**Cost per role, per run.** A stacked breakdown: lead 12%, researchers 71%, verifier 17%. This is how you find that your verifier — which everyone assumed was cheap — is re-reading every artifact and costs more than the research. That has happened to me.

**Cache hit rate per role.** `cache_read_tokens / (cache_read_tokens + input_tokens)`. If a role that should have a stable prefix shows a low ratio, something is varying in its prompt — a timestamp, a randomized tool ordering, a per-request ID injected into the system prompt. 💰 One such bug: a `Generated at {timestamp}` line at the top of a 9k-token system prompt destroyed caching for every call. Fixing it moved 9k tokens per call from $0.027 to $0.0027; at 400k calls/month that is **$9,720/month** recovered by deleting one line. You only find it if you graph cache hit rate.

**Sampling policy.** Full traces for every run is expensive at volume. I keep: 100% of spans with `status != completed`, 100% of runs above a cost threshold, 100% of runs flagged by a user, and a 5% random sample of the rest. Full transcripts go to object storage with the span carrying the pointer, never inline in the span — otherwise your tracing bill exceeds your model bill, which I have also seen.

**⚠ Trap:** logging prompts and completions into your general observability stack without redaction. Those payloads contain customer PII, credentials that leaked into tool output, and internal documents. Your tracing vendor is now a data processor for content nobody classified. Redact at the emitter, and keep raw transcripts in a store with the same access controls as your primary database.

### A customer asks why one request cost $14. Trace that back through a fan-out. What has to be true for you to answer?

One invariant has to hold: **every model call in the system carries the originating `user_request_id`, and there are no exceptions.** If a single background task, retry, or async worker drops it, your attribution is wrong by an unknown amount and you cannot detect it.

Getting that right is a plumbing problem you have solved before — it is request-ID propagation — with two twists. First, sub-agents run in separate coroutines or separate processes, so the ID has to travel in the spawn payload, not just in a `contextvars` context that async boundaries may or may not preserve. I put it in the `WorkerSpec` explicitly, as a required field, because a required field cannot be forgotten. Second, some costs are *deferred*: an async summarization job, an overnight memory-consolidation pass, an embedding of a produced artifact. Those must carry the ID too or you will systematically undercount, and undercounting is worse than not counting because it looks like data.

The ledger I actually write: one row per model call, appended by the client wrapper, never by application code.

```
usage_events(
  ts, run_id, user_request_id, tenant_id, agent_role, agent_version,
  model, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens,
  cost_usd, span_id, parent_span_id
)
```

Cost is computed at write time from a versioned price table, not at read time. Prices change; a report run six months later must reproduce what you actually charged, and re-deriving from today's price table silently rewrites history. This is the same reason you snapshot a line-item price on an order rather than joining to the products table.

Then the answer to "why $14" is one query grouped by `agent_role`, and it usually reads like: lead $0.60, 11 researchers $11.20, verifier $2.20. Then one level deeper: researcher #7 alone was $4.10 because it hit its step cap. Then: it hit the cap because a search tool returned 30k-token pages and its transcript grew quadratically. That is a real chain and it takes about ninety seconds if the ledger exists.

**💰 What the arithmetic on the answer looks like:** 11 researchers averaging 145k input and 3k output at $3/$15 per Mtok = 11 × (0.145 × 3 + 0.003 × 15) = 11 × (0.435 + 0.045) = 11 × $0.48 = $5.28. Getting to $11.20 means the average was double that, which points at unbounded tool output — and now you have a specific, fixable finding rather than "agents are expensive."

**⚠ Trap:** attributing cost only to the top-level API call and treating sub-agent spend as platform overhead. I have seen a dashboard where "cost per request" was the lead's tokens only, and the real cost was 9× higher. Everyone believed the unit economics worked for a year. The reconciliation check that catches it: sum `cost_usd` over the ledger for a day and compare against the provider's actual invoice for that day. If they differ by more than a couple of percent, something is uninstrumented, and finding it is worth more than any optimization.

### What is an "agent version," exactly? What has to change for the version to change?

This is a question I like because most teams have never defined it, and without a definition you cannot A/B, you cannot roll back, and you cannot correlate a quality regression with a change.

**An agent version is a hash over everything that determines the model's behaviour.** Concretely:

- The system prompt text, byte-exact.
- The tool set: names, descriptions, and JSON schemas — the *rendered* schemas, not the Python source, since a framework upgrade can change the rendering without changing your code.
- The model identifier, pinned to an exact snapshot, never an alias.
- The sampling parameters: temperature, top_p, max_tokens, thinking budget.
- The loop policy: max steps, budgets, termination conditions, retry policy.
- For a multi-agent system: the topology and the version of every sub-agent.
- The versions of the spec and report schemas.

```python
def agent_version(cfg: AgentConfig) -> str:
    payload = json.dumps({
        "system": cfg.system_prompt,
        "tools": sorted(render_schema(t) for t in cfg.tools),
        "model": cfg.model,
        "sampling": cfg.sampling.model_dump(),
        "loop": cfg.loop_policy.model_dump(),
        "children": sorted(agent_version(c) for c in cfg.sub_agents),
    }, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(payload.encode()).hexdigest()[:12]
```

Two properties matter. It is **content-addressed**, so it is impossible to change behaviour without changing the version — which is the whole point, and the reason a human-assigned `v2.1` is not good enough. And it is **recursive**, so bumping a worker's prompt bumps the lead's version too, which is correct: the composite system behaves differently.

What this buys you operationally. Every span, every usage event, and every eval result carries the version. "Resolution rate dropped Tuesday" becomes a join: group resolution rate by `agent_version` and the change is immediately visible, including changes nobody logged in a changelog because they were made by a dependency bump. Rollback becomes concrete — you can serve version X because X fully specifies the behaviour. And your eval results become attributable: a score without a version attached is a number you can never reproduce.

**Store the config, not just the hash.** A content-addressed store mapping version → full config, written on every deploy. Otherwise six weeks later you have a hash in your metrics and no way to know what it was.

**⚠ Trap:** the retrieval corpus. If your agent's behaviour depends on a knowledge base, a set of skills, or a memory store, those are inputs too — and they change continuously without any deploy. You cannot hash a live corpus, so what I do instead is stamp a **corpus version** (index alias name plus embedding model plus snapshot timestamp) as a separate dimension on every span. Then a quality change can be attributed to either the agent version or the corpus version, and "we didn't deploy anything" stops being an acceptable end to an investigation.

### How do you A/B two agent versions safely? Assume real users and real actions.

The honest opening: **A/B testing agents is harder than A/B testing a ranking change**, because the outcome metric is often subjective, the variance is high, the per-sample cost is dollars rather than microseconds, and the unit of analysis is a multi-turn session rather than an impression. So the design has to be more careful than the standard playbook, and saying that is part of the answer.

**Stage 1 — offline eval, always first.** Run both versions over a frozen task set with graders. This is free of user risk and it catches gross regressions. It will not catch distribution shift, so it is necessary and never sufficient. Gate: version B must not regress any category by more than a pre-declared threshold.

**Stage 2 — shadow mode.** Run B on real production traffic in parallel with A, serving only A. Compare on everything you can measure without a user seeing B: cost, latency, tool-call distribution, error rate, and LLM-judge quality on the paired outputs. Shadowing is where you catch "B calls the expensive search tool 3× more often," which no offline set will show you because your task set does not have your traffic's distribution. **The critical constraint: shadow runs must have all mutating tools disabled**, enforced by the credential B holds, not by B's prompt. A shadow agent that issues a real refund is a headline.

**Stage 3 — canary with sticky assignment.** Assign at the **user** level (or account level), hashed and stable, not per request. Two reasons this is non-negotiable: a user flipping between agent versions mid-conversation gets incoherent behaviour, and your outcome metric is session-level so per-request assignment contaminates the units. Start at 1–5%, hold for enough sessions to power the comparison, and gate the ramp on automated guardrails.

**Guardrails that auto-halt the ramp**, evaluated continuously: cost per resolved task above A by more than X%, p95 latency above threshold, escalation-to-human rate up, tool error rate up, any safety-classifier trigger rate up. These are one-sided — you halt on harm, you do not auto-promote on benefit.

**Powering it.** This is where people wave their hands and I would not. If A resolves 70% of tasks and you want to detect a 3-point absolute improvement at 80% power and 5% significance, the standard two-proportion sample size is roughly n = 2·(z_{α/2}+z_β)²·p̄(1−p̄)/δ² ≈ 2 × (1.96+0.84)² × 0.715 × 0.285 / 0.03² ≈ 2 × 7.85 × 0.2038 / 0.0009 ≈ **3,554 sessions per arm**. At 5% traffic and 30k sessions/day that is 1,500 sessions/day per arm, so about **2.4 days**. Knowing you need days rather than hours is the difference between a real experiment and a vibe check, and 💰 at $0.40 per session the shadow stage alone over 30k sessions/day for two days costs 60,000 × $0.40 = **$24,000** — which is a real number you should raise before someone is surprised by it.

**⚠ Trap:** comparing A and B on different time windows because "we deployed B on Tuesday." Traffic is not stationary — weekday/weekend, an incident, a marketing push, a big customer onboarding. Sequential comparison of agent versions is the most common bad measurement in this space and it will confidently tell you B is better when B is Wednesday.

**🗣 Say this in the room:** "Offline eval, then shadow with mutations disabled at the credential level, then a sticky user-level canary with one-sided auto-halt guardrails. I'd insist on sticky assignment because the outcome metric is session-level, and I'd compute the sample size up front — for a three-point lift on a seventy-percent baseline you're looking at roughly 3,500 sessions per arm, which is days, not hours."

### How do you evaluate an agent under extreme context growth — a run whose context grows to hundreds of thousands of tokens?

The mental model first: **advertised context length and usable context length are different numbers, and the gap is where agents fail.** A model may accept 1M tokens and still be unable to reliably use a fact that sits at position 400,000 among 900,000 tokens of similar-looking material. Agentic runs manufacture exactly that condition, because a long run's context is hundreds of near-identical tool results.

**What a long-context agentic evaluation has to measure**, which is more than "can it find the needle":

- **Retrieval at depth.** Can it use a fact stated early, after 200k tokens of intervening material? The classic needle-in-a-haystack probe measures this, and models generally do well on it — which is exactly why it is insufficient. A single distinctive sentence in unrelated filler is the easiest possible version of the problem.
- **Retrieval among distractors.** The realistic case: 40 near-identical tool results and the answer is in one of them. This is much harder than the classic needle and is where degradation actually appears.
- **Multi-hop across distance.** Fact A at position 10k, fact B at position 300k, and the answer requires joining them. This degrades far earlier than single-fact retrieval.
- **Instruction persistence.** A constraint stated in turn 1 — "never modify files under `vendor/`" — still honoured at step 90. This is the one that produces incidents, and almost nobody tests it. It is trivially easy to test: state a constraint, run a long task, count violations.
- **Aggregation.** "How many of the documents mention X" requires reading all of them, not retrieving one, and it degrades hardest.
- **Behaviour across compaction boundaries.** Deliberately push past the compaction threshold and re-ask a question answerable only from pre-compaction material. This is the measurement that tells you whether your compaction policy is safe, and I have never seen a team run it before shipping.

**📄 Paper:** the needle-in-a-haystack probe originates as an informal community evaluation (Kamradt, 2023) rather than a formal paper, and synthetic long-context suites in the RULER family (NVIDIA, 2024) generalized it into multi-hop, multi-needle, aggregation and tracing tasks — which is the right shape. **📅 Volatile:** long-context and long-horizon agentic benchmark names churn quickly and I would not walk into a room citing a specific leaderboard number unless I had run it that month. What is durable, and what an interviewer is actually testing, is that you know the *measurement design*: distractors, multi-hop at distance, instruction persistence, aggregation, and compaction-boundary behaviour. Describe the axes and note that you would check the current benchmark landscape rather than quote a stale score.

**How this changes the design.** If instruction persistence degrades past ~100k tokens in your own measurements, then your architecture must not rely on the transcript to carry constraints — they go in the system prompt, which is re-sent verbatim every call and is never compacted, and critically-irreversible constraints get enforced in the *tool implementation* as well, because a prompt-level constraint is a request and a dispatcher-level check is a guarantee.

**⚠ Trap:** benchmarking on your model provider's advertised context and assuming your agent inherits it. Your agent's effective ceiling is set by whichever degrades first — retrieval accuracy, instruction adherence, latency (TTFT grows roughly linearly with prompt length on the prefill), or cost. Measure *your* task's degradation curve and set your compaction threshold below the knee. I would rather compact at 60% of the advertised window with a well-designed spine than run at 95% and discover instruction adherence collapsed at step 70.

### Give me the failure taxonomy for multi-agent systems. I want a decision procedure, not war stories.

**🔍 Failure taxonomy — multi-agent, diagnosed by symptom:**

**The final answer is confident and wrong, and no component reported an error.** Cause: silent compression loss or hallucinated synthesis from thin evidence. Diagnostic: resolve every evidence ref in the answer; count how many worker reports had `status: completed` but empty `findings`. Fix: require resolvable evidence for every assertion; add `negative_findings` so "found nothing" is distinguishable from "did not look"; permit the synthesizer to answer "not established."

**The answer addresses a subtly different question than was asked.** Cause: intent decay across handoffs, or a decomposition shape that destroyed a comparative or aggregate framing. Diagnostic: read the emitted task specs against the user's verbatim message. Fix: propagate `root_objective` byte-exact; decompose by dimension rather than by subject for comparative questions.

**Cost is 3–10× the model.** Cause: raw tool output entering the lead's context, unbounded worker steps, or a broken prefix cache. Diagnostic: cost by `agent_role`, then cache hit rate by role, then the token-per-step growth curve inside the most expensive worker. Fix: cap report sizes in the schema; truncate tool results before they enter a transcript; stabilize the cacheable prefix.

**Artifacts are corrupted or a change is missing entirely, with no error anywhere.** Cause: concurrent writes — conflict, ordering, or interface drift between phases. Diagnostic: intersect worker file sets; compare each worker's claimed changes against the final artifact; check read timestamps against write timestamps on shared files. Fix: disjoint namespaces enforced in the write tool; serial phase for interface changes; single-writer merge; one authoritative test run after the merge.

**Two workers produced the same finding and the synthesis presents it as two independent confirmations.** Cause: overlapping partition plus a synthesizer that cannot tell independent corroboration from duplication. Diagnostic: compare the specs for scope overlap. Fix: validate disjointness at spawn; pass the partition to the synthesizer so it knows what independence means here.

**Latency is bad and the wall-clock is mostly idle.** Cause: serialized spawning where the lead emits one worker per turn instead of a batch, or an unbounded concurrency limit causing 429 retry storms. Diagnostic: plot span start times — a staircase means serialization, a cliff-then-retries means rate limiting. Fix: prompt and schema the lead to emit a batch of specs in one turn; size the concurrency semaphore from your TPM limit.

**Behaviour changed with no deploy.** Cause: model alias moved, corpus/index changed, dependency bump, or a provider-side default change. Diagnostic: group your quality metric by `agent_version` and by `corpus_version`; if both are constant across the change, it is provider-side. Fix: pin model snapshots; version the corpus; snapshot-test the wire payload.

**A run never finishes.** Cause: lead re-planning loop, worker tool-retry loop, or a deadlock on a shared claim. Diagnostic: repeated-identical-call counters, progress-free-step counters, cost velocity per worker. Fix: wall-clock deadline at the supervisor, loop detection with an injected corrective tool result, TTL on claims.

**⚠ Trap:** treating every one of these as a prompting problem. In this list, exactly two (intent decay and thin-evidence synthesis) respond meaningfully to prompt changes. The rest are topology, dispatcher, or schema problems, and a team that reaches for the prompt first will spend months.

### 🏋 Drill: build an orchestrator-worker system with filesystem memory and crash resumption. Ninety minutes, no AI assistance. What's the rubric?

**The task.** Given a research question, a lead agent produces a plan of 3–6 subtasks, spawns one worker per subtask concurrently, each worker runs a bounded tool-calling loop against a search tool and writes an artifact to `runs/{run_id}/workers/{i}/`, returns a validated structured report, and the lead synthesizes a cited answer. The run maintains a progress file such that killing the process with `SIGKILL` at any point and restarting resumes correctly. Enforce a per-run dollar cap.

**Pass criteria — all of them, or it is a fail:**

1. **It runs.** Real API, real concurrency, produces a cited answer in under 5 minutes.
2. **Worker context is genuinely isolated.** Grep your own code: no raw tool output from a worker appears in the lead's message list. Report tokens are capped and the cap is enforced in the dispatcher, not requested in the prompt.
3. **`SIGKILL` mid-run, restart, correct resume.** Completed tasks are not re-run. The in-flight task is handled by an explicit, defensible policy. The lead does not re-plan. The remaining budget is inherited, not reset — I check this specifically, because it is the most commonly missed item.
4. **Structured report validated with a schema.** A deliberately malformed worker output produces one repair attempt and then a `failed` status — not a silent pass-through of raw text.
5. **A worker failure does not kill the run.** Kill one worker's tool by making it raise; the lead receives a failure report and synthesizes anyway, noting the gap.
6. **Budget cap enforced in code.** Set the cap absurdly low ($0.05) and confirm the run stops spawning, still produces a synthesis from partial results, and does not exceed the cap.
7. **Every model call is logged with tokens and cost**, tagged with run ID and agent role, and you can produce the per-role cost breakdown at the end.
8. **Disjoint write namespaces**, enforced in the write tool with a path-prefix check that raises.
9. **Findings carry resolvable evidence refs** and the final answer's citations resolve.

**Self-scoring.** Under 90 minutes with all nine is a strong pass. The items people fail, in frequency order: budget inheritance on resume (4), re-planning on resume (5), and enforcing report size in the prompt rather than the dispatcher (6). If you fail items 3 or 6, do not move on — those two are the whole difference between a demo and a system, and they are exactly what an interviewer probes when they ask "what happens if it crashes."

**🏋 Extension drill, 30 minutes:** make the lead spawn 40 workers instead of 5, with a concurrency limit derived from a stated tokens-per-minute budget, and add repeated-identical-tool-call detection that injects a corrective result on the third occurrence. Pass criterion: with a deliberately looping tool, the worker breaks out or terminates within 4 steps rather than burning to its step cap.

### Design case: we're a workspace product adding an assistant that answers questions across documents, tickets, calendars and code. Pick the topology and defend it.

I would build this as **a single agent with well-designed tools, plus exactly one sub-agent shape reserved for deep-read tasks** — and I would spend most of the design review arguing for the first half.

**Why single-agent for the common case.** The dominant query is "when is the design review and what did we decide last time" — one or two retrieval calls, a synthesis, sub-second-to-few-second latency expectation, and the user is watching. A multi-agent decomposition adds a full model round-trip of planning latency (600–1,200ms) plus worker spawn overhead to a query that a single loop answers in two tool calls. It would be slower, more expensive, and no better. 💰 Single agent: 8k input + 600 output = 8 × $0.003 + 0.6 × $0.015 = $0.024 + $0.009 = **$0.033**. Orchestrator with three workers on the same query: lead ~$0.05 plus 3 × ~$0.30 = **$0.95**, 29× the cost for a query that did not need it. At 500k queries/day that is $16,500/day versus $49,500 — and the arithmetic is the argument.

**Where the sub-agent earns its place.** "Summarize everything we decided about pricing across the last two quarters." That touches 200 documents. No single context holds them, and the compression ratio is enormous — 400k tokens of source to a 1k-token answer. This is the canonical read-heavy fan-out and it is exactly the case the topology exists for. So: a `deep_research(question, scope)` capability that the main agent may invoke, which spawns bounded read-only workers over a partitioned corpus, writes artifacts, and returns a cited synthesis.

**The routing decision** — cheap path or deep path — I would make with a small classifier or a cheap model rather than letting the main agent decide, because letting the model choose means paying planning latency on every query to decide you did not need planning. Route on signal: estimated result-set size from a cheap retrieval probe, query type, explicit user intent ("research", "across all"). Show the user which path they got, and let them escalate manually — "search deeper" as a button is better product than a model guessing.

**The permission boundary is where I would actually spend the design.** This product's hard problem is not topology, it is that the assistant answers from a corpus with per-user ACLs, and a retrieval layer that leaks one document across a permission boundary is an enterprise-ending incident. So: permissions are enforced at **retrieval time against the live ACL system**, filtered pre-ranking not post-ranking, with the user's identity carried in the spec to every worker and every tool call. Never cache retrieval results across users. Never let a worker inherit a service credential — workers act as the user. And I would build the eval for this first: a corpus with known ACLs, a set of queries whose answers require restricted documents, and a hard gate that zero restricted content appears in any answer.

**What I would explicitly refuse.** A "specialist agent per data source" design — a calendar agent, a docs agent, a code agent. They share a tool set shape and a corpus model, they differ only in a prompt, and building five agents means five system prompts to keep consistent, five eval suites, and a routing layer that will misroute cross-source questions, which are the most valuable queries this product answers. One agent with source-aware retrieval tools handles cross-source questions natively. I would say that in the room, because the org-chart topology is the design everyone proposes and it is wrong for exactly this reason.

### Last one: when do you collapse a multi-agent design back into a single agent, and how do you say that in an interview?

The signals that tell me to collapse, in the order I check them:

**The sub-agents share a tool set and differ only by system prompt.** Then they are not agents, they are prompting modes, and you have paid a process boundary for a conditional. Collapse.

**The lead is passing large payloads down and getting large payloads back.** The context-isolation benefit is zero and you are paying the handoff loss for nothing. Either fix the compression contract or collapse.

**Every sub-agent is called exactly once, in a fixed order, with no branching.** That is a pipeline, and it should be a pipeline in your code with one agent per stage or, more often, one agent that does all three stages in one context. Fixed sequence is the strongest possible signal that the topology is decoration.

**Your quality problems trace to handoffs rather than to reasoning.** If your postmortems keep concluding "the worker didn't know X," the architecture is manufacturing your bugs.

**You cannot state the isolation boundary.** Back to the first question in this section: if neither context nor permissions requires the split, collapse it.

**How to collapse without regressing.** Do not delete agents and hope. Take the sub-agents' system prompts and merge them into a sectioned single prompt. Take their tools and union them, then *prune* — the union is usually larger than a single agent should carry, and this is the moment to consolidate overlapping tools. Keep whatever verification steps existed as explicit steps in the single loop. Then run your eval suite on both and compare cost, latency, and quality. In my experience the collapsed version is faster, cheaper, and slightly better on coherence, and slightly worse on any task where the fan-out was genuinely reading more material than one context can hold — which tells you exactly which single capability to re-extract as a sub-agent.

**🗣 Say this in the room:** "I'd collapse it. The three agents share a tool set and differ only by system prompt, they're called once each in a fixed order, and I can't name a context or permission boundary between them — so what I actually have is a three-stage pipeline paying three English serialization costs. I'd merge them into one sectioned prompt, union and prune the tools, keep the verification as an explicit step, and run both against the eval set. My prior is that the single agent is cheaper, faster, and more coherent, and if the eval says otherwise I'll have learned exactly which stage needed the isolation."

The meta-point, and the reason this is worth saying explicitly in an interview: **arguing for the simpler architecture is a seniority signal, not a lack of ambition.** Anyone can draw a five-agent diagram. The interviewer is checking whether you know that each box is a lossy, untyped, stochastic RPC boundary that you will personally debug at 3am. What they want to hear is that you can name the exact conditions under which you would pay that price — separate context, separate permissions, genuine read-heavy fan-out — and that you would refuse to pay it otherwise. The candidate who says "I'd start with one agent and good tools, and here is the specific measurement that would make me split it" is the one I hire.
