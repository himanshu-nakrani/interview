### Before PagedAttention existed, how did serving engines allocate the KV cache — and walk me through exactly where the memory went?

They allocated it the way you would allocate a fixed-size buffer in C when you do not know the final length: reserve for the worst case, up front, contiguously. When a request arrived, the engine carved out one contiguous KV tensor sized `max_seq_len` for that sequence — because the attention kernel indexed the cache with plain strided arithmetic, and strided arithmetic requires contiguity. A request that would eventually produce 300 tokens got 8,192 tokens' worth of GPU memory nailed down at admission time and held until it finished.

The mechanism is worth being precise about because the failure is not one thing, it is three. **Reserved-but-unused waste**: the slots between the current length and `max_seq_len` are allocated and untouchable. **Internal fragmentation on the tail**: even after the request finishes, its allocation was sized to a request-level maximum, not to the actual generation. **External fragmentation**: after a few hundred requests of varying `max_seq_len` arrive and leave, the free memory is a swiss cheese of holes, none of them large enough for the next 8k-contiguous reservation, even though the *sum* of free memory is plenty. This is exactly the malloc pathology you have debugged in a long-running C process — except there is no `mmap` fallback, no compaction, and the arena is 80 GB of HBM that costs several dollars an hour.

**📐 Numbers you must know:** the vLLM paper (Kwon et al., SOSP 2023) measured that pre-paging systems wasted **60–80% of allocated KV memory** to these three effects combined, and that vLLM's block allocator brings the waste **under ~4%**. Memorize the pair, not just the first half — the second number is what makes the argument land.

**⚠ Trap:** candidates describe this as "we allocated too much memory." That is not the interesting part. The interesting part is that *KV memory is the sole determinant of batch size*, and batch size is the sole determinant of throughput on a decode-bound workload. Fragmentation is not a memory bug, it is a **throughput** bug wearing a memory bug's clothes. If you waste 70% of KV, you run at roughly 30% of the concurrency you paid for, and your tokens-per-dollar is 3.3× worse than the hardware allows.

### Explain PagedAttention to me. Assume I've written a memory allocator but I've never seen a GPU.

Then you already know it. PagedAttention is virtual memory for the KV cache, and the analogy is not a teaching device — it is literally the design. The paper's contribution is the observation that KV cache management is the *same problem* as OS paging, and therefore admits the *same solution*, which the systems community solved in the 1960s.

The mapping is one-to-one. A **page** becomes a **KV block**: a fixed-size chunk holding the keys and values for a fixed number of tokens (16 is vLLM's CUDA default). A **process's virtual address space** becomes **a sequence's logical token positions** — position 0 through position T-1, which the model reasons about as if they were contiguous. The **page table** becomes the **block table**: a per-sequence array mapping logical block index → physical block index in the global KV pool. **Physical memory** becomes one giant pre-allocated slab of HBM carved into uniform blocks at engine startup. **Demand paging** becomes lazy allocation: a sequence gets its next physical block only when it actually crosses a block boundary during decode.

The consequence follows immediately and this is the beat to hit out loud. Because blocks are uniform-size and allocated on demand, **external fragmentation is structurally impossible** — every free block fits every request, exactly as in an OS page allocator. And because allocation is lazy, reserved-but-unused waste collapses from `max_seq_len - current_len` down to at most one partially-filled block. The remaining waste is bounded by `block_size - 1` tokens per sequence, which for block 16 and a 0.31 MB/token model is at most 15 × 0.31 MB ≈ 4.7 MB per sequence. Against a 2.5 GB reservation, that is the difference between "you can run 60 requests" and "you can run 600."

**📄 Paper:** Kwon et al. (2023), *Efficient Memory Management for Large Language Model Serving with PagedAttention*, SOSP. Introduced the block allocator + block-table attention kernel and shipped it as vLLM. It replaced contiguous max-length KV reservation, the design used by Orca and FasterTransformer at the time.

**🗣 Say this in the room:** "PagedAttention is virtual memory applied to the KV cache. Fixed-size blocks, a per-sequence block table, demand allocation. It makes external fragmentation impossible and bounds internal fragmentation to one block per sequence — the vLLM paper measured a drop from 60–80% waste to under 4%, and since KV capacity *is* your batch size, that waste reduction shows up directly as throughput."

### What's actually in a block table, and what does the attention kernel have to do differently once you page the cache?

The block table is the smallest data structure in the system and the one that changes the kernel. Per sequence it is a flat `int32` array of length `ceil(current_len / block_size)`, where entry `i` holds the *physical* block id backing logical token positions `[i·B, (i+1)·B)`. That is it. The engine keeps these on the host for scheduling and uploads them to device memory as a `[num_seqs, max_blocks_per_seq]` tensor each step, padded with a sentinel.

The kernel change is a level of indirection on every KV read. Unpaged attention computes the address of key `t` as `base + t · stride`. Paged attention computes `physical = block_table[seq, t // B]`, then `addr = kv_pool_base + physical · block_bytes + (t % B) · token_stride`. So every load turns into a gather through a lookup table rather than a linear walk. In practice the kernel loads the block table row into shared memory or registers once per thread block, then iterates blocks, and inside a block the reads *are* contiguous and coalesced — which is why the cost stays small.

Two second-order details matter and interviewers probe for them. First, the K and V pools are usually shaped differently: vLLM's classic layout stores K as `[num_blocks, num_kv_heads, head_dim/x, block_size, x]` with a vectorization factor `x` so that the K reads inside the QK^T loop hit full-width vector loads, while V stays `[num_blocks, num_kv_heads, head_dim, block_size]`. The asymmetry exists because K is consumed contracted over `head_dim` and V is consumed contracted over `seq`. Second, because sequences in a batch now have arbitrary lengths and arbitrary physical scatter, the kernel cannot be a dense batched GEMM — it is a custom kernel (or a varlen FlashAttention entry point taking `cu_seqlens` cumulative-length offsets).

**⚠ Trap:** people assume paging forced a slow, hand-rolled kernel and that this is a tax you pay for memory efficiency. That framing is backwards on modern engines: the paged decode kernel and FlashDecoding-style split-KV parallelism are the *same* kernel family, and the block structure is what makes splitting the KV dimension across thread blocks natural in the first place. The block table did not fight the kernel; it gave the kernel a work-partitioning unit.

### How do you pick block size? Tell me what breaks at 1 and what breaks at 512.

Block size is a classic allocator trade and you should answer it as one: it sets the granularity of waste against the granularity of overhead and sharing. Small blocks waste less memory and share more precisely; large blocks amortize metadata and give the kernel longer contiguous runs.

At **block_size = 1** you have perfect memory utilization — zero internal fragmentation, every token exactly accounted. You also have a block table with one entry per token, which for a 128k-context request is a 128,000-entry `int32` array (512 KB) uploaded and indexed every decode step, per sequence. The gather is now fully random at token granularity, so your KV loads stop coalescing and you throw away memory bandwidth on a workload that is *defined* by being memory-bandwidth-bound. And prefix caching becomes a per-token hash chain, which is more bookkeeping for no extra sharing.

At **block_size = 512** the kernel is happy — long contiguous runs, tiny block table, great coalescing. But a 40-token request now occupies 512 tokens of KV: 92% internal waste, which is most of the fragmentation you just built the whole system to eliminate. Worse, prefix-cache sharing now only fires on prefixes that match to a 512-token boundary. If your system prompt is 1,700 tokens, you share 1,536 of them and re-prefill 164 for every request forever.

The rule I enforce: **16 for chat and agent traffic, consider 32–64 only when your minimum sequence length is comfortably above a few hundred tokens and you have measured a kernel win.** vLLM's CUDA default of 16 is the right default and I would push back on someone tuning it without a profile showing block-table gather as a hot path.

**📐 Numbers you must know:** internal fragmentation per sequence is bounded by `(block_size − 1) × bytes_per_token`. For Llama-3.3-70B at ~0.31 MB/token: block 16 → ≤ 4.65 MB/seq; block 128 → ≤ 39.4 MB/seq. At 256 concurrent sequences that is 1.2 GB versus 10.1 GB of pure waste — on an 80 GB card, the second one costs you roughly 32,000 tokens of usable KV, or ~12% of your context budget, for nothing.

**⚠ Trap:** raising block size to "improve prefix cache hit rate" is exactly backwards, and I have seen it in a real PR. Hit rate is measured in *tokens saved*, and coarser blocks round every shared prefix **down** to a boundary. Larger blocks strictly reduce the tokens you can share.

### Where does copy-on-write actually pay off in a serving engine?

Copy-on-write pays off exactly where two logical sequences are guaranteed to have identical KV for a prefix, which happens far more often than people expect. The mechanism is the one you know from `fork()`: the child's block table points at the parent's physical blocks, each block carries a reference count, and a write to a shared block triggers allocate-copy-remap for that block only.

Three cases fire in production. **Parallel sampling** — `n=4` completions from one prompt. Without CoW you prefill the prompt four times and store four copies of its KV; with CoW you prefill once, hand all four sequences the same physical blocks with refcount 4, and only the final partially-filled block gets copied when the four generations diverge. **Beam search** — beams fork and die constantly, and the KV of a killed beam is freed by decrementing refcounts rather than by copying anything. **Shared system prefixes** — this is the big one commercially, and it is the same machinery generalized: if every request in your product starts with the same 6,000-token instruction block, those blocks live once in HBM with a refcount in the hundreds.

**💰 Math:** a code-assistant endpoint serving `n=3` candidate completions on a 4,000-token prompt for a 70B at 0.31 MB/token. Naive: 3 × 4,000 × 0.31 MB = 3.72 GB of KV per request, plus three full prefills at ~2·70e9·4,000 = 5.6e14 FLOPs each. With CoW: 1.24 GB of KV (a 2.48 GB saving per in-flight request) and one prefill instead of three, cutting prefill compute by 1.12e15 FLOPs. On an H100 at ~400 effective TFLOP/s for prefill that is ~2.8 seconds of GPU time reclaimed per request — at $2.50/GPU-hour and 50,000 requests/day, 2.8 s × 50,000 = 38.9 GPU-hours/day = $97/day = **~$2,900/month from one flag**. (**📅 Volatile:** GPU hourly rates move constantly; verify before quoting.)

**⚠ Trap:** CoW is not free when generations diverge immediately. If the very first sampled token differs across the `n` sequences — which is the *point* of sampling — the last block splits right away. The saving is on the prefix, not the suffix, and someone who claims "CoW makes n=8 sampling cost the same as n=1" has not thought about the decode phase, which is 8× regardless.

### Distinguish internal from external fragmentation in this system — and tell me which one paging doesn't solve.

External fragmentation is free memory that exists but cannot be used because it is not contiguous in the shape the allocator needs. Internal fragmentation is memory that is allocated to a request but not carrying useful data.

Paging **eliminates external fragmentation by construction**. Every allocation is exactly one block, every block is the same size, so any free block satisfies any request. There is no shape mismatch left to have.

Paging **bounds but does not eliminate internal fragmentation**. Every sequence's last block is on average half empty; worst case it holds one token in a 16-token block. That residue is real and it is the ≤4% the paper reports.

The thing paging genuinely does not solve — and this is the answer that separates people — is **fragmentation of the *pool itself* against competing consumers**. The KV pool is carved out at startup as a fixed fraction of the card (`gpu_memory_utilization`, default 0.9 in vLLM). Everything else — weights, activation workspace, CUDA context, NCCL buffers, the allocator's own caching in PyTorch, CUDA graph memory pools — lives outside it. If your activation peak grows because someone raised `max_num_batched_tokens`, or a LoRA adapter set gets loaded, you do not get a graceful degradation: you get an OOM at some unlucky moment because the KV pool was sized months ago and cannot shrink. That is external fragmentation at the *arena* level, and it is where real incidents come from.

**🔍 Failure taxonomy — "we OOM'd at 3am with no traffic change":** (1) Did `gpu_memory_utilization` stay the same but the *model* change (new tokenizer, larger vocab embedding, added adapters)? (2) Did activation peak grow — check `max_num_batched_tokens` and chunked-prefill settings. (3) Is PyTorch's caching allocator fragmenting outside the KV pool — set `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` and re-test. (4) Did CUDA graph capture allocate a new pool for a batch-size bucket you had never hit before? That fourth one is the sneaky one: it fires only when traffic reaches a shape you have not previously served.

### Does PagedAttention make the attention kernel slower? Quantify it, and tell me why you'd accept it.

Yes, slightly, and you should say so rather than pretending it is free — an interviewer who has read the paper knows the authors measured it themselves. The paged kernel adds an indirection (block-table lookup per block) and gives up some of the long contiguous runs a dense layout would hand the memory system. The vLLM authors reported the paged attention kernel running roughly **20–26% slower than a fused, unpaged FasterTransformer-style attention kernel** in microbenchmarks.

You accept it because you are trading a **kernel-level** cost for a **system-level** win, and the system-level win is an order of magnitude larger. Attention is not the whole decode step — for a 70B at moderate context, the linear layers dominate the bytes moved, because you read 70 GB of weights per step regardless of batch size, while the KV read scales with `batch × context`. If attention is 25% of your step time and paging makes attention 25% slower, your step got 6% slower. In exchange, your batch size went from ~60 to ~600, and throughput on a decode-bound workload is very nearly linear in batch size until you hit the compute roofline.

**💰 Math:** step time 20 ms → 21.2 ms (+6%), so per-sequence token rate drops from 50 tok/s to 47.2 tok/s. Batch goes 60 → 400 (a conservative 6.7×). Aggregate throughput: 60 × 50 = 3,000 tok/s → 400 × 47.2 = 18,880 tok/s. That is **6.3× more tokens per GPU-second for a 6% per-token latency regression**. There is no serving workload where I would not take that trade.

**🗣 Say this in the room:** "The paged kernel is measurably slower than a contiguous one — the paper reports around 20–26% on the attention kernel alone. That is the wrong level to optimize at. Attention is a minority of decode step time, and the memory it frees multiplies batch size, which multiplies throughput almost linearly. I'd take a 6% step regression for a 6× batch every time."

### A colleague proposes skipping paging entirely: just grow the KV tensor with a realloc-style doubling. Why won't that work?

Because `realloc` on the CPU is cheap for reasons that do not hold on a GPU serving loop, and because the growth is not the expensive part — the *copy* is.

Mechanically: doubling means that when a sequence crosses its capacity, you allocate a new contiguous region of `2×` the size, copy the old KV into it, and free the old. For a 70B at 0.31 MB/token, a sequence at 32k tokens holds 9.9 GB of KV. Doubling it means allocating 19.8 GB (which you may not have) and copying 9.9 GB device-to-device. At H100's ~3.35 TB/s HBM bandwidth and counting both the read and the write, that copy is 19.8 GB / 3.35 TB/s ≈ **5.9 ms of pure bandwidth**, during which you are moving zero useful tokens. Amortized over the doubling it looks acceptable; in a serving system it is a 5.9 ms stall that lands unpredictably in the middle of a decode step and blows your p99 ITL SLO for *every sequence in the batch*, because the batch steps in lockstep.

Then the deeper problem: you have reintroduced external fragmentation, and you have made it worse. You now need contiguous regions of many different sizes (1×, 2×, 4×, …), arriving and departing in arbitrary order, in a fixed 80 GB arena with no compaction primitive. That is the textbook setup for a buddy allocator's worst case, and unlike a CPU heap you cannot fall back on the OS giving you a fresh mapping.

**⚠ Trap:** "we'll just compact when fragmentation gets bad." Compaction means moving live KV, which means rewriting every pointer the kernel uses — and it means a multi-gigabyte device-to-device copy while the engine is stalled. Paging exists precisely so that you never need compaction. If your answer to a fragmentation question requires a stop-the-world compaction, you have re-derived the problem, not the solution.

### Work the memory math for me. Llama-3.3-70B, a realistic length distribution, H100s. How much does paging actually buy?

Set up the model first. Llama-3.3-70B: 80 layers, 8 KV heads (GQA), head_dim 128. KV bytes per token = 2 (K and V) × 80 × 8 × 128 × 2 bytes (fp16) = **327,680 bytes ≈ 0.3125 MiB/token**. Hold that constant; it is the single most useful number in this section.

Now the budget on 4×H100 SXM5 (TP=4, 320 GB total). Weights in fp16: 140 GB → 35 GB/GPU. CUDA context, NCCL buffers, activation workspace and allocator slack: budget ~6 GB/GPU. That leaves ~39 GB/GPU × 4 = **156 GB for KV**, or 156,000 MB / 0.3125 MB = **~499,000 tokens** of KV capacity.

**Naive contiguous reservation at `max_model_len` = 8,192:** every admitted request reserves 8,192 × 0.3125 MB = 2.56 GB. Concurrency ceiling = 499,000 / 8,192 = **60 sequences**. This is a hard cap. It does not matter that your median request is 700 tokens; you cannot admit the 61st.

**Paged, same traffic:** measure the actual distribution — say mean prompt 550, mean completion 250, so mean occupancy ≈ 800 tokens plus at most one partial block. Effective per-sequence cost ≈ 808 × 0.3125 MB = 253 MB. Concurrency ceiling = 499,000 / 808 = **617 sequences**.

That is **10.3×**, and the waste fraction under the naive scheme is (8,192 − 800)/8,192 = **90.2%** — comfortably inside the paper's 60–80% band once you account for the fact that most systems set `max_model_len` more conservatively than 8k.

**💰 Math:** you will not actually run 617 concurrent — you will cap at `max_num_seqs` = 256 because past that the batch becomes compute-bound and ITL degrades. But the naive scheme cannot reach 256 *at all*; it tops out at 60. To serve 256 concurrent you would need ⌈256/60⌉ = **5 nodes instead of 1**. At 4×H100 per node and ~$2.50/GPU-hour, one node is 4 × 2.50 × 24 × 30 = **$7,200/month**; five nodes is **$36,000/month**. Paging is worth $28,800/month on a single 256-concurrency endpoint. (**📅 Volatile:** GPU pricing — verify.)

**🗣 Say this in the room:** "0.31 megabytes per token for a 70B with GQA. That is the number I do everything else from. 156 gigabytes of usable KV on a 4-way H100 node is half a million tokens of cache; at 8k reservations that is 60 requests, at an 800-token real mean it is 600. The 10× is why paging exists."

### A sequence is mid-decode and the block manager has no free blocks. Walk me through what happens.

This is the preemption path and it is the most systems-y question in the whole engine. Every decode step, before launching the model, the scheduler asks the block manager: can each running sequence be given one more block if it crosses a boundary this step? If the answer is no for some sequence, the engine cannot simply stall — it has to *reduce* the working set.

The policy is: **evict a victim, in reverse arrival order (last-in-first-preempted), and free its blocks.** Preempting the newest request rather than the oldest is deliberate — it preserves the progress of requests closest to finishing, which minimizes the number of requests in flight and therefore minimizes total KV pressure. It is the opposite of the fairness instinct, and it is correct here for the same reason SJF beats FIFO on mean response time.

Then there are two ways to preempt, and the choice is a real engineering trade:

**Swap.** Copy the victim's KV blocks out to pinned host memory over PCIe, free the device blocks, and copy back when it is rescheduled. Cost is pure bandwidth: PCIe Gen5 x16 is ~64 GB/s theoretical, realistically ~50 GB/s. A 4,000-token sequence's KV is 4,000 × 0.3125 MB = 1.25 GB → 1.25/50 = **25 ms out and 25 ms back**. You pay 50 ms of transfer but zero recomputation.

**Recompute.** Throw the KV away and re-run prefill over the whole sequence when it resumes. Cost is compute: prefill FLOPs ≈ 2 × N_params × tokens = 2 × 70e9 × 4,000 = 5.6e14 FLOPs. On a 4-way H100 node at, say, 1,200 effective TFLOP/s aggregate for prefill, that is **~0.47 ms**… which sounds absurdly cheap, and it is why recompute usually wins. The honest caveat is that the recompute has to *share* the prefill budget with incoming requests, so its real cost is scheduler contention and TTFT for other requests, not just its own FLOPs.

The modern default is **recompute**, and prefix caching makes it strictly better: if the sequence's prompt blocks are still resident in the prefix cache, the recompute is partial — you only re-prefill the generated tail. Swap earns its keep on very long sequences where PCIe time beats prefill time, and on setups with generous host RAM and idle PCIe. **📅 Volatile:** vLLM's V0 engine exposed both swap and recompute preemption; V1 consolidated toward recompute. Verify against the version you are actually running before asserting either in an interview.

**⚠ Trap:** treating preemption as an error condition. It is not — a well-tuned engine preempts routinely under load, and `num_preempted_requests` climbing is a *signal*, not an alarm, until it correlates with an SLO breach. What *is* an alarm is a preemption **loop**: a sequence gets preempted, rescheduled, immediately preempted again. That means your admitted working set exceeds capacity structurally, and the fix is admission control (`max_num_seqs` down), not more preemption.

### Blocks are reference counted. What bug shows up if you get the refcount wrong, and how does it present in production?

Two bugs, and they present completely differently — which is the useful part of the answer.

**Refcount too high (leak).** A block is never returned to the free pool. Symptom: usable KV capacity monotonically decreases over the life of the process. Your dashboard shows `gpu_cache_usage` creeping up at a fixed traffic level, concurrency slowly falling, preemption rate slowly rising, and then after eleven hours the pod starts thrashing and someone restarts it and it "fixes itself." That is the classic slow-leak signature you already know from a Python object that got captured in a module-level cache — same shape, different arena. The tell is that it is **time-correlated, not load-correlated**: it does not spike with traffic, it accumulates with request count.

**Refcount too low (premature free).** A block still referenced by a live sequence is returned to the pool and handed to another request, which overwrites it. Symptom: **silent, non-crashing corruption of generated text**. The affected sequence starts attending to another request's keys and values. It does not error, it does not OOM, it produces fluent, plausible output that drifts off-topic or — this is the nightmare version in a multi-tenant product — contains content derived from a *different tenant's* prompt. This is the single scariest class of bug in an inference engine, because your unit tests pass, your latency is fine, and your only detector is quality evaluation or a customer complaint.

**⚠ Trap:** believing your integration tests would catch the second one. They will not. Single-request tests never exercise the sharing path, and multi-request tests at low concurrency rarely force reuse of a just-freed block. The test that catches it is a **concurrency soak with deterministic content assertions**: run 200 concurrent requests where each prompt embeds a unique nonce and the model is instructed to echo it, at temperature 0, with the block pool sized deliberately small to force eviction and reuse. Assert every response echoes its own nonce. That test would have caught every cross-request KV corruption bug I have ever seen reported.

**🔍 Failure taxonomy — "output is subtly wrong under load but fine in staging":** (1) Does it reproduce at concurrency 1? If yes, it is not a cache-sharing bug. (2) Does it correlate with `num_preempted_requests` > 0? Preemption/restore paths are where refcounting is most often wrong. (3) Does disabling prefix caching make it vanish? Then it is in the block-sharing/hash path, not the allocator. (4) Does it survive `--enforce-eager`? If disabling CUDA graphs fixes it, the bug is in graph capture with stale pointers, not refcounting.

### Does the paging idea generalize beyond the KV cache? Where else in the stack do you see the same pattern?

It generalizes, and noticing that is a good senior signal because it tells the interviewer you extracted the principle rather than memorizing the instance. The principle is: **when a resource has unpredictable per-consumer lifetime and size, stop reserving contiguously and start indirecting through a table.**

Three places it recurs. **Multi-LoRA serving**: an engine hosting one base model with dozens of tenant adapters faces exactly the KV problem one level up — adapters have different ranks, different residency needs, and unpredictable request mixes. The S-LoRA line of work applies a unified paged pool holding both KV blocks and adapter weights, so that adapter residency and KV capacity trade against each other dynamically rather than being statically partitioned. **Paged optimizer states**: QLoRA's "paged optimizers" use CUDA unified memory to let Adam moment tensors spill to host RAM on a gradient-checkpointing spike, which is demand paging with the CUDA driver as the pager. **Tiered KV storage**: once KV lives in blocks, moving cold blocks to host DRAM or NVMe is a *policy* change, not an architecture change — which is why LMCache-class and Mooncake-class systems could be built on top of paged engines without redesigning them.

The negative cases are just as instructive. Model **weights** are not paged, because their access pattern is fully predictable — every weight is read exactly once per forward pass, so there is nothing to gain from indirection and everything to lose from a gather. Transient **activations** are not paged either; they live in a caching arena because their lifetime is a few kernels long and a bump allocator is strictly better.

**🗣 Say this in the room:** "Paging is the right answer when lifetime and size are unpredictable per consumer. KV, LoRA adapters, optimizer spill — yes. Weights and activations — no, their access pattern is static, so indirection is pure cost. Knowing which side a resource falls on is the whole skill."
